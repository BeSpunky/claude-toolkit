# The lenses

One reviewer per lens. Each entry says **what the lens hunts**, **when it applies**, and **the rubric it judges against** — where the toolkit has a skill for that dimension, the reviewer invokes it, so the review holds the change to the same standard the work was meant to meet. A lens the project's plugins do not provide is judged on its own description.

**Always run:** correctness, architecture, completeness. **The rest:** by what the change touches. **And invent** the lens the change needs when nothing here covers it.

| Lens | Hunts | Applies when |
| --- | --- | --- |
| **Correctness** | Bugs: wrong logic, unhandled edge cases (empty, missing, huge, concurrent, malformed), error paths that swallow or mislead, off-by-ones, races, regressions in what already worked. Runs the tests, then tries to break the change with an input nobody tested. | Always |
| **Architecture** | Boundaries crossed, internals reached into, a concern placed where it fits instead of where it belongs, a missing concept worked around, coupling that grew, a special-case `if`, a flag that makes one unit do two things, a cast silencing a type, a patch at the symptom instead of the root cause. Rubric: `bespunky-engineering:architect-mentality`, `bespunky-engineering:architecture-first`, `bespunky-engineering:software-design`. | Always |
| **Completeness** | The half-done job: an identifier renamed in one place and alive in another (`git grep` it — lock, generated and doc files included), a leftover nothing depends on any more, docs, catalogues, tips and changelogs that no longer match, a release bump or migration the project's rules owe, an assumption about an environment nobody observed. Rubric: the *Finish gate* of `bespunky-engineering:architecture-first`, and the project's `CLAUDE.md`. | Always |
| **Reuse** | Code that duplicates something the codebase already has (search for it), copy-paste between the new pieces, a second occurrence of a pattern that should now be extracted — and the opposite: an abstraction built for a single use. | New code of any size |
| **Scalability** | What breaks at 10× or 1000×: quadratic loops, unbounded reads or memory, N+1 calls, work repeated per item that could be done once, a design that needs rewriting to grow a second instance of the thing. | Code on a data, request or file path |
| **Clean code** | Names that lie or say nothing, functions doing several things, dead code, commented-out code, comments that narrate instead of explain *why*, inconsistency with the surrounding code's idiom and comment density, magic values. | Any code |
| **Security** | Injection (shell, SQL, path, template), secrets in code, logs or transcripts, missing authorisation, trusting input across a boundary, unsafe defaults, floating or unpinned dependencies, over-broad permissions. | Input from outside, auth, shell, network, dependencies |
| **Types** | `any` and casts, types that admit illegal states, types re-declared instead of derived, generics that lost their inference. Rubric: `bespunky-engineering:advanced-typescript`. | TypeScript |
| **UX** | Friction, hoops, unclear states, a wait without orientation, errors that blame or strand the user, input that makes them compile intent into the system's shape, output that makes them decompile data into a conclusion. Rubric: `bespunky-product-ux:astonishing-to-use`, `bespunky-product-ux:keep-users-oriented`, `bespunky-product-ux:model-intent-not-data`. | Anything a person uses: UI, a CLI, prompts, messages |
| **Visual & design system** | Raw values where a token belongs, a pattern's second copy outside the design system, style reach-ins, broken themes or breakpoints. Rubric: `bespunky-design-system:design-system-first`. | Styles, templates, markup |
| **DX** | Is it one step to run, obvious to discover, honest when it fails? Error messages that name the cause and the fix, flags that are consistent, setup that is automated, generator-first respected, a next developer who can understand it cold. Rubric: `bespunky-engineering:nx-monorepo-and-dx`. | Tooling, commands, generators, scripts, APIs, config |
| **Tests** | New behaviour with no test, tests that encode the author's assumption instead of testing it, fixtures that cannot meet the shapes production meets, assertions that would pass on broken code. | Any behaviour change |
| **Prompt & skill design** | For instructions written for a model — skills, agents, directives, hooks: does the trigger text fire when it should and stay quiet when it should not, is every rule stated once, do the instructions contradict each other or the house rules, is the return shape specified? | Skills, agents, prompts, CLAUDE.md-style docs |

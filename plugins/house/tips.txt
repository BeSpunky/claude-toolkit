# Spinner tips for this plugin, shown now and then while Claude works (see plugins/bespunky/hooks/tips.mjs).
# One tip per line; blank lines and lines starting with # are ignored. Keep each short enough to glance at.

/bespunky-house:upgrade brings a project up to the current house standard in one step — it adds no layer
An upgrade on a protected branch opens its own worktree off the integration line — it never commits onto a protected line
/bespunky-house:new creates a project: the house DX on Nx — no Angular, no package.json; add only the layers you pick
Want the house web app? Ask for the angular preset (house.sh new --preset=angular) — Angular, dev loop, design system
Add only the house DX to any repo: /bespunky-house:add-layer agent
Testing a toolkit change before it's published? Add --local to an upgrade to install your working tree
Pick where projects live and how they link when creating one: --layout=apps-libs|packages --linking=paths|workspaces
The row above the prompt saying your house tooling is behind has an Upgrade button — it asks Claude, never upgrades by itself
Adding a layer is its own command: /bespunky-house:add-layer firebase — an upgrade that also creates the layer
A dark-first design? Set $default-mode: 'dark' in the design system's _tokens.scss — 'system' follows the OS
After an upgrade, UPGRADE_VERIFY names the one command that builds, lints and tests what it rewrote
House containers keep your logins across rebuilds — Claude, and every tool that logs in under ~/.config (gh, git through it, firebase)
Need a system package in the container? Add it to .devcontainer/os-packages.txt — it is built into the image, so rebuilds reuse it
Deploying to Firebase App Hosting? Its Root Directory must be the app (--root-dir <the app's dir>) — ask Claude, it knows both deploy modes
Ship the Firebase backend with nx affected -t deploy — functions build through Nx, rules ship from what firebase.json declares
First Firebase deploy? node tools/firebase-deploy.mjs --check ticks off login, alias, deploy and CI — and says how to tell each worked
Rules only in the Firebase console? npx firebase init firestore, then npx firebase init storage, pulls the live ones into the repo (one feature per init)
Your edits inside a house target (inputs, args, configurations) survive upgrades — the upgrade's summary lists any it had to replace, under UPGRADE_ATTENTION
What is running, and whose? tools/dev/dev ps lists every dev stack in every worktree; tools/dev/dev stop takes yours down cleanly
Deploy from CI with /bespunky-house:add-layer ci — the branch model's `ci` bindings decide which branch deploys where
The cloud setup behind CI deploys is yours to run: ! bash tools/setup-gcp.sh --dry-run --environment <env> shows every IAM grant first
Node is one project fact: .nvmrc (or .node-version / volta.node; lts/* works) — the devcontainer and Cloud Functions follow it, and no upgrade moves it
firebase in a house project is the repo's own pinned firebase-tools — the same CLI on every machine and in CI
gcloud in a house Firebase container is pinned in the image — a rebuild never moves it, and its login stays in ~/.config/gcloud

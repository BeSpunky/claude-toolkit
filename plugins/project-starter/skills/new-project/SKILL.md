# Start a new project (BeSpunky standard)

Scaffold a new project into the projects root (see step 1).

## Prerequisite (do not skip)

The `bespunky-project-starter@claude-toolkit` plugin must be installed and **current** in the session running this skill — otherwise this SKILL.md isn't even loaded and the procedural details below aren't in your context. If you have this skill available (you're reading this), good. If you've been asked to scaffold but this skill is **not** available in your session, ask the user to install/refresh the plugin first (`/plugin marketplace update claude-toolkit` then `/reload-plugins`), then re-trigger the scaffolding request. **Do not improvise scaffolding from memory** — every step below encodes a hard requirement and dropping any one of them produces a non-compliant project.

## Requirements, per layer (do not deviate)

**A requirement belongs to the layer that brings it, and a project carries only the requirements of the layers it wears.** Which layers a new project wears is its **preset** plus any `--ensure` (step 0); the layer registry (`assets/nx-tools/src/layers/<id>.ts`, projected into `assets/layers.sh`) is the single source of truth for what each layer is, requires and brings. The bullets below are grouped by layer; when a layer is not in the ensure set, none of its bullets apply and none of its artifacts may appear.

### Every project — the `nx` floor and the `agent` layer

- **Nx is the floor, always ensured**: every house generator and migration runs through `nx g` / `nx migrate`, so no project exists without it. How it is **hosted** depends on the `node` layer: with `node` (a root `package.json`) the workspace is created by `create-nx-workspace --preset=apps` (latest Nx, no version pinning) and `@bespunky/nx-tools` + `@nx/devkit` are exact devDependencies; **without** it, Nx comes through its own **wrapper** — `git init`, then `nx init --useDotNxInstallation` — so the repo gains `nx.json`, `./nx`, `nx.bat` and `.nx/nxw.js`, the toolkit is pinned exactly in `nx.json` → `installation.plugins`, and there is **no** `package.json`, lockfile or `node_modules`. Every Nx command on that host is `./nx …` (the generated `HOUSE.md` renders it that way).
- **Node — never nvm.** The generators run on whatever Node is running the script when it's new enough (22.18+, e.g. inside a devcontainer — no Docker), falling back to the `mcr.microsoft.com/devcontainers/typescript-node:<major>` base image via `docker run` only for an old host Node. The **generated project's** Node major is resolved from the newest available tag (Docker path) or the running Node's major (native path), and lands in the devcontainer below.
- **Devcontainer, COMPOSED from the active layers' fragments** (each layer's descriptor carries its `devcontainer` fragment; the generator composes them into `devcontainer.json` and one `post-create.sh`). The `agent` layer brings the **Claude CLI** (feature), the **Claude VS Code extension** (`Anthropic.claude-code`), the `.claude` persistence mount, and a **neutral base** — `mcr.microsoft.com/devcontainers/base:debian` with Node as a feature (the Nx floor and the house tooling need Node at runtime). The `node` layer **swaps in** the `typescript-node:<major>` image (and brings the `node_modules` volume, `node_modules/.bin` on `PATH`, the `CHOKIDAR_USEPOLLING`/`CHOKIDAR_INTERVAL` polling env and the package-manager install). Firebase, voice, the web dev loop and Angular add their own fragments; nothing is hard-coded per flag.
- **CLAUDE.md** capturing the project's intentions + conventions, plus a bounded generated pointer that **`@`-imports `HOUSE.rules.md`** (the always-on house directives, layer-gated — a project only carries rules that can apply to it) and links the mechanical how-to, with a **toolkit version stamp** in `HOUSE.md`'s header.
- **bespunky/claude-toolkit** marketplace wired into `.claude/settings.json` with **`autoUpdate: true`**, AND pre-installed by the devcontainer's `postCreateCommand` (`claude plugin marketplace add` + `claude plugin install --scope project`), so the toolkit's skills are live the moment the container builds. **Which plugins is the layers' call** (`descriptor.claudePlugins`, one list feeding both `enabledPlugins` and the post-create install): `agent` → `bespunky`, `bespunky-project-starter`, `bespunky-engineering`, `bespunky-workflow`, `bespunky-product-ux`, `bespunky-vscode-identity`, `bespunky-communication`; `web` → `bespunky-browser-automation`; `design-system` → `bespunky-design-system`; `angular` → **`bespunky-angular`** (the optional Angular plugin — `angular-architecture`, `angular-native-wrappers` — worn like the layer itself, never imposed on a project without Angular); `nx` → Nx's own `nx@nx-claude-plugins`. (Declaring `enabledPlugins` alone does not auto-install; the CLI step is what makes it immediate.)
- **Private GitHub repo (always-on)** — full scaffold creates a **private** GitHub repo via `gh` and pushes the project to it. This runs **host-side, after** the scaffold (the `gh` auth lives on the host, not in the base image), so the host running the script must have `gh` installed and authenticated (`gh auth login`). It is **best-effort, never fatal**: if `gh` is missing/unauthenticated, or an `origin` remote already exists, the script logs a `GITHUB_SKIP` reason and the (fully committed) local repo is left intact. Opt out with **`--no-github`**. Sync mode never touches the remote. **Why always-on, not just for Firebase:** Firebase App Hosting deploys are GitHub-driven — linking the repo at `firebase apphosting:backends:create` is what makes Firebase provision its own Cloud Build CI/CD, so the repo must already exist; and every other project still wants a remote. The scaffolder generates **no** deploy workflow of its own — see the Firebase bullet.

### `angular` — the house web app (the `angular` preset)

- **An Nx monorepo in the workspace shape you chose** (*The workspace shape* below: the app in the layout's apps directory — `apps/` by default — linked by `paths` unless `--linking=workspaces`), via `create-nx-workspace` (the `node` host) then `nx add @nx/angular` (the layer's `nxPlugin`). A literal `angular-*` preset always forces a demo app and is verified impossible to suppress; `apps` + `nx add @nx/angular` is the only one-shot Angular-ready path with no demo.
- **One clean `--minimal` app** (no Nx welcome/demo content), created through the **Angular stack adapter** by the house `app` generator (`--stack=angular`).
- **Dev server reachable from outside the devcontainer**: the app's `dev-server` leaf gets `host: 0.0.0.0`. File-watching over Docker bind mounts is the `node` layer's `CHOKIDAR_*` polling env on the devcontainer — modern Angular's `@angular/build:dev-server` does **not** accept a `poll` option, which is why polling lives there, not on the target.
- **Angular AI tooling** — the layer's `angular-ai` generator wires Angular's official AI tooling in two layers. (1) **MCP**: a project-scoped, committed `.mcp.json` declaring the **Angular CLI MCP server** (`npx -y @angular/cli mcp` — always the latest CLI). Only the **default knowledge tools** are enabled (`get_best_practices`, `search_documentation`, `find_examples`, `ai_tutor`, `onpush_zoneless_migration`); the **experimental exec tools** (`build`, `devserver.*`, `test`, `e2e`) are deliberately omitted because an integrated Nx workspace has **no root `angular.json`** — they read `angular.json` / shell out to `ng build` and would only pull agents off Nx-owned targets. The generator **merges** into any existing `.mcp.json`, preserving user-added servers. (2) **Skills**: the Angular **agent skills** (`angular-developer`, `angular-new-app`) are **not vendored** — `post-create.sh` fetches them fresh from `github.com/angular/skills` into `.claude/skills/` on every container build (gitignored cache; the skills repo is itself auto-generated upstream, so a fork would silently go stale). Comes with the layer — every project wearing `angular` gets it, no project without it does.

### `web` — the dev loop (any stack)

- **One stack-free dev engine.** `.bespunky/dev.json` declares what the project serves (apps → processes, their ports, env, readiness, URLs); the generator-owned **`tools/dev/dev serve`** (Node built-ins only) runs it — worktree selection, a port offset sized from the declared ports, a `http://<slug>.localhost` domain per worktree (`worktree-domains`), the shared co-driven browser, one Ctrl+C. On an Nx app, `nx serve <app>` is a thin wrapper over it (the house `serve` executor), so the flags are the engine's, kebab-case: `--worktree=`, `--port-offset=`, `--skip=`, `--no-shared-browser`, `--no-install`, `--dry-run`. Two exist only on the Nx face, because they are Nx's: `--configuration=` (the target's configurations) and `--no-emulators` (an alias the executor turns into `--skip=emulators`); `tools/dev/dev` refuses both. A Python or Go project writes `dev.json` by hand and gets the same engine. The `dev` generator seeds a declaration entry for every Nx app with a serve composer that lacks one, and never overwrites one afterwards (the project owns it).
- **Shared browser** — one headed Chromium on Xvfb, co-driven by a human over noVNC and an agent over CDP. The web layer's post-create provisions it with `bash tools/shared-browser/shared-browser install --with-deps` (it carries its own pinned `playwright-core` runtime, so it needs no `package.json`).

### `js` — TypeScript/JavaScript libraries

- **Playwright** — the layer's `playwright` generator pins `@playwright/test` in `devDependencies`, and the devcontainer's `post-create.sh` detects that entry and runs `playwright install --with-deps chromium` (Chromium binary + apt deps), cached in a per-workspace Docker volume so rebuilds reuse it. Pairs with the `bespunky-browser-automation:playwright` skill.
- **Libraries** are `nx g @bespunky/nx-tools:publishable-lib <name> --stack=<adapter>` (`--stack=js` for plain TypeScript; `--nonAngular` is a deprecated alias of it).

### `design-system` — in the `angular` preset, from moment zero

- The `design-system` generator creates the workspace's **single source of visual truth** in the workspace's libraries directory (`<libsDir>/design-system` — `packages/design-system` by default) **from moment zero**. This is not a nicety: a design system introduced after five screens of hardcoded hex is not a design system, it is an archaeology dig — the values are already scattered, and nobody will ever go back for them. Its **core is stack-neutral** — design tokens as **CSS custom properties** (the runtime layer — switching theme is a *re-binding through the cascade*: live, no rebuild, no second stylesheet) and a **zero-output SASS API** (token accessors that `@error` on an unknown key, the single `theme()` emission, mixins, placeholders — with a **public** barrel at `styles/_index.scss` carrying an explicit `@forward … show` contract and the implementation in `_`-prefixed folders named for what they are — `styles/_core/` (the token engine) and `styles/_utils/` (the authoring toolkit)) — and the **stack binding comes from the app's adapter**: on Angular, a publishable library (ng-packagr via `publishable-lib`, `nx release`, Vitest, the tsconfig path alias), the TS half of the theming mechanism (`DsTheme`, the one thing that writes the `[data-ds-mode]` attribute) and `provideDesignSystem()`. Tagged `type:design-system`, with a `STRUCTURE.md` telling feature work where components and styles go. It ships **zero components and zero opinionated visual styles** — the token *values* are loudly-marked **placeholders** that exist only so the library compiles and the app runs on day zero, and the design phase (`bespunky-product-ux:stage-the-vision` → `realize-the-vision`) replaces them wholesale. Every app is wired to it through its adapter (on Angular: sass load path + an implicit dependency for cache correctness + the `@use`/`ds.theme()` blocks + `provideDesignSystem()`), including apps added *later*, because the `app` generator runs the layer's same per-app step. The always-on `Design-system-first` directive in `HOUSE.rules.md` and the `bespunky-design-system` plugin are the behavioural half of the same layer.

### `firebase` — opt-in

- **Firebase support is opt-in**: when scaffolded with `--firebase` (or `--ensure=firebase`), the scaffolder wires Firebase end-to-end. The layer is a **capability on the Nx floor**, not an Angular feature: its neutral core (`firebase.json`, the emulator suite, Cloud Functions, the tooling under `tools/`) is the `firebase-emulators` workspace step, and the client half reaches an app only through that app's **stack adapter** (`firebase-client`, the per-app step — on Angular, the environment files and providers below):
  - **Devcontainer** (the layer's fragment): adds the **Firebase CLI** (`ghcr.io/devcontainers-extra/features/firebase-cli`) + **Google Cloud CLI** (`ghcr.io/jajera/features/gcloud-cli`) features, the `toba.vsfire` VS Code extension, labeled `portsAttributes` entries, and **explicit same-port `forwardPorts`** for the dev server + emulator suite (4200, 4000 UI, 9099 Auth, 8080 Firestore, 9150 ws, 9199 Storage, 5001 Functions). Same-port forwarding is **required** for the app to work in a host browser: the page loads over forwarded :4200, then the Firebase SDK *inside that page* calls the emulators at the hardcoded `localhost:9099`/`localhost:8080` from `environment.ts` — addresses that only resolve from the host when those container ports forward to **identical** host ports (auto-forward may pick a different free port, which the browser SDK can't discover → `ERR_CONNECTION_REFUSED` on auth refresh → Firestore writes hang). Tradeoff: parallel Firebase devcontainers collide on these host ports; to run several, re-port one container in `devcontainer.json` + `environment.ts` + `firebase.json` together. Backend emulators are `onAutoForward: "silent"`, the dev server `openPreview`.
  - **Emulator config**: writes **`firebase.json`** — the emulator suite (+ `singleProjectMode: true`) **and a `functions` block** pointing at the built Nx output (`dist/<appsDir>/functions`, predeploy = `yarn nx lint functions && yarn nx build functions`). The functions block is **required**: a configured functions emulator with no backend behind it makes `emulators:start` fatally abort. The `emulators`/`functions` keys are generator-owned; other top-level keys the user adds (rules paths, …) are preserved. The generator does **not** write `.firebaserc` — the cloud-project linkage belongs to the Firebase CLI (`firebase use --add` validates against the user's actual account). The launch script passes `--project=demo-<workspaceName>` explicitly so emulators work without `.firebaserc`, without login, and without a real GCP project (the `demo-` prefix is Firebase's documented offline-only convention). Also adds the `.gitignore` entries (`*-debug.log`, `firebase-debug.*.log`, `/.emulator-data`, and `apps/functions/.secret.local`).
  - **Cloud Functions as a first-class Nx app** (`<appsDir>/functions` — `apps/functions` by default; an existing functions project stays where it is): esbuild-bundled by `nx build functions` into `dist/<appsDir>/functions` with a generated deploy-manifest `package.json`; runtime deps (`firebase-admin`/`firebase-functions`) live at the **workspace root** (no per-project `node_modules`); lints via the workspace flat config; `nx run functions:deploy` runs `firebase deploy --only functions`. **Functions secrets** (`defineSecret`) get a one-source-of-truth flow: the gitignored `apps/functions/.secret.local` (shape documented by the committed `.secret.local.example`) is injected beside the local bundle by `tools/emulators.sh` for the emulator, and pushed to **Google Secret Manager** for prod by `nx run functions:push-secrets` (`tools/push-secrets.sh` — each value via stdin, never a command line or log). Source files + `.secret.local.example` are written only if absent (the user owns their functions); the build/lint/deploy/push-secrets targets are generator-owned. A **platform firewall** is inserted into the root ESLint config's depConstraints: `platform:web` (the app) bans `firebase-admin`/`firebase-functions` imports; `platform:server` (`functions`, `firebase`) bans `firebase`/`@angular/*`.
  - **The emulator suite as its own workspace-level Nx project** (`firebase/project.json`): targets `emulators` (full suite, `dependsOn` functions:build), `emulators:auth`/`:firestore`/`:storage`/`:functions` (one + UI), `seed:build`, and `reset` — all funneling through **`tools/emulators.sh`** (the single launch path: **reap → prime → start**). Reap = `tools/reap-emulators.sh`, a verified process+port reclaim (kills orphaned emulator JVMs by cache path, then polls the configured ports until actually free, SIGTERM → SIGKILL) so an ungraceful prior death never breaks the next start. Prime/start = the **seed & cache layer**: the suite imports the gitignored `.emulator-data/` working dir (primed from a committed seed in `tools/emulator-seeds/` on first run) and exports back on clean exit (full runs only) — onboard once, session + data survive every serve. Seeds are generated from the **declarative, user-owned `tools/seed/world.mjs`** via `nx run firebase:seed:build`; reset on call with `nx run firebase:reset`.
  - **App initialization** (the Angular adapter: Angular's environment-files pattern, **per-service emulator-aware**): generates **`environment.interface.ts`** (the shared shape), **`environment.ts`** (dev — `production: false`, `authDomain: 'demo-<workspaceName>.firebaseapp.com'`, and a **per-service emulator toggle**: an `EMULATE` map drives each service's emulator `default`), and **`environment.prod.ts`** (production). **All three are write-if-absent** — each holds real per-project values (the web config, custom emulator ports, app-specific blocks the project added to the interface), so an existing one is the project's and never the generator's to rewrite. Carrying a **pre-toggle** bundle (bare emulator endpoints, and the interface that typed them as bare strings) onto the per-service shape is therefore **migration `0.24.3/upgrade-emulator-environment-shape`**, not generator healing — see §1d for why that one is the most consequential migration in the ladder. The production build swaps in `environment.prod.ts`. **Going all-real is a runtime override, not a build** — `nx serve <app> --no-emulators` opens the app with `?emulate=none`, resolving every service against `environment.ts`'s `firebase` block; there is **no** `environment.no-emulators.ts` and **no** `no-emulators` build configuration (both retired — sync removes them). **`emulator-overrides.ts`** (generator-owned) is the per-session override resolver — `?emulate=`/`?real=`/localStorage, precedence *default < localStorage < URL* — so a dev can run e.g. **Firestore emulated + real Auth** without editing source or rebuilding. **`firebase.config.ts`** exports `provideAppFirebase()` — the Firebase **app** and nothing else — and **one file per SDK service beside it** (`firebase-auth.config.ts` → `provideAppAuth()`, and the same for `firebase-firestore` / `firebase-storage` / `firebase-functions`), each gating its own emulator wiring on `committed-default ⊕ override` behind **`ngDevMode`** — Angular's dev-mode flag, which the optimizer folds to `false` in production builds, so the resolver, every `connect*Emulator(...)` call, the endpoints, and the whole override module tree-shake out of the prod artifact. (We gate on `ngDevMode`, **not** `environment.production` — the latter, a const-object property, isn't reliably inlined by the esbuild builder and leaves emulator code in prod; verified by grepping the production bundle. Firebase's own SDK still ships its internal emulator support — that's library code, not ours.) The fail-loud prod guard lives here too (and stays on `environment.production`, since it SHOULD ship in prod). **`firebase.config.ts` is generator-owned by default** — written when absent and rewritten on outdated shapes (the ancient two-consts shape, the pre-per-service whole-block shape, OR a per-service file that predates the `ngDevMode` prod-DCE gate; `--sync --firebase` self-heals all of them, with a logged warning to re-apply any custom provider wiring). Once it's on the current shape (imports `'./emulator-overrides'` **and** uses the `ngDevMode` gate) it's left alone.
  - **App wiring**: best-effort insertion of `provideAppFirebase()` into `<appsDir>/<app>/src/app/app.config.ts`'s providers array, followed by the four **service** providers as a **commented menu** naming each one's weight on the initial bundle and where it usually belongs (logs a warning if the file shape is unrecognized — you then add it manually). **Only the Firebase app is wired**: a service is provided where it is used — at root, or in the `providers` of the **lazily-loaded** routes file that needs it. So the first `inject(Firestore)` in a fresh app throws `NullInjectorError` until it is placed, which is the deliberate price of not charging every app for services it may never call (measured on a fresh app: 479 kB initial raw with all four at root against 238 kB with the Firebase app alone). Two traps: a providers array in the **eager** `app.routes.ts` defers nothing (a static import is what pins a chunk — it must be the file behind `loadChildren`), and a **guard** named in the eager `app.routes.ts` is statically imported by the initial chunk, so its `inject(Auth)` pins `@angular/fire/auth` there wherever the provider is written — an auth-gated app therefore keeps `provideAppAuth()` at root by construction. (Route providers *are* visible to that route's own `canActivate`; only a child route's are not. The reason is bundling, not DI.)
  - **Nx targets** — the app's local dev loop is the `web` layer's dev engine (`.bespunky/dev.json`, run by `tools/dev/dev serve`; `nx serve <app>` wraps it) with the app's **`dev-server`** leaf as its primary process, *not* a Firebase-specific target set. What `firebase-emulators` contributes is the **workspace-level emulator suite** (`firebase:emulators*` on `firebase/project.json`), seeded into the app's `dev.json` entry as an `emulators` process beside the dev-server: `nx serve <app>` brings up emulators + app together (one Ctrl+C, the full offline stack); `nx serve <app> --no-emulators` (an alias of `--skip=emulators`) skips the suite and resolves every service real (`?emulate=none`). The per-app `emulators*` targets of earlier generations moved to the workspace-level `firebase` project (run/restart the suite alone via `nx run firebase:emulators`). **Earlier generations are carried forward by MIGRATIONS, not by healing code in the generator** (§1d): `0.24.0/unify-serve-targets` collapses the legacy inner dev-server names (`serve-app`/`serve-standalone`) into the single `dev-server` leaf and drops the retired `serve-worktree`/`serve-with-shared-browser` targets, `0.24.1/relocate-emulator-targets` moves the per-app `emulators*` targets to the workspace-level `firebase` project and removes the `build:no-emulators` configuration plus `environment.no-emulators.ts`, and `0.24.3/upgrade-emulator-environment-shape` carries the *environment files themselves* onto the per-service toggle shape this serve loop assumes — without it `--no-emulators` is the only mode that behaves, because every service silently resolves real (§1d). The app is left with just the unified `serve` + `dev-server`.
  - **Deps**: the generator adds `firebase` + `@angular/fire` (dependencies), `firebase-admin` + `firebase-functions` (the Functions runtime, at the **workspace root** — keep aligned with `<appsDir>/functions/package.json`, the deploy manifest), and `@nx/esbuild` (devDependency, pinned to the workspace's own Nx version — Nx plugin packages move in lockstep with `nx`) to `package.json`, then runs the package-manager install via Nx's `installPackagesTask` (post-commit). Existing entries are never overwritten (user pins survive `--sync`). No shell-side `yarn add`.
  - **CI/deploy is Firebase's, not ours**: the scaffolder writes **no GitHub Actions deploy workflow**. Deploy CI is wired when the user links the (always-created, see the GitHub bullet above) repo at `firebase apphosting:backends:create` — App Hosting then provisions and maintains its own Cloud Build pipeline and auto-deploys on every push to the configured branch. This is deliberate: relying on Firebase's native GitHub integration means deploys keep working as Firebase evolves its mechanism, with nothing in the project to maintain. The repo-as-CI linkage is documented in the "connect a real Firebase project" recipe below, the `{{#firebase}}` blocks of the generated `HOUSE.md`, the `apphosting.yaml` header comment, and the devcontainer welcome banner.
  - **Never enabled by default** — only when the user explicitly asks for Firebase or **you asked and they said yes**.
- **Voice support is opt-in**: when scaffolded with `--voice`, the `devcontainer` generator bridges the **host's audio server** into the container — WSLg on Windows, or a native PulseAudio / PipeWire(-pulse) socket on Linux. Where that socket lives is a **per-machine fact**, so nothing host-specific is committed: a generator-owned `.devcontainer/host-probe.sh` runs on the host (`initializeCommand`) on every open and points the gitignored `.devcontainer/.host/pulse` at whichever socket directory exists (an empty directory when there is none, so the bind mount can never fail on any host); the container always sees it at one fixed endpoint, `PULSE_SERVER = unix:/run/bespunky/host/pulse/native`. The devcontainer's `post-create.sh` **self-adapts on a socket being present** to install the free **espeak-ng** TTS floor + `pulseaudio-utils` and pre-install the **`bespunky-voice`** plugin at project scope, so `/speak` works the moment the container opens. (Piper — the natural neural-voice upgrade — stays a manual, machine-local opt-in via the plugin's `install-piper.sh`.) **Why opt-in, not always-on like Playwright/shared-browser:** `voice` records the project's **intent** ("this project wants audio") — an extra host probe and package install that most projects don't need. One flag wires all three halves — the audio bridge, the engine, and the plugin — and because post-create keys off the socket rather than a second flag, `--sync --voice` retrofits voice onto an existing project too. **Never enabled by default** — only when the user explicitly asks for hands-free/spoken output.

## Generator-first, manual last (applies to ALL scaffolding)

For anything Nx can generate - apps, libraries, components, services, project config - **use the Nx generator (`nx g ...`); never hand-create and fill files.** Before hand-writing anything structural, check what exists: `nx list <plugin>` / `nx g <generator> --help` (or the `nx-generate` skill / the Nx MCP server). Only fall back to manual file creation when no generator covers the task. **Never guess flags** - verify against `--help` / `nx_docs`.

In this skill that means: the workspace, every Nx plugin, the app, the dev loop, the design system, the devcontainer, the Claude settings, and the house docs all come from generators — the `@nx/*` ones plus the house `@bespunky/nx-tools` generators. Which ones run is not a list in this skill: it is each ensured or detected layer's `generators` (`workspace` steps, and per-app `app` steps), read by the planner (`cli.js plan`). The `app` generator creates an app through its stack's **adapter** (`--stack=<adapter>`) and runs every active layer's per-app steps on it, so it is the single command for the first app *and* every later one. The **only** non-generated artifact is the project-specific half of `CLAUDE.md`, which the skill fills in (the file itself, and its pointer block, are generated).

## 0. Gather inputs (skip any already provided)

1. **Project name** - kebab-case; becomes the project folder and the workspace name.
2. **Project intentions** - 2-4 sentences: what it's for, who uses it, the core domain. Drives CLAUDE.md.
3. **Which preset / layers** - what the project should wear. **Default: the `agent` preset** (`nx` + `agent`: the house DX on the Nx floor, wrapper-hosted — no `package.json`, no framework, no app). Ask only when the user's intent doesn't already say it; offer the presets by what they get:
   - `agent` (default) — the house DX for any kind of project (Python, Go, docs, a stack still to be chosen);
   - `node` — `nx`, `agent`, `node`: a Node workspace (root `package.json`, the toolkit as exact devDependencies);
   - `angular` — `nx`, `agent`, `node`, `web`, `angular`, `design-system`: the house web app (Angular app + dev loop + design system from moment zero).
   Further layers ride on top with `--ensure=<csv>` (`scaffold.sh --help` lists what a scaffold can ensure). The set is **closed under `requires`**, so asking for a layer brings its prerequisites with it (announced, not an error).
4. **First app name** - **only when a chosen layer creates an app** (a stack whose adapter can create apps — today `angular`). Defaults to the project name; lives at `<appsDir>/<app-name>` (`apps/` unless the layout says otherwise). Without such a layer, don't ask — the script refuses an `[app]` argument it has nothing to create with.
5. **Firebase?** - **only when the project will have an app or Cloud Functions to wire it into** (in practice, the `angular` preset). Will it use Firebase (Firestore, Auth, Hosting, Functions, Storage)? **If the user hasn't stated it, ASK** — yes/no, one question. Default: **no**. When **yes**, pass `--firebase` (the firebase layer: emulator suite, Cloud Functions app, and its devcontainer fragment — the Firebase CLI + Google Cloud CLI features, `toba.vsfire`, labeled `portsAttributes` and same-port `forwardPorts` for the dev server + emulator suite, required for the Firebase SDK in a host browser to reach the emulators at their hardcoded `localhost:<port>` addresses). `firebase` requires `node`, so it brings a Node workspace with it. Do **not** silently turn this on — it's an opt-in.
5b. **Workspace shape** - **only when `node` is ensured, and only when the user's intent says it** (never a question by default — the default is the house's long-standing output). Two independent choices, see *The workspace shape* below: **layout** `--layout=apps-libs` (`apps/` + `libs/`) or `--layout=packages` (everything under `packages/`), omitted = `apps/` + `packages/`; **linking** `--linking=paths` (the default: `project.json` + tsconfig `paths`) or `--linking=workspaces` (an Nx TypeScript-solution workspace: package.json projects, package-manager workspaces, project references). Pass them when the user asks for "an apps/libs monorepo", "a packages-based repo", "npm/pnpm workspaces", "a TS-solution / project-references setup", or names the folder convention they want.
6. **GitHub repo** - **not an input**: a private GitHub repo is created automatically (see *Every project* above). You don't need to ask. Only pass `--no-github` if the user explicitly says they don't want a remote. (Prerequisite: the host has `gh` installed and authenticated; if not, the script skips repo creation gracefully and you tell the user how to create it later.)

## 1. Run the scaffold script

The bundled script is at **`${CLAUDE_SKILL_DIR}/assets/scaffold.sh`** (that variable resolves to wherever this skill is installed - never hardcode a path). It runs the generators on the **local Node when it's new enough (22.18+ — e.g. inside a devcontainer), with no Docker at all**, and falls back to the typescript-node base image via `docker run` only when the local Node is too old (`--docker` forces the image). Docker was never the requirement — a modern Node was. **Run the whole script** - do not replicate its steps by hand; the phases together are the project's requirements.

**A scaffold is a sync with an ensure set, against an empty directory** — and that is now literally how it runs. The script forms the **ensure set**, then every bootstrap step below is **gated on it**; scaffold.sh names no layer itself (it reads the registry projection, `assets/layers.sh`):

- **1.0 Form the ensure set**: `ENSURE = nx (the floor) ∪ the preset (--preset=<id>, or the default agent preset when neither --preset nor --ensure is given) ∪ --ensure ∪ {firebase if --firebase}`, then **closed under `requires`**. A layer that can only come into being *via* another (`web` via an app-creating layer — `web` alone cannot say which app it serves) is still refused when its partner is missing. Presets are data (`assets/nx-tools/src/layers/presets.ts`), projected into `layers.sh` like the rest of the registry.
- **1.1 The host** — decided by the ensure set:
  - **`node` ensured → node host**: `create-nx-workspace <project> <preset> --packageManager=yarn --nxCloud=skip --no-interactive`, where the preset is the **linking** choice: `--preset=apps --workspaces=false` for `paths` (the default), `--preset=ts --workspaces=true` for `workspaces` (`--preset=apps --workspaces=true` was verified to produce no TS-solution at all). A root `package.json`, yarn; the agent-mode env vars are stripped for this one command, because create-nx-workspace's "AI Agent Mode" ignores `--preset` and would make the linking choice for you.
  - **otherwise → wrapper host**: `mkdir` + `git init`, then the same `nx init --useDotNxInstallation` block a sync uses on a repo with no `package.json` — `nx.json`, `./nx`, `nx.bat`, `.nx/nxw.js`, and nothing that makes the repo a Node project.
- **1.2 Nx plugins** — each ensured layer's `nxPlugin` is `nx add`ed, in registry order (`angular` → `nx add @nx/angular`; under `--linking=workspaces` with `NX_IGNORE_UNSUPPORTED_TS_SETUP=true` inline for that one command — see *The workspace shape*).
- **1.3 Install the house plugin (`@bespunky/nx-tools`)** — the **published** package, pinned to an exact version (never a caret): an exact devDependency on the node host, an exact `nx.json` → `installation.plugins` pin (beside `@nx/devkit`, pinned to the Nx version) on the wrapper host. It is a real, declared install, not a copy dropped into `node_modules`: a copy is undeclared, so every generator's `installPackagesTask` prunes it, and — the reason that matters most — `nx migrate` reads the *resolved* version to decide which migrations a project needs, which a copy would always answer with the newest one. Nothing is compiled on this path; the published package ships compiled JS. **Only `--local`** (developing the toolkit itself) compiles: it builds the working tree, `npm pack`s it, and installs that tarball instead of the registry copy — still a real install, only its origin differs. See §1d for the migration ladder this ordering exists to serve.
- **1.3b The layout** — only with `--layout`: `nx g @bespunky/nx-tools:workspace-layout --layout=<id>` declares it in `nx.json` → `workspaceLayout` **before the first project exists** (an empty workspace has nothing to infer a layout from, so every generator after it — the first app, the design system — reads the declaration). Without `--layout` nothing is declared, and the resolver's default (`apps/` + `packages/`) is exactly the old output.
- **1.4 The first app — only when an ensured layer is a stack whose adapter can create apps** (today `angular`): `nx g @bespunky/nx-tools:app <appsDir>/<APP> --stack=<adapter> --layers=<ensure set>`. The house `app` generator **creates** the app through the stack's adapter (on Angular: `@nx/angular:application` with the house defaults `--minimal --style=scss --routing --e2eTestRunner=none`) and then **attaches** every capability by running each active layer's **per-app steps** — the same steps a sync runs: the web layer's `serve` + `serve-options` (the `nx serve` wrapper over the dev engine, `host: 0.0.0.0` on the `dev-server` leaf), the design system's `design-system-styles`, the Firebase client under `firebase`, the Angular `worktree-tab-label`. `--layers` is passed because at first-app time nothing this run ensures exists yet to be detected. This is the **same one command a developer runs to add any later app**, so the first app and every subsequent app are configured by one code path and can't drift. No app-creating layer → no app, and an `[app]` argument is refused.
- **1.5 The planner — exactly as in a sync.** The script asks the installed package for the plan (`cli.js plan`) and runs each line as `nx g @bespunky/nx-tools:<generator> <args>`: per-layer **workspace steps in registry order**, then **`house-doc` last** (it writes the stamp, so it must see the final layer set). Nx-native via devkit `Tree`, format-aware, **all idempotent**. Which generators that means depends entirely on the ensure set — for orientation:
  - `agent` → `devcontainer --name=<PROJECT> --nodeMajor=<MAJOR> --layers=<active>` (the devcontainer **composed** from the active layers' fragments — see *Every project*; `--voice` adds the voice fragment), `claude-settings --layers=<active>` (**merges** the house keys — marketplaces + `autoUpdate: true` + `enabledPlugins` from the layers' `claudePlugins` + `permissions.defaultMode` — into `.claude/settings.json`; every key it does *not* declare, the project's own `hooks`, extra `permissions.allow`, `env`, `statusLine`, survives a `--sync`), `window-identity --name=<PROJECT>`.

### 1z. The layer model — what makes this work on a repo that isn't the house shape

**A project is not one shape; it is a stack of layers.** Each has its own detector, its own generators, and its own reason to exist. This is what lets the same script scaffold a greenfield Angular+Firebase monorepo *and* add house DX to a five-year-old TypeScript library without imposing a framework on it.

| Layer | Requires | Detected by | What it owns |
| --- | --- | --- | --- |
| `nx` | — | `nx.json` | **The floor, always ensured** — every house generator and migration runs through Nx; `nx init` in place (into `node_modules` with a `package.json`, else through the `./nx` wrapper). Every sync on it writes each applied layer's `.gitignore` entries (`gitignore`) and the house docs, `HOUSE.rules.md` + `HOUSE.md` (`house-doc`, the stamp) |
| `agent` | — | `.devcontainer/.bespunky-devcontainer.json` or `.vscode/.window-identity.json` | **Stack-agnostic DX**: the composed devcontainer, Claude settings, window identity |
| `node` | — | a root `package.json` | The typescript-node devcontainer image, the `node_modules` volume, the package-manager install |
| `js` | `nx` | `@nx/js`, or an `@nx/js:` executor | `publishable-lib --stack=js`, tool extraction, `nx release`, `@playwright/test` (pinned) |
| `web` | `agent` | `.bespunky/dev.json`, or a dev-server: a `dev-server` target, the house `serve` composer, or a dev-server executor a stack adapter recognises (never merely a target called `serve` — a backend has one) | The stack-free dev engine (`tools/dev/dev serve`), worktree domains, the shared browser |
| `angular` | `nx`, `node` | `@angular/core` / `@nx/angular`, or an Angular executor (`@angular/build:`, `@angular-devkit/build-angular:`, `@nx/angular:` — the adapter's own list) | The Angular adapter: `app --stack=angular`, the dev-server leaf, `angular-ai`, the `bespunky-angular` plugin |
| `design-system` | `nx` | the `type:design-system` tag | `design-system`, `ds-theme`; wired into apps through their adapter. With the **Angular** adapter also `ds-component` and `secondary-entrypoint` (both need the `angular` layer) |
| `navigation` | `angular` | the `type:navigation` tag | `navigation-core`, `domain-navigation` |
| `firebase` | `nx`, `node` | `firebase.json` | Emulators, `<appsDir>/functions`, apphosting; the client half through the app's adapter |

**This table is a reading of the registry, not the registry.** The source of truth is one file per layer at `assets/nx-tools/src/layers/<id>.ts`, registered in `layers/registry.ts`; `assets/layers.sh` is **generated** from it (titles, requires, evidence, ensurability, hints) and is what `scaffold.sh`, its `--help`, and the `SessionStart` hook read. `scaffold.sh --help` prints which layers each mode can ensure — trust it over this table.

**Stacks vs capabilities.** A **stack** builds things (apps, libraries, environment files, providers, styles, dev-server ports) — it is an **adapter** (`assets/nx-tools/src/adapters/`: `angular`, `js`). A **capability** (`firebase`, `design-system`, `navigation`, `web`) is something a project wears; it does its framework-neutral part itself and reaches an app **only through that app's adapter's ports** — so wearing the design system or Firebase does not drag Angular in, and a new stack is one adapter, not an edit to every capability.

Two separate questions, and keeping them apart is the whole design:

- **DETECT** — what the workspace already *has*. Read from the workspace itself (never declared, never inferred from a flag), so the scaffolder and the generators can't disagree about what a project is. Detected layers get **refreshed** — that is what a sync does.
- **ENSURE** (`--ensure=<csv>`, or a `--preset=<id>` — a named ensure set; the two union) — which layers this run should **bring into being**. Always explicit. A sync ensures **nothing above the Nx floor** by default: refreshing house tooling and turning someone's library into an Angular app are very different requests, and only one of them was asked for. The floor itself is the exception because nothing house-shaped runs without it.

#### The workspace shape — layout and linking

Two more facts about a workspace, **orthogonal** to its layers and to each other, kept on the same detect/choose split:

| Fact | Values | Detected from (sync, and every generator) | Chosen by (scaffold only) |
| --- | --- | --- | --- |
| **Layout** — where projects live | `apps-libs` (`apps/` + `libs/`) · `packages` (`packages/` for everything) · default `apps/` + `packages/` | `nx.json` → `workspaceLayout` → else inferred from where existing projects sit (`tools/` excluded) → else the default | `--layout=<id>`, recorded in `nx.json` → `workspaceLayout` |
| **Linking** — how projects reach each other | `paths` (`project.json` + tsconfig `paths` aliases) · `workspaces` (Nx TypeScript-solution: package.json-defined projects, package-manager workspaces, TS project references; a consumer declares `workspace:*` / `*`) | Nx's own TS-solution predicate (workspaces on + a references-only `tsconfig.json` + a composite `tsconfig.base.json`) | `--linking=<id>` — `workspaces` needs the `node` layer (a package.json to declare workspaces in) |

**Omit both and the output is exactly what the house always produced.** A **sync refuses both flags** — an existing workspace already *is* some shape, and the sync detects it; changing an existing workspace's shape is a migration of the user's repo, not a flag. Every house generator places and links through the detected shape (a library generator under `workspaces` makes a real package and declares it in each consumer; under `paths` it writes the alias), and `house-doc` renders the project's real directories and its linking model into `HOUSE.md` → *Workspace layout & linking*. So **never write `apps/` or `libs/` into a command from memory** — read the project's `HOUSE.md`, or give a house generator just a name (`nx g @bespunky/nx-tools:app --name=<n>` lands in the resolved apps directory).

**Angular + `workspaces` is an honest hybrid.** `@nx/angular` refuses TS-solution workspaces (the Angular compiler does not support project references); the house steps past that guard with upstream's opt-out `NX_IGNORE_UNSUPPORTED_TS_SETUP`, scoped to one generator call at a time. Angular apps become `project.json` islands that consume workspace packages through their `exports`; Angular libraries are real workspace packages. The opt-out is **undocumented** upstream — say so when a user picks this combination; if Nx removes it, the house generators fail loudly with Nx's own error, and the toolkit's fixture test is the tripwire.

**The scaffold is a sync with an ensure set against an empty directory** — literally: its bootstrap (the host, the Nx plugins, the first app) is gated on the ensure set (step 1), and after it the same planner a sync uses runs the same steps, so the two modes can't drift.

#### Retrofitting an existing repo (the common non-scaffold case)

```
bash "${CLAUDE_SKILL_DIR}/assets/scaffold.sh" --sync --ensure=agent [--yes] <PROJECT_PATH>
```

That gives *any* repo the house DX and nothing else: the Nx floor laid **in place** with `nx init` if it has none — into `node_modules` when the repo has a `package.json` (plus `@nx/devkit`, which an `nx init` workspace does not ship), otherwise through Nx's **wrapper** (`./nx`, `.nx/nxw.js`, the toolkit pinned in `nx.json` → `installation`), so a Python or Go repo does **not** become a Node project — the devcontainer, `.claude/settings.json`, the window identity, and `HOUSE.md` — with **no Angular, no design system, no dev-loop tooling**, because none of those layers is present or requested. The generated `HOUSE.md` renders only the sections that apply, so a plain library is never handed instructions for an Angular MCP server it doesn't have.

**On the node host it adopts the project's package manager** (the wrapper host has none to adopt — the wrapper installs with npm into the gitignored `.nx/installation`). A scaffold sets the house standard (yarn); a sync detects — `packageManager` (corepack) first, then the lockfile — and routes every install/exec/add through it. Say this when offering a sync on an npm or pnpm repo: running yarn there would leave a **second lockfile**, and `npm ci` would start failing for the whole team. A repo that declares nothing gets the house default, written down *before* `nx init` runs (which otherwise picks npm on its own and produces the same two-lockfile mess from the other direction). If the project's package manager isn't installed locally, the script falls back to Docker rather than substituting a different one.

**What it will NOT do to a repo that already has its own setup** — this is the part to state plainly when offering it:

- An existing **`.devcontainer/devcontainer.json`** is **merged additively**: house keys that are missing get added, and everything the repo already declares — its image, its name, its `postCreateCommand`, its features, its comments — is left exactly as-is.
- **Ownership is explicit and the divergence is recorded.** `.devcontainer/.bespunky-devcontainer.json` carries `owned: true|false`. A devcontainer the generator wrote is regenerated every sync; one it adopted is merged into, permanently — and the marker then carries an **adoption report** (`adopted.skipped`) listing the keys where the project's value genuinely *differs* from the house value. **When offering a sync on an adopted repo, read that list and tell the user what they're not getting** — it is the only surface for a divergence that otherwise grows silently. It lists divergences rather than merely-present keys, so it converges and stays short.
- An existing **`.devcontainer/post-create.sh`** is **never touched**. The house script is written beside it as `post-create.bespunky.sh`, with the one line needed to chain them printed for the user to place. A shell script's contents can't be merged meaningfully, so it isn't attempted.
- **`CLAUDE.md`** gets only the marker-delimited house pointer (seeded if the repo has no `CLAUDE.md`); the prose is preserved verbatim (§1b).
- **`.claude/settings.json`** is merged, never overwritten.
- On a project the generator **does** own (one it scaffolded, marked by `.devcontainer/.bespunky-devcontainer.json`), the devcontainer is regenerated normally — ownership is what separates the two paths.
- `.devcontainer/post-create.local.sh` is created once, never regenerated, and runs last — the seam for project-specific setup that must survive every future sync.

**Adding a layer later** is the same command with a bigger ensure set for what a sync can ensure (`--ensure=firebase`); for the rest, the error names the native command (e.g. `nx add @nx/angular`, then `nx g @bespunky/nx-tools:app --name=<name>`), after which a plain sync detects and refreshes it. The `SessionStart` hook notices the reverse case: a project that has *grown* a layer (someone ran `nx add @nx/angular`, or added `firebase.json`) whose house tooling was never applied, by comparing the workspace against the `layers=` list in `HOUSE.md`'s stamp.

### 1a. Recovery (if the script can't complete end-to-end)

If `scaffold.sh` fails partway, **do not improvise the remaining phases by hand** - the house generators encode hard requirements that are easy to miss. Use the script's **sync mode**, which probes where the project actually is, lays the Nx floor if it is missing, re-applies phase 1.3 (the install), then runs the house **migrations** from the probed version (the one-way version deltas — §1d), then re-applies phase 1.5 (the planner — per-app steps for the named app, then the workspace steps, then `house-doc`) on the existing project (the generators are idempotent; the migrations are not, and are not meant to be):

```
bash "${CLAUDE_SKILL_DIR}/assets/scaffold.sh" --sync [--firebase] [--yes] <PROJECT_PATH_OR_NAME> [<APP_NAME>]
```

**The ordinary way to run this is the `/sync` command**, which updates the claude-toolkit plugins first and
then syncs the current project — so the sync applies the CURRENT house standard rather than whatever copy
this machine happens to have. **It completes in ONE run.** A plugin update used to end the run and demand a
restart, because `${CLAUDE_PLUGIN_ROOT}` is frozen for the life of a session; the command now resolves the
just-installed root from `~/.claude/plugins/installed_plugins.json` (via `scripts/resolve-plugin-root.sh`)
and runs *that* scaffolder in the same session. That also settles which payload lands, since `scaffold.sh`
derives the `@bespunky/nx-tools` version it installs and stamps from its own directory — the frozen root
would have installed and stamped the old one, leaving the ladder for a later run to walk.

```
/sync [--ensure=<layers>] [--preset=<id>] [--firebase] [--voice]
```

Reach for the raw script above when syncing a project that is **not** the one open in this session (the
command always targets `.`), or when you need a flag it does not pass through (`--local`, `--docker`,
`--no-backup`, `--staging`).

**Sync runs right here — including inside the project's own devcontainer.** It does **not** require Docker: when the local Node is new enough (22.18+, which is *always* true inside a devcontainer) the script runs the house generators natively, no daemon and no image. So the correct place to sync a scaffolded project is from a Claude session *at that project* — the devcontainer, or any Linux/macOS shell with a modern Node. **Do not tell the user to "run it on the host with Docker Desktop"** — that was only ever needed on the old-Node fallback path, and it is wrong for a devcontainer (which has no Docker). Only when the local Node is too old does it fall back to `docker run` (then it needs a Docker CLI + daemon; `--docker` forces that path).

**Sync REFUSES to run unattended — the `--yes` gate.** A sync rewrites generated files and takes minutes, so it must never happen because something *inferred* that it should. On a TTY the script prompts a human. With no TTY (your shell), it **aborts** unless `--yes` is passed — and `--yes` *asserts that the user has explicitly agreed in this conversation*. Pass it only when that is true: never to satisfy the gate, never on inferred consent. In CI it refuses outright — no flag can conjure a human. This is what makes "detection is automatic, execution is consented" (§1c) structural rather than a matter of your good behavior.

(On a Windows host, invoke per *Where the script runs* in step 1.) `--firebase` and `--sync` may be combined to retrofit Firebase support onto an existing project. A project whose dependencies were never installed (a fresh clone) needs no intervention: the sync installs them itself and carries on, rather than bailing out to make you type the command it is about to run anyway.

**Sync auto-backs up to git first.** Because sync runs **migrations** (one-way rewrites, across every project in the workspace — e.g. 0.24.2, which carries a legacy `productionFirebaseConfig` out of `firebase.config.ts` into `environment.prod.ts`) and then re-runs the generators, which rewrite the files they own — `--sync` starts from a restore point it never has to build: **preflight refuses a dirty tree**, so every sync that runs at all starts clean, and the clean `HEAD` *is* the pre-sync state. No tag is written; the run prints `BACKUP_OK` with that `HEAD` sha after preflight passes, and the final `SYNC_OK` line reports it as `backup=HEAD(<sha>)`. **To recover after a sync:** review what changed with `git -C <project> diff <sha>`, restore a clobbered file with `git -C <project> checkout <sha> -- <path>`, or undo the whole run with `git -C <project> restore --source=<sha> --staged --worktree -- .` followed by `git -C <project> clean -n` (it lists what the run ADDED — review before `-f`). **Never `git reset --hard`**: it moves the branch and discards the working tree wholesale. If the project isn't a git repo, sync **aborts** rather than change files unprotected — `git init && git add -A && git commit` first, or pass **`--no-backup`**, whose only meaning now is "sync a non-git directory with no restore point at all".

**One sync, one boundary — the run tells you which, on the `SYNC_NEXT:` line.** Some of what a sync writes takes effect only when a *session* starts (`.claude/settings.json`, `.mcp.json`, the hooks of plugins it just enabled) and some only when a *container* is created (`.devcontainer/*` — mounts, `runArgs`, `containerEnv`, features). Neither can apply mid-session; that is the one irreducible cost of a sync. What is avoidable is paying it more than once, so the run computes what it actually changed and names exactly one:

| `SYNC_NEXT:` | Meaning |
| --- | --- |
| `none` | Nothing this run wrote needs a new session or container. Say so — silence gets read as "restart to be safe". |
| `restart-session` | Session-scoped config moved. Restart Claude Code; **no rebuild**. |
| `rebuild-container` | `.devcontainer/*` moved. **Dev Containers: Rebuild Container** — which *subsumes* the restart (a rebuild is a new session, and its post-create reinstalls the plugins), so never ask for both. |
| `unknown` | No git base to compare against; say so rather than guess. |

Until a needed rebuild happens the tooling degrades rather than fails — the shared browser's cross-container port registry isn't mounted, and its `up` warns that parallel containers are invisible to each other.

**Tell the user, don't do it.** Never rebuild a container or restart a session on your own initiative — same detect-don't-execute rule as the `SessionStart` version hook. Both throw away the session they are working in, and only they know what that costs right now.

**`SYNC_RELOAD:` is NOT a boundary.** It names the generated guidance files that changed (`HOUSE.rules.md`, `HOUSE.md`, `CLAUDE.md`). They are `@`-imported at session start, so the *old* text is what is in context — but simply **reading** them puts the new content in context immediately. Read every file it names before reporting; no restart is involved.

### 1b. `--sync` touches ONLY `CLAUDE.md`'s generated pointer — the rest is preserved verbatim

**`scaffold.sh --sync` preserves everything the user owns in `CLAUDE.md` (intentions + conventions) verbatim.** The one thing it manages there is the marker-delimited **house pointer** — the `house-doc` generator upserts it between `<!-- @bespunky/house-tooling:start … -->` / `<!-- … :end -->` (inserted if absent, restored/regenerated if present); it never rewrites your prose. **If `CLAUDE.md` doesn't exist at all, it is seeded** — a minimal file whose only purpose is to host the pointer, because `--sync --ensure=agent` retrofits onto repos of any shape and one without a `CLAUDE.md` would otherwise get house docs that nothing references. The volatile **house guidance** lives in two generated files, which `--sync` regenerates in full every run.

**Two files, split by how they REACH the model — the distinction to keep straight:**

| File | How it reaches the session | What belongs in it |
|---|---|---|
| **`HOUSE.rules.md`** | **`@`-IMPORTED** by `CLAUDE.md`'s pointer block → in context **every session** | The **directives** — the rules that must hold on every change (architect mentality, architecture-first, redesign-means-rethink, design-system-first, the branch & release rules, a feature is a package, generator-first, local-server isolation). Layer-gated, so a project only carries rules that can apply to it. |
| **`HOUSE.md`** | **LINKED** → read **on demand** | The **mechanical how-to** — stack, the design system, serving, worktrees, Firebase, Nx, Playwright, and this project's branch/deploy parameters. Also carries the **version stamp** the `SessionStart` hook reads. |

**Putting a rule in the wrong file is not cosmetic — a directive in `HOUSE.md` is a directive nothing loads.** Claude Code loads `CLAUDE.md` and follows its `@` imports; it does not load a file merely because `CLAUDE.md` mentions one. Between 0.5.0 and 0.25.0 every "non-negotiable" sat one un-taken hop outside the context it governed. When adding house guidance, ask which half it is: *must this hold before anyone thinks to look something up?* → rules. *Is this how you do a thing once you've decided to do it?* → how-to. The generators run by `--sync` — whichever the active layers' plans name (§1, step 1.5) — touch `project.json`, `HOUSE.md`, the `CLAUDE.md` pointer, `.devcontainer/*`, `.claude/settings.json`, `.mcp.json`, `package.json`, the app's global stylesheet, and the Firebase config files.

**One exception to "generators rewrite":** the design system's `styles/` and `src/` are **seeded, not owned** — each file is written only if *absent*. This is deliberate and load-bearing: `styles/_core/_tokens.scss` is precisely the file the design phase **replaces** with the project's real visual system, and a `--sync` that rewrote it would silently restore the placeholder palette over a shipped design. What `--sync` *does* re-assert on the design system is its config (`ng-package.json`, `package.json` exports, the `type:design-system` tag), its `STRUCTURE.md`, and every app's wiring.

Everything a toolkit upgrade can change is now **syncable** — no hand-merge:

| What | How it gets to a project | Retrofitted by `--sync`? |
|---|---|---|
| Generator outputs (configs, mounts, scripts, deps) | Generators (idempotent rewrites) | **Yes** — `--sync` re-runs them. |
| House guidance (architecture directives, branch/release workflow, serving, Firebase, Nx, browser tooling) | The **`house-doc`** generator → **`HOUSE.rules.md`** (imported) + **`HOUSE.md`** (linked) | **Yes** — `HOUSE.md` is generator-owned and fully rewritten every `--sync`. |
| Project-specific `CLAUDE.md` (intentions + conventions) | Step 2 of THIS skill | n/a — it's the user's; the volatile house content no longer lives there. |

The old asymmetry (house guidance stuck inline in the hand-owned `CLAUDE.md`, unreachable by `--sync`) is **gone**: `house-doc` moved it to `HOUSE.rules.md` + `HOUSE.md` (regenerated every sync) and left a bounded pointer in `CLAUDE.md`. So a toolkit upgrade reaches an existing project entirely through `--sync` — **never hand-merge house sections into `CLAUDE.md` again.**

**The pre-split duplication is handled by a migration now — nothing to do by hand.** A project scaffolded before 0.5.0 kept a frozen copy of the house sections inline in its `CLAUDE.md` (the split wrote the new state and never removed the old one), and this skill used to ask for a one-time manual cleanup. The **`retire-inline-house-sections`** migration at 0.25.0 does it: it removes a section only when the heading is one of ours **and** the body still carries a phrase from the text we shipped, so a project's own `## Stack` or `## Firebase` survives — and anything that matches by name but not by content is left in place and **reported**, because a rewritten section is indistinguishable from one the project wrote itself.

### 1c. Sync announces itself when the toolkit moves (the SessionStart hook)

`--sync` made an upgrade *reachable*, but nothing made it **noticed**: Claude Code has **no plugin-install/update hook event**, so `/plugin marketplace update` upgrades the plugin silently and a project just quietly drifts a version behind. The plugin closes that gap itself:

- **The stamp** — `house-doc` renders it into **`HOUSE.md`'s header**: `<!-- @bespunky/house-tooling:stamp nx-tools=<v> plugin=<v> -->`. It lives there, and *not* in a file of its own under `.claude/`, because the hook's whole premise is that the stamp reaches every clone — so it must be **committed**. `.claude/` is the conventional home for *local* Claude state (this project's own generators gitignore `.claude/data/` and `.claude/skills/`), where one entirely reasonable `.gitignore` line would silently delete the stamp from every other checkout and leave the hook nagging forever with no way to fix it. `HOUSE.md` is root-level, unambiguously committed, generator-owned, rewritten on every sync — and already the file the hook stats as its guard.
- **The hook** — `plugins/project-starter/hooks/hooks.json` registers a **`SessionStart`** (`startup` only — a `resume` is by definition mid-task, the worst moment to raise an unrelated multi-minute chore) command hook, `hooks/check-house-version.sh`. Plugin hooks run in the sessions of everyone who has the plugin **installed** — i.e. in the scaffolded project, which is exactly where a sync belongs.
- **It compares `@bespunky/nx-tools`, and *only* that** — the package the generators come from, so the only thing that can change what a sync *produces*. Deliberately **not** the plugin version: the house convention bumps a plugin on **any** change (a SKILL.md typo, a README line), and demanding a several-minute sync for a change that regenerates nothing would train everyone to ignore the notice.
- **Direction matters — it ORDERS the versions, it doesn't just compare them.** The stamp is a *repo* fact (committed, travels with every clone); the installed plugin is a *machine* fact. So "the project is ahead of this machine" is an ordinary state — a teammate who hasn't run `/plugin marketplace update`, a second machine, a CI checkout — **not** an error. Reporting that as "you're behind, run `--sync`" would be a lie, and the sync would regenerate the project's house files with **older** generators, stamping it backwards and re-arming the notice for the teammate who *was* up to date. So each direction gets its own true sentence, and the older-plugin case explicitly says **do not sync — update the plugin.**
- **It DETECTS; it never RUNS.** On a match (the overwhelmingly common case) it exits silently — a few small file reads. On a real drift it prints a **statement of fact** to stdout, which lands in Claude's context, for Claude to **relay**. It is deliberately not phrased as an order: a hook that commands the model to act is one compliant model away from doing the very thing we refused to automate — and in a headless run (`claude -p`, CI) there is no one to consent at all. **Detection is automatic; execution stays consented.**
- **A decline is remembered.** If the user says no, Claude writes `.claude/house-snooze.json` (`{"declinedNxToolsVersion": "<v>"}`) and the hook stays silent for that version. It's **gitignored** (house-doc writes the rule) — one person's "not now" must never silence the notice for their teammates. A *newer* version un-snoozes itself; that's a different question.
- **Silent everywhere else.** No `HOUSE.md` → not a house project → exit 0 without a word (which is also why developing the toolkit never trips its own hook). Values read from the stamp are validated against a strict version charset (no whitespace, ≤32 chars) before they are ever echoed — a real but *partial* mitigation: it rules out prose and multi-line payloads, not a short underscore-joined imperative, so the notice's framing (every echoed value is reported *as a version*, never as something to act on) is what carries the rest of the weight.

**When you see that notice in your context:** relay it briefly at the start of your reply, offer the sync, and run it **only** after an explicit yes. If nobody answers (a scripted run), do nothing. If they decline, write the snooze file.

| What | How it gets to a project | Retrofitted by `--sync`? |
|---|---|---|
| Knowing a sync is **due** | The `SessionStart` hook, ordering `HOUSE.md`'s stamp against the installed `@bespunky/nx-tools` | **Yes** — and it's the sync that *writes* the stamp, so one sync makes the project self-announcing from then on. |

### 1d. Migrations — how a ONE-WAY change reaches an existing project

A sync used to be pure **convergence**: every generator re-ran and re-asserted the desired state. That works for a file the toolkit owns end-to-end, and not at all for a *change of shape* — a renamed target, a project moved from the app to the workspace, a retired build configuration. Convergence handled those by making each generator recognise every shape the toolkit had ever produced, forever. Every generator grew a museum of legacy-healing branches, and every new shape added one to all of them.

So one-way changes are now **versioned migrations**, run by **native `nx migrate`**:

- They live in the payload at `src/migrations/<version>/<name>.ts`, are registered in `migrations.json`, and are exposed to Nx through the `nx-migrations` key of `@bespunky/nx-tools`'s `package.json`. `nx migrate` **collects and orders** them itself — from the version the project has, up to the version being installed — so a project three versions behind walks the ladder in order, once. The generators shed their healing code in exchange.
- **The sync PROBES before it writes anything, and migrates AFTER the install with an explicit `--from`.** The order is: **probe → ensure the Nx workspace → install `@bespunky/nx-tools` → migrate → detect layers → run the generators → `house-doc` last** (it writes the stamp, so it must see the final layer set).
  - **The probe** runs while nothing has been touched and `node_modules` still holds what the project *had*, and answers one question — *where is this project actually at?* — from **two** sources: the version resolved in `node_modules`, and the `nx-tools=` version stamped in `HOUSE.md`. It migrates from the **older** of the two. That is not belt-and-braces: every project scaffolded before this release declares the old **caret** range, so an ordinary `yarn install` has already floated `node_modules` to the newest published version with **not one migration having run**. Take `node_modules` at its word and the sync concludes "already current", collects nothing, and then `house-doc` stamps the project as current — closing the gap over **permanently**, because the stamp is what every later sync believes. The stamp records the last version whose migrations actually ran, so the older of the two is the only honest floor.
  - **It refuses a downgrade with the same two numbers, reading the NEWER of them.** If either source says this project has been on house tooling above the version this checkout installs, the sync **aborts before the install** — the last moment nothing has been written. Running older generators over a newer shape and re-stamping `HOUSE.md` backwards would record a state nothing ever migrated down to, and migrations do not walk backwards, so there is no repair path. (Taking the older figure for *both* questions would look tidy and quietly disable this guard.)
  - **The explicit `--from` is what freed the ordering.** `nx migrate` left to itself infers the range from whatever is resolved in `node_modules` — which is exactly the number the caret float corrupts. Handing it the probed version instead means the range no longer depends on `node_modules` at all, so the install can safely come first (and the migrations run against the package they will actually be applied by).
- **The dependency is pinned exactly, and that pin is load-bearing.** `@bespunky/nx-tools` is a real npm devDependency of the project (not a copy in `node_modules`), written as an exact version rather than `^`. A caret lets an ordinary install float the project to a newer published version with **no migration behind it**, so the version in `node_modules` stops meaning "what was applied here". `nx migrate` is the only thing that should ever move it. The probe above is the *backstop* for every project already carrying the old caret — it distrusts `node_modules` on purpose — but a backstop is not a substitute: the pin is what keeps the two numbers agreeing in the first place. (The `SessionStart` hook watches for the same gap from the other side — §1c.)
- **The ladder itself is `migrations.json` — read it there, not from a list in prose.** Every entry carries its version, its implementation path, and a description written to be read on its own, so the registry is both the mechanism and the documentation. This bullet used to enumerate the rungs and had silently drifted three behind the real ladder by `0.24.6` — which is the argument for not restating it anywhere. **The one rung worth knowing by name is `0.24.3/upgrade-emulator-environment-shape`**, because it is the reason to care that this ladder actually runs: it carries a pre-toggle Firebase `environment.ts` (bare emulator endpoints) and its `environment.interface.ts` onto the per-service `default` shape that the generator-owned `firebase.config.ts` reads. Skip it and `firebase.config.ts` evaluates `environment.emulators?.auth?.default ?? false` against a file that has no `default` key — so **every emulator silently resolves to OFF and the dev app talks to the REAL Firebase backend using `demo-*` credentials**. There is no compile error; there is just `auth/api-key-not-valid` at runtime and no clue why. It edits surgically (a project that moved Firestore to `:8081` keeps `:8081`) and is **all-or-nothing per `src/environments` directory**, because the values and the interface type each other — upgrading one alone would trade the silent failure for a build break.
- **What you'll see.** Exactly one `[migrate]` outcome line — read it by *meaning*, not by matching its wording (it is prose and it gets tuned):
  - **the ladder ran**, naming the two versions it walked between — **relay it**; it rewrites every project in the workspace and there is no reverse, so name the restore point (`BACKUP_OK`'s pre-sync `HEAD` sha) alongside it;
  - **the baseline line**, saying the toolkit was not installed here before this run — a first retrofit, with no applied version to migrate *from*;
  - **the steady-state line**, saying the project is already at the version being installed, so there is nothing to run.

  When the two probe sources disagree, an extra `[migrate]` line reports both (the installed version and the `HOUSE.md` stamp) and says which one it is migrating from — that is the caret-float case above, and it is worth relaying because it is the one that proves the ladder was *not* silently skipped. **If a migration fails mid-ladder, stop** — the version bump and install have already happened, Nx leaves a `migrations.json` in the workspace root, and re-running restarts the ladder against a half-migrated tree. Surface the failure and the restore point (the pre-sync `HEAD` sha, restored with `git restore --source=<sha> --staged --worktree -- .`, never `reset --hard`); let the human choose.

**Three classes of generator output — and knowing which one a file is tells you what a sync will do to it:**

| Class | Examples | What a sync does |
| --- | --- | --- |
| **A. Owned template artifacts** | `tools/shared-browser/*`, `tools/worktree-domains/*`, `HOUSE.rules.md`, `HOUSE.md`, `.devcontainer/post-create.sh`, a devcontainer the generator **owns** | **Regenerated every sync.** The generator states desired state; local edits to these are lost by design (that's what `post-create.local.sh` and adoption are for). |
| **B. Project state** | `project.json` targets, `package.json` deps, `firebase.json`, the environment files | **Created at baseline, then evolved ONLY by migrations.** A generator writes it when it's absent; changing its *shape* afterwards is a migration's job, never a re-run's. |
| **C. Seeded, never owned** | design tokens (`styles/_core/_tokens.scss`), `environment.ts`, the `ds-theme` output, `.devcontainer/post-create.local.sh` | **Written once, never again.** These are precisely the files a project is expected to replace — a sync that rewrote them would restore placeholder tokens over a shipped design. |

**Toolkit development:** `--local` packs the working tree (`npm pack`) and installs *that* instead of the published package, so a generator or migration can be exercised against a real project before it reaches npm. Two rules govern **authoring** the ladder, and they are stated in full in the toolkit repo's own `CLAUDE.md` (§*Release & versioning*) — the short form: **(1) no payload release ships without the migrations it owes** — before bumping the version, ask of every change *does this alter a shape existing projects already have?*, and treat "nothing to migrate" as a finding you state, never a default you fall into, because a skipped migration fails silently and is then sealed behind a stamp every later sync believes; **(2) a migration cleans up after itself** — it is done only when the old shape is *gone*: deletions made, every reference to a moved path retargeted (including the ones the toolkit never wrote), carried data cleared from its old home, and anything deliberately left un-deleted **reported by name with its reason**, since an unexplained leftover is indistinguishable from an oversight.

## 2. Author a tailored CLAUDE.md

**Step 1 has already written `<project>/CLAUDE.md`** — the `house-doc` generator seeds it and upserts the generated pointer block, which `@`-imports **`HOUSE.rules.md`** (the always-on directives) and links **`HOUSE.md`** (the mechanical how-to). Both are generator-owned; you author **neither**.

- Where the seed carries a component/directive **prefix** prompt (Angular projects), set it to something derived from the project name.
- Replace each remaining `<!-- … -->` prompt with real content, and delete any prompt or bullet that doesn't apply.

If the block is missing, the fix is to re-run `house-doc`, not to type it.

## 3b. Declare the branch model — ASK, then land it through the skill

**A new project has no branch model, and the scaffold does not pick one.** It creates exactly one branch — `main`, holding the scaffold commit (pushed to `origin` unless `--no-github`) — and no `development` or `staging`: which lines a project has is a decision about how it ships, not a house default. Until it is declared in `.bespunky/branches.json`, the house rules render the *undeclared* state (every branch named `main`, `master`, `development`, `develop` or `staging` protected; investigate and ask before any branch or promotion action), and every `/sync` signals it.

So, once step 3 passes, **invoke `bespunky-workflow:branch-and-release` and ask the user which model** this project follows. There is no history to investigate yet, so offer the presets by what they mean for this project (its intentions from step 0, whether it deploys, where):

- **`trunk`** — `main` only; work lands on it, releases are tags. The default for a library, a tool, docs, a solo project.
- **`two-line`** — `development` → `main`: an integration line ahead of production.
- **`three-line`** — `development` → `staging` → `main`: a pre-production stage with its own deploy (the shape `--staging` builds a bundle for).
- **`gitflow`** — `develop`, release branches cut and shipped to `main`, hotfixes.
- **`maintained-releases`** — `main` plus long-lived `release/{version}` lines maintained in parallel.

**If `--staging` was passed**, say that the staging bundle deploys from a pre-production stage, so only a model that has one (`three-line`, or a custom chain) gives it a line to bind to — a later `/sync --staging` refuses on a model without one.

Then follow **the skill's change procedure** to write and land the choice: expand the preset, show the user the declaration, write it with its engine (never by hand — the `projection` block in it is derived), and then, **in this order**: if the chosen **integration line** is not `main`, create it from `main` first (pushing it when the project has a remote); land the declaration on it; only then create the model's other lines from `main` (pushing them likewise). The skill owns every one of those commands; this skill names none of them. **Never write the declaration without the user's answer** — if they want to decide later, leave it undeclared and say so in the report; the next `/sync` will raise it again.

After it lands, the house docs still carry the *undeclared* wording until the next `--sync` re-renders them with the real line names — run it from a worktree off the integration line (the skill's procedure), or tell the user it is due.

### Recipe: add another app to the workspace

The scaffolder configures the **first** app (when a layer created one), but a workspace can hold many. To add another, **always go through the house `app` generator — never the raw framework generator such as `@nx/angular:application`** (which produces an unconfigured app: no `serve` `host: 0.0.0.0`, and in a Firebase workspace none of the per-app Firebase wiring — environment files, `firebase.config.ts`, `app.config` wiring, the production `fileReplacements`, the `platform:web` tag, or the serve orchestrator):

```
yarn nx g @bespunky/nx-tools:app --name=<new-app-name> [--stack=<adapter>]    # -> <appsDir>/<new-app-name>
```

This is the **exact command step 1.4 runs for the first app**, so the new app is configured identically — no drift. The generator **creates** the app through the stack's adapter (`--stack`, defaulting to the workspace's own app-creating stack — `angular` today, with the house defaults), then **attaches every capability the workspace wears** by running each active layer's per-app steps (`serve` + `serve-options` for `web`, `design-system-styles` for `design-system`, `firebase-client` for `firebase`, …). It **auto-detects Firebase** from `firebase.json` at the workspace root (resolving the emulators' `demo-<workspaceName>` identity from the workspace root, not the new app's name), so a second app in a Firebase workspace is wired end-to-end with **no flag**. Override with `--firebase=false` to opt one app out, or `--firebase=true` to force wiring where `firebase.json` isn't present yet.

Run it from inside the devcontainer (where the workspace's `node_modules` holds the generators). `@bespunky/nx-tools` is published on npm and installed as an exactly-pinned devDependency of the project, so every house generator is directly runnable there — no staging step. If it's missing (a project that predates the real install), `scaffold.sh --sync` installs it.

### Recipe: work with the design system

Every project wearing the `design-system` layer has one (the `angular` preset from moment zero), found by its `type:design-system` tag — at `<libsDir>/design-system` (usually `packages/design-system`; `HOUSE.md` names the real path). It ships the **mechanism** — tokens as CSS custom properties, a zero-output SASS API, a theme — and **zero components**. The library's own `STRUCTURE.md` is its conventions doc; `HOUSE.rules.md` carries the always-on rule. Three things to know:

**Consuming it.** One `@use` per SCSS file, in an app component or a design-system component alike — always the **public** barrel, never the private `styles/_core/` or `styles/_utils/`:

```scss
@use 'design-system/styles' as ds;

:host { gap: ds.space(3); color: ds.color('on-surface'); border-radius: ds.radius('md'); }
```

An unknown token is a **compile error**, not an empty `var()` — a typo can't ship. `@include ds.theme()` is emitted once, in the app's global stylesheet (the generator put it there); never call it again.

**Promoting a component into it** — on the **second** occurrence of a UI pattern, never the first, and never by hand. With the **Angular** binding (the `angular` layer worn too) that is the adapter's generator; a design system on the neutral core has no component generator, and gets the export by its stack's own means:

```
yarn nx g @bespunky/nx-tools:ds-component <name>
```

That creates `<design-system root>/<name>/` as its **own secondary entry point** (importable as `@<scope>/design-system/<name>`, independently tree-shakeable), with its SCSS already wired to the token layer. Then migrate **both** call sites onto it and delete the copies — a promotion that leaves the original behind is just a third copy. Hand-creating the folder gets you a component that resolves in the editor and **vanishes on publish**, because the entry-point config *is* the boundary.

**The tokens that ship are placeholders.** They exist so the library compiles and the app runs on day zero, and they carry **no design authority**. The real visual system comes from the design phase (`bespunky-product-ux:stage-the-vision` → `realize-the-vision`), which replaces `styles/_core/_tokens.scss` wholesale. Don't build a look on top of the placeholders, and don't tweak them into one.

For the discipline, invoke **`bespunky-design-system:design-system-first`**; for the techniques, **`bespunky-design-system:design-tokens-and-theming`**.

### Recipe: add the design system to an existing project

`design-system` is a layer a sync **refreshes** but does not **create** (a project wears it on purpose), so bring it into being with its own generator — never by hand — and let every later sync keep it current:

```
nx g @bespunky/nx-tools:design-system --scope=<PROJECT>        # ./nx g … on the wrapper host
```

The generator creates the library and wires **every** app whose adapter has a styles port through the per-app `design-system-styles` step (on Angular:  the sass load path, the implicit dependency, the stylesheet blocks, `provideDesignSystem()`); with no app it lays down the stack-neutral core alone. From then on the `type:design-system` tag is the layer's evidence, so a plain `--sync` detects and refreshes it. It is safe to re-run: the sass and TS files are *seeded*, so a sync on a project that has since replaced the placeholder tokens with its real design **leaves that design alone**.

The retrofit gets you the mechanism. It does **not** retroactively de-hardcode the values already scattered through the project's components — that's a migration, and it's the one place the discipline has to be applied by hand: sweep the existing SCSS, lift each literal into a token, and delete it from the component.

### Recipe: add Firebase to an existing project

If a project was scaffolded **without** `--firebase` and you now need it, use sync mode + the flag — **never hand-create the artifacts**, always go through the generator (this is the BeSpunky way: *generator-first, manual last*):

```
bash "${CLAUDE_SKILL_DIR}/assets/scaffold.sh" --sync --firebase <PROJECT_PATH_OR_NAME> [<APP_NAME>]
```

(On a Windows host, invoke per *Where the script runs* in step 1.) This first runs the house **migrations** (§1d) — for a project that already had Firebase, the three that matter are **0.24.1**, which relocates the per-app `emulators*` targets to the workspace-level `firebase` project and drops the retired no-emulators build configuration and environment file; **0.24.2**, which rescues a legacy `productionFirebaseConfig` out of `firebase.config.ts` into `environment.prod.ts` before the generator rewrites that file; and **0.24.3**, which upgrades a pre-toggle `environment.ts` (bare emulator endpoints) and its `environment.interface.ts` to the per-service `default` shape. That last one is the one to watch: the generator-owned `firebase.config.ts` gates each service on `environment.emulators?.<svc>?.default ?? false`, so against an un-upgraded file every read falls through to `false` and the dev app talks to the **real** Firebase backend while still holding `demo-*` credentials — a runtime failure with no compile error to warn you (you just get `auth/api-key-not-valid`). It edits surgically, so a project that moved Firestore to `:8081` keeps `:8081`, and it is all-or-nothing per `src/environments` directory, because the values and the interface type each other — upgrading one without the other would trade a silent failure for a build break. Then it re-runs the house generators idempotently; the `firebase-emulators` generator writes `firebase.json` (does **not** write `.firebaserc` — see below), generates the env files `<appsDir>/<APP>/src/environments/{environment.interface.ts, environment.ts, environment.prod.ts}` (the latter two only if absent — your customizations and real production web config are preserved), writes `<appsDir>/<APP>/src/app/firebase.config.ts` (written when absent; rewritten when it detects an outdated shape — and where that shape is the legacy `ngDevMode`-and-two-consts one, migration **0.24.2** has already carried any populated `productionFirebaseConfig` values into `environment.prod.ts`, which is what makes the rewrite safe. Once `firebase.config.ts` is on the current shape (per-service gating + the `ngDevMode` prod-DCE guard, importing `./emulator-overrides`), the generator leaves it alone — your custom providers, `messagingSenderId`, `initializeFirestore` options, etc. are preserved across `--sync`), registers the `environment.ts` → `environment.prod.ts` `fileReplacements` on the production build configuration, best-effort-wires `app.config.ts`, scaffolds `<appsDir>/functions` + `firebase/project.json` + the emulator tooling under `tools/` (seeds, cache, reset, verified reaping), inserts the platform-firewall ESLint constraints, asserts the `.gitignore` entries, and updates `package.json` (the post-commit `installPackagesTask` runs install). The `devcontainer` generator simultaneously adds the Firebase CLI + Google Cloud CLI features, the `toba.vsfire` extension, labeled `portsAttributes`, and same-port `forwardPorts` for the dev server + emulator suite. **Rebuild the devcontainer** afterwards (VS Code → *Dev Containers: Rebuild Container*) to materialize the new features.

After the retrofit, run step 3 (Verify) against the project — every check that mentions "if `--firebase` was used" must pass. If `app.config.ts` couldn't be auto-wired, the generator logged a warning; add `provideAppFirebase()` to its providers array by hand. For a project that existed before 0.33.0 **and had `provideAppFirebase()` wired**, migration **`0.33.0/split-firebase-service-providers`** has already added `provideAppAuth()`, `provideAppFirestore()`, `provideAppStorage()` and `provideAppFunctions()` beside that call — preserving the old behaviour exactly. Deleting the ones the app doesn't use, and moving the rest into lazy routes, is the project's own follow-up. Where it found no call site it says so and adds nothing; that is the expected outcome for any app scaffolded between nx-tools 0.26.0 and 0.32.x, which never had the provider wired at all — migration **`0.33.1/wire-missing-baseline-providers`** is what repairs those.

**The Firebase house guidance is regenerated into `HOUSE.md` — no hand-merge.** The per-service toggling, emulator seeds, and the connect-to-a-real-project App Hosting recipe (the `{{#firebase}}` block) are written into the project's **`HOUSE.md`** by the `house-doc` generator on this same `--sync --firebase` run; the `CLAUDE.md` pointer already links to it. (This is the whole point of the HOUSE.md split — the old "hand-merge the Firebase section into CLAUDE.md" step is retired.)

### Recipe: connect a real Firebase project (App Hosting)

The scaffolder deliberately does NOT fabricate `.firebaserc` or the production web config — the cloud state is the Firebase CLI's source of truth, and inventing values would lie about what the user's account actually has and break `firebase apphosting:*` / `firebase use` the moment they're touched. The BeSpunky default is Firebase **App Hosting** (the framework-aware product), not classic static Hosting — App Hosting build/runtime config lives in `apphosting.yaml` at the workspace root (generated by the scaffolder, ready to override as needed). When you (or the user) are ready to wire a real Firebase project, run these from the workspace root inside the devcontainer (where the Firebase CLI is installed):

```
firebase login                                                            # one-time auth against the user's Google account
firebase use --add                                                        # pick a project from their account — writes .firebaserc
firebase apphosting:backends:create --project <projectId>                 # one-time: creates the App Hosting backend (interactive — LINK THIS REPO; that linkage is the deploy CI)
firebase apps:sdkconfig WEB <appId> --project <projectId>                 # prints the real web config for client-side SDK init
```

Paste the returned `firebaseConfig` fields into the `firebase` block of **`<appsDir>/<APP>/src/environments/environment.prod.ts`** — the production environment file, which the Angular build swaps in for `environment.ts` via `project.json`'s `targets.build.configurations.production.fileReplacements`. **Never edit `apps/<APP>/src/app/firebase.config.ts` or its `firebase-<service>.config.ts` siblings** — that's structural code the generator owns end-to-end and rewrites on every `--sync --firebase`. (*Where* each service is provided is the app's call, and lives in `app.config.ts` / its lazy routes.) 

**The deploy CI is Firebase's — we generate no workflow.** When the user **links the project's GitHub repo** at `firebase apphosting:backends:create` (the repo already exists — the scaffolder created it), App Hosting provisions and maintains its own Cloud Build pipeline: **pushing to the configured branch triggers a build via Cloud Build and a Cloud Run deploy.** That is the "automatic CI with Firebase deploy" — owned and kept current by Firebase's GitHub integration, so the project never carries a `.github/workflows/*` deploy file we'd have to update as Firebase evolves. Tweak build/runtime behavior in `apphosting.yaml` at the workspace root. The local emulator setup is unaffected by any of this — emulators continue to use the `demo-<workspaceName>` offline project id passed by the Nx targets.

## Decisions (as they happened)

- **2026-10-28 — scope.** The user, from the concept session for a new consumer project (`INBOUND-HANDOFF.md`): *"I want the toolkit to support Supabase and Postgres correctly and officially"*.
- **2026-10-28 — two layers, not one.** The user asked: *"If we incorporate a new layer into our toolkit, it won't just be Postgres then. It would be a Supabase layer, isn't that so?"* The session agreed and gave the reasoning: a neutral `postgres` core, plus a `supabase` layer that `requires` it. This follows the house's capability model and the consumer's own rule that a vendor is a provider, not infrastructure.
- **2026-10-28 — the bar is the Firebase layer, without its history.** The user: *"Looking at the home layer for Firebase, do you think we can easily replicate something similar for Postgres? The home layer for Firebase took a lot of iterations to get right"*. The session's answer, recorded in `INBOUND-HANDOFF.md` § 4, was that most of Firebase's iterations came from its client-dials-emulators architecture, which a backend-held connection removes. The lessons still carry over, and so do the safety guarantees.
- **2026-10-28 — the consumer waits on this effort.** The user: *"We'll use Postgres and Supabase for this project, but we won't implement them until the toolkit lands with its layers implementation"*. So the life app is this effort's first real consumer, and its database work is blocked until these layers land on `development`.
- **2026-11-04 — research before implementing.** The user stopped the resume: *"Before you implement, I need you to research Postgres and Supabase online, then research our existing layer infrastructure, specifically Firebase and its layer."* Findings in `research/`, proposal in `research/ARCHITECTURE.md`, awaiting confirmation.
- **2026-11-04 — Supabase runs on the native runtime.** Asked whether to build the `supabase` layer on the alpha native runtime, pinned to an exact version and guarded by an automated check against the real CLI, or to use Docker, the user answered: *"Yes"*. No Docker feature, no privileged container. This settles that one question; the rest of `research/ARCHITECTURE.md` is still a proposal.
- **2026-11-04 — architecture confirmed.** Asked whether to confirm `research/ARCHITECTURE.md` (as amended by the spikes) and start on the plan and the shared dev-engine, CI and installer changes, the user answered: *"yes"*.
- **2026-11-04 — review decisions, by the orchestrator.** Blocked line stays red on existing projects (F3, option A): a `ci` key states intent to deploy, and a note is how deploys stopped silently; to be named in the release notes and put to the user at the landing gate. Stop order is launcher policy, not engine staging (E1). `github-cli` stays a stated exception (F12). Installer duplication removed at the cost of one gcloud re-download for Firebase projects.

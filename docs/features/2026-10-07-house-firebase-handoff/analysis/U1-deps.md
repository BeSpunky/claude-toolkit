# U1 — dependency pins & the Node source (A1, B5)

Analysed 2026-10-07 against nx-tools 0.49.2 (worktree `house-firebase-handoff`). Paths below are relative to
`plugins/house/engine/nx-tools/src/` unless stated. Read-only triage; the consumer repo was not available.

## A1 — `firebase: latest` + `@angular/fire: latest`

**Verdict: real toolkit gap, originates here.**

- `adapters/angular/firebase-client.ts:104` — `Object.entries({ firebase: 'latest', '@angular/fire': 'latest' })`,
  written by `addDependenciesToPackageJson` (line 108) whenever neither is declared yet.
- Two independent floating ranges for packages that have a hard version relationship (`@angular/fire` declares
  its own `dependencies.firebase`, and a peer on `@angular/core` of one major). `latest` on each resolves both
  to *their* newest, which need not be compatible: AF 20.0.1 wants `firebase ^11.8`, latest firebase is 12.x, so
  yarn v1 nests a second `firebase`/`@firebase/app` under `@angular/fire` → "No Firebase App '[DEFAULT]'".
- A second, unaddressed facet: `@angular/fire: latest` also ignores the workspace's **Angular major**. Nx pins
  Angular; AngularFire's major tracks Angular's. Next time AF ships a major ahead of Nx's Angular, `latest`
  produces a peer conflict on a fresh scaffold. The proposal (derive firebase from AF) does not cover this.
- Notable: every generated client file imports **only** `@angular/fire/*` (`firebase.config.ts.tpl:88`,
  `firebase-auth/firestore/storage/functions.config.ts.tpl`). Nothing the toolkit writes imports `firebase`
  directly — the direct `firebase` declaration exists only for user code.

### The class (sweep of floating specs the payload writes)

| Site | Spec | Hazard |
| --- | --- | --- |
| `adapters/angular/firebase-client.ts:104` | `firebase`, `@angular/fire` → `latest` | **the reported crash** |
| `generators/navigation-core/generator.ts:69` | `@bespunky/typescript-utils` → `latest` | same class; our own package floats in every consumer |
| `generators/adopt-extracted/generator.ts:122` + `schema.json:21` | `options.version ?? 'latest'` | same class; default floats |
| `generators/firebase-emulators/generator.ts:295` | `@nx/esbuild` → root `nx` spec, else `latest` | fallback only (firebase requires `node`, so `nx` is normally declared) but `latest` here could drift @nx/esbuild off the Nx version — should refuse/derive, never float |
| `generators/firebase-emulators/generator.ts:298` + `functions-package.json.tpl:9-10` | `firebase-admin ^13.6.0`, `firebase-functions ^7.0.0` | not `latest`, but **two sources** of the same pin (the template even says "keep aligned") |
| `generators/firebase-emulators/generator.ts:340-342` | esbuild/typescript/@types/node fallbacks | fine: derived from `@nx/js` versions, fallback documented |
| `layers/firebase.ts:84` | features `firebase-cli`, `gcloud-cli` with `{}` options | unpinned devcontainer features (B5) |
| `layers/agent.ts:74` | feature `github-cli` with no version | unpinned (lower stakes: a dev tool, not a build input) |
| `engine/house.sh:1858,1883` (`npx nx@latest init`), `house.sh:388-399` (`create-nx-workspace` empty tag = latest) | bootstrap only | one-shot; `nx init` writes an exact version afterwards. Acceptable, but the floor Nx is then whatever is newest that day, not a version the payload was tested against — worth a deliberate decision |

Precedent already in the codebase: `migrations/0.35.0/pin-playwright.ts` fixed exactly this class for
`@playwright/test`, with `generators/_utils/playwright.ts:6` (`PLAYWRIGHT_VERSION`) as the single source and
`tools/playwright-deps/project.mjs` projecting/verifying derived data against the npm registry. The firebase fix
should reuse that pattern, not invent a new one. The pin-playwright fix was the instance; the class was never
swept — this report is that sweep.

### Correct fix (architecture)

1. **A rule, not a patch: the payload never writes a floating spec.** Every `addDependenciesToPackageJson` call
   takes its versions from one module (e.g. `generators/_utils/versions.ts` — or extend the `_utils/playwright.ts`
   idea into a versions table). Enforce with a test in `tools/test-generators` (or a grep-style check like
   `check-script-modes`) that fails on `'latest'`/`'*'`/`'next'` in generator dependency writes.
2. **AngularFire compatibility as derived data.** A table keyed by Angular major →
   `{ '@angular/fire': '^20.0.1', firebase: <AF's own dependencies.firebase range> }`, generated by a
   `tools/angularfire-compat/project.mjs` (`npm view @angular/fire@<major> dependencies.firebase peerDependencies`)
   with `--write` and a drift check — the playwright-deps shape. The adapter reads the workspace's
   `@angular/core` major (declared or resolved) and picks the row; unknown major → refuse with a clear message
   rather than guess.
   - Alternative worth weighing: do **not** declare `firebase` at all (generated code never imports it; AF brings
     exactly one copy). Rejected as the default because yarn v1/npm hoisting is incidental and pnpm-strict users
     who import `firebase/*` need it declared — but if declared, it must be AF's range verbatim.
3. **Single source for the functions runtime deps** — `firebase-admin`/`firebase-functions` from the same versions
   module, rendered into `functions-package.json.tpl` instead of typed twice.
4. **Duplicate guard (`>1 @firebase/app`).** Agree in principle; place it as a **read-only detect** in the firebase
   layer's upgrade/serve path (walk `node_modules/**/@firebase/app/package.json`, warn with versions and the
   `resolutions`/re-pin fix). Not a hard failure in generators (Tree-only, may run before install). A cheap
   enforcement point is `tools/dev` preflight before `serve` — the crash is a runtime one, so warn where the
   runtime starts.

### Migration: **yes**

`migrations/<next>/pin-firebase-client.ts`, modelled on `pin-playwright`:
- Touch only the literal `latest` (and `*`/`next`) for `firebase` / `@angular/fire`; leave any concrete spec.
- Pin `@angular/fire` to the installed version (node_modules) when present, else the table row for the
  workspace's Angular major.
- Pin `firebase` to **`@angular/fire`'s own `dependencies.firebase`** read from the installed
  `node_modules/@angular/fire/package.json` — *not* to installed `firebase` (in the bug state the installed root
  firebase is the wrong 12.x; pin-playwright's "pin what's installed" rule would freeze the bug). Frozen fallback
  table inside the migration (never import the live constant).
- Report (not fix) a detected duplicate `@firebase/app`, and say a reinstall is needed.
- Also sweep in the same release: `@bespunky/typescript-utils: latest` (navigation-core) → installed version;
  adopt-extracted's package if declared `latest`.
- Fixture case in `tools/test-migrations/cases/` including the bug state (AF 20 + firebase 12 installed).

## B5 — firebase CLI unpinned; Node stated in three places

**Verdict: real; partly toolkit (CI is not generated by the toolkit).**

- `layers/firebase.ts:84` — `{ id: 'ghcr.io/devcontainers-extra/features/firebase-cli' }`, no `version` option →
  the CLI that runs emulators/deploys is whatever is newest at image build. `firebase-tools` is never declared
  as a devDependency anywhere in the payload.
- Node, the three sources the consumer saw, and where each comes from:
  - **Devcontainer image** — `layers/node.ts:33` `typescript-node:{{nodeMajor}}` / `layers/agent.ts:54` node feature.
    `nodeMajor` comes from `engine/house.sh:1008`: **`process.versions.node` of the machine running the upgrade**
    (`generators/devcontainer/generator.ts:124` uses the same fallback; `layers/cli.ts:54` defaults `'22'`).
    So the container's Node changes depending on *who ran the last upgrade on which machine* — an upgrade run
    inside a Node-24 container re-stamps 24. That violates the repo's own rule "a stamp is a repo fact, an install
    is a machine fact" and is the actual root of "image 24 vs engines 22".
  - **Functions engines** — `generators/firebase-emulators/functions-package.json.tpl:5-6` hardcodes `"node": "22"`;
    `generator.ts:342` falls back to `@types/node ^22`.
  - **CI** — not toolkit-generated (the consumer hand-wrote deploy-backend.yml). Becomes toolkit-owned if B3's
    ci-deploy generator lands.
  - No `.nvmrc`, no root `engines`.

### Correct fix

- **Node: one declared project fact.** Seed it once (class C/B — project state, not owned template): root
  `.nvmrc` (or `package.json` `engines.node`; `.nvmrc` works on the wrapper host which has no package.json, and
  `actions/setup-node` reads it via `node-version-file`). Every reader derives from it: the devcontainer
  composer's `nodeMajor` (replacing `house.sh:1008`'s host probe), the functions manifest's `engines.node`,
  `@types/node`, and any generated CI. Seed value at `new` = the house default (a payload constant), not the host.
  Functions must clamp to a runtime Cloud Functions supports; if the declared major is unsupported, warn rather
  than silently diverge.
- **firebase-tools: a pinned devDependency is the source** (firebase requires `node`, so a package.json always
  exists). Nx `run-commands` (`firebase:emulators`, `functions:deploy` at `generator.ts:433`) already put
  `node_modules/.bin` on PATH, so the targets use the pinned CLI with no further change. Then **drop the
  devcontainer feature** rather than pin it to a second copy of the version — two CLIs on PATH is the exact
  shadowing bug this repo already lived through with `claude-code` (agent.ts comments). Interactive
  `firebase login` / `firebase use --add` in docs/banners (`firebase-welcome.sh.tpl:57-58`,
  `firebase.config.ts.tpl:171-198`, `HOUSE.md.tpl:247`, `inline-house-sections.ts:122`) must then render as
  `{{PM}} firebase …` (or `npx firebase`) — sweep those. Auth state lives in `~/.config/configstore` (persisted
  volume) — nothing to re-persist, but verify by running it.
- `gcloud-cli` feature: pin its version option too (same class); it has no npm equivalent.

### Migration: **yes**

- Add `firebase-tools` devDependency (pinned; installed-CLI version if detectable, else house constant) where
  firebase layer is present and it is undeclared.
- Seed `.nvmrc` from the **existing** devcontainer's Node major (what the project currently runs; read the marker /
  `devcontainer.json`), so the next upgrade does not move it; report if functions `engines.node` disagrees
  (don't silently rewrite the functions runtime — that's a deploy-affecting change; ask/report).
- Removing the `firebase-cli` feature from `devcontainer.json`: owned → regenerated anyway; adopted → remove only
  if `houseWrote()` says the house added it (the 0.43.0 claude-code precedent), and strip its
  `devcontainer-lock.json` pin (the 0.44.0 lesson).
- Fixtures in `tools/test-migrations`; extend `tools/test-layers` persistence case; dogfood a rebuild
  (`which -a firebase`) before release since this reaches the container.

## Extra ideas / pushback

- The host-Node `nodeMajor` (house.sh:1008) is a bigger finding than B5 as reported — it makes the generated image
  non-deterministic across machines, for every house project, not just Firebase ones.
- `@angular/fire` must be keyed on the Angular major too; deriving only `firebase` from AF leaves AF itself floating.
- Make "no floating specs in generated manifests" a machine-checked invariant (like check-descriptions), since the
  playwright fix already proved the instance-by-instance approach leaves siblings behind.
- The duplicate-`@firebase/app` guard belongs at the serve/preflight boundary as a warning, not in the generator.

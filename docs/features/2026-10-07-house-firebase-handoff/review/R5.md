# R5 — adversarial review: deploy targets and the house-targets record

Reviewer: R5 (read-only on code). Scope: `firebase:deploy` / `functions:deploy`, `--seedRules`,
`_utils/house-targets.ts` + `house-targets-0.49.2.ts`, `tools/firebase-deploy.mjs` and `firebase-deploy-rules.mjs`.
Evidence: the pure merge was driven directly (`scratchpad/r5/m.mjs`, `m2.mjs`, node type-stripping over the real
`.ts`); Nx 23.1 behaviour in a scratch workspace (`scratchpad/r5/ws`); firebase-tools 15.32.1 source (yarn cache).
`node tools/test-generators/run.mjs "house targets"` → 11/11 pass; none of the findings below is covered by a case.

## Findings (ranked)

### R5-1 · HIGH · conf high — the seeded `firestore.indexes.json` is unmarked, so `firebase:deploy` ships it; with `--force` it deletes every production index
- Where: `firebase-emulators/firestore.indexes.json.tpl` (no marker — JSON cannot carry one); `firebase-deploy-rules.mjs.tpl:57-63` skips by `firestore:rules`/`storage` service only.
- Scenario: project created/`add-layer firebase` with `--seedRules`; rules files carry the marker, so `firestore:rules` and `storage` are skipped — but `firestore:indexes` (empty seed) still deploys. firebase-tools `firestore/api.js:85-104`: indexes and field overrides "not present in your firestore indexes file" are deleted when `options.force`. The deploy contract forwards EVERY argument to EVERY deploy target, and `--force` is exactly what a team adds the first time `functions:deploy --non-interactive` aborts on a deleted function. `nx affected -t deploy --project=prod --non-interactive --force` → production indexes and field overrides wiped. Without `--force` it is merely a pointless deploy (and an interactive prompt by hand).
- Fix: treat a Firestore entry as seeded when its rules file carries the marker — skip `firestore:indexes` with it (or don't seed the indexes file at all; the emulator does not need it). Add a fixture: seeded project → `firebase:deploy` invokes nothing.

### R5-2 · HIGH · conf high — a house target name the project already uses is silently hijacked (`command` vs `commands`)
- Where: `house-targets.ts:121-131` / `mergeValue` — per-key merge with no notion of "this whole target was the project's".
- Scenario (verified, `m2.mjs`): the consumer that filed B1 hand-made `firebase:deploy` = `{ options: { commands: ['firebase deploy --only firestore,storage,hosting'] } }`. First 0.50 upgrade: `commands` kept (house doesn't declare it), `command` arrives (project doesn't have it) → **0 overrides reported**; Nx run-commands `normalizeOptions` lets `command` win over `commands`, so the hosting deploy silently stops. Same for any future release that introduces a target name a project already uses (record present, `recorded[name]` undefined → same path). A project-owned `executor` change is also kept while house `options` merge into it.
- Fix: when the house first introduces a target (`base` absent for that target, with or without a record) and the project already defines one, treat the whole target as a conflict: keep the project's, report it, and record nothing for it (or name it in a migration). At minimum treat `command`/`commands` (and executor) as one key.

### R5-3 · MEDIUM · conf high — `--seedRules` fires on re-ensure of an existing Firebase project and flips the local emulators to deny-all
- Where: `layers/firebase.ts:74` (`ctx.ensured.has('firebase')`); `house.sh:719-731` drops an evident layer from the ensure set only when it is NOT upgrade-ensurable — firebase is, so it stays ensured.
- Scenario: every 0.49 house project has no `firestore`/`storage` key in firebase.json (checked: `fx1/coach049/firebase.json`) — its emulators run open. `/bespunky-house:add-layer firebase` (or `add-layer --firebase ci`) on it seeds deny-all and declares it; the emulators now enforce deny-all and every client read/write fails locally. Production is safe (marker), local dev is not. The stated rationale for "never on upgrade" (overwriting live rules) is already neutralised by the marker; the real hazard is this one, and the gate doesn't catch it.
- Fix: gate on "firebase ensured AND not evident before this run" (pass `ctx.active`-before-ensure, or have house.sh compute `created = ensured − evident`). Add a test-layers case.

### R5-4 · MEDIUM · conf high — `readiness()` ignores the active project `firebase use --add` sets
- Where: `firebase-deploy.mjs.tpl:68`, `:87`, `:139`.
- Scenario: firebase-tools `commands/use.js:104` — `use --add` writes the alias and `configstore.activeProjects[<dir>]`, never `projects.default`. So after following step 2 exactly, `--check` still shows step 2 unticked (tick requires a `default` alias or `-P`), and a failed `nx run functions:deploy` with no `-P` (Firebase used the active project) is misdiagnosed as "No project was named… step 2". Also gcloud ADC is looked up under `$XDG_CONFIG_HOME`, but gcloud honours `CLOUDSDK_CONFIG`/`~/.config/gcloud`, not XDG.
- Fix: read `store.activeProjects[ROOT]`; tick step 2 on `aliases.length` (its own "Worked when"); use `CLOUDSDK_CONFIG ?? ~/.config/gcloud`.

### R5-5 · MEDIUM · conf medium — no-record set merge ignores the 0.49.2 baseline: deliberate removals are resurrected silently
- Where: `house-targets.ts:166-167` (`base = hasRecord ? base : []`).
- Scenario (verified): 0.49 project that removed `build` from `functions:deploy.dependsOn` → first upgrade returns `['build','lint']` with **no report**, though scalars in the same situation ARE reported. The header promises "a hand edit is never lost silently".
- Fix: use `before` as the set base when there is no record (it is evidence of what the house wrote), or report every set member the merge adds back.

### R5-6 · LOW-MEDIUM · conf medium — the record-less path silently keeps keys older releases dropped
- `mergeValue:153-157`: no record → an undeclared key is kept, then the first record makes it look like the project's forever. 0.50 compensated by hand with migrations (`read-functions-params-in-place`, `stack-owned-dev-processes`, `lint-house-apps`). But a project jumping from < 0.49.2 never ran the replace-whole generators of 0.41–0.49 that used to heal drops; those drops have no migration. I found no concrete such key in history (house targets were stable), so this is a class risk: the baseline should decide removals too (a key equal to the 0.49.2 value that the house no longer declares is the house's → drop it), instead of each drop needing a hand migration.

### R5-7 · LOW · conf high — record hygiene
- Renamed/moved/removed house projects leave stale record entries forever (`recordHouseTargets` never prunes), and house-doc lists them in HOUSE.md (`recordedHouseProjects`).
- Deleting the record (or a renamed project) falls back to the **0.49.2** baseline at any future version: a value deliberately set equal to a 0.49.2 value is then replaced silently.
- Two branches upgrading at different payloads conflict textually on the record; resolving to the older side makes later upgrades report false conflicts (noisy, not lossy — `same(theirs, ours)` short-circuits).

### R5-8 · LOW · conf high — arguments go through a shell before the runner
- The runner's `spawnSync` (no shell) is safe, but Nx run-commands re-quotes forwarded args in double quotes: `-m 'cost $HOME \`id -u\`'` executes the substitution (observed). Upstream, but the contract "forwards every extra argument" should say args are shell-interpreted. CI passes fixed args, so low.

## Verified true (claims I tried to break)
- `parallelism: false` is honoured across projects in one invocation (`tasks-schedule.js:231-252`; observed serial run of two projects' deploys). It does nothing across invocations — the CI concurrency group must cover that.
- `{workspaceRoot}/…` target inputs do drive `nx affected` (`affected/locators/workspace-projects.js` `getImplicitlyTouchedProjects`) — even on a `cache: false` target.
- `nx run p:deploy -P prod -m "a b"` and `run-many -t deploy --project=prod --non-interactive` forward as claimed.
- Missing declared rules file fails before shipping; nothing is deployed when firebase.json declares no rules.

## Design disputes
1. **"House wins on conflict."** For a deploy target the project's edit is the more specific intent (a wrapper, `--force`, a `-P`), and the only signal of the loss is a `logger.warn` buried in an upgrade's generator stream — house.sh aggregates only `[layers] WARNING` lines into its summary. Either keep the project's value and report the house's (git's conflict stance), or surface overrides in the final summary/UPGRADE_PARTIAL-style line.
2. **The deploy contract is fully overridable.** `parallelism`, `cache`, `dependsOn: lint` are ordinary keys: a project flipping `parallelism: true` or deleting `cache` keeps it silently. If these are the CONTRACT (the header says so), they should be re-asserted, or at least reported when the project diverges.
3. **The generic mechanism leaked one Firebase-specific artifact into every house project.** `project-files.ts` passes `HOUSE_TARGETS_AS_OF_0_49_2[canonical.name]` for shared-browser and worktree-domains too — fine — but the baseline was captured from ONE scaffold (`--preset=angular --firebase --staging`, apps/ layout): different layouts/flags differ in path values, which only stays silent because those values did not change. The baseline should be per-version data owned by the migration ladder, not a hard-coded fallback with no expiry.
4. **`tools/firebase-deploy.mjs` is an input of both deploy targets** — every toolkit release that touches the runner redeploys functions and rules from CI on the upgrade commit. Probably acceptable (idempotent deploys), but it should be a stated choice; the same goes for `firebase.json`, whose `emulators` block the house rewrites.
5. **Rules inputs are frozen at generation time** (`rootRulesInputs`) while the deploy reads firebase.json at run time: a rules file declared later at a non-conventional root path deploys but is invisible to `affected` until the next upgrade.

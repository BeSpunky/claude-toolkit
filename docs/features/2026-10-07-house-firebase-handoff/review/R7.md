## Findings (ranked)

### R7-1 · HIGH · high confidence: the always-on rules and the Firebase reference still say the emulator launch kills the developer's suite
- **Where:** `HOUSE.rules.md.tpl:113` ("`tools/emulators.sh` **reaps existing emulator processes** on launch, so a suite booted on the base ports kills the developer's running one") and `local-server-isolation/reference/firebase-emulators.md:5` ("`firebase emulators:start` **reaps existing emulator processes first**").
- **What's wrong:**
  - Both statements are false. `reap-emulators.sh.tpl` kills only orphans (`is_orphan`: reparented to PID 1). When it finds a live owned holder it exits 1 and says "Nothing was killed".
  - `firebase emulators:start` reaps nothing at all.
  - The text is always in context, so every session learns the wrong failure mode.
- **Fix:** say that a colliding suite on the base ports **refuses to start** (the reaper names the holder and kills nothing), so you shift your own stack. Drop the attribution to `firebase emulators:start`.

### R7-2 · HIGH · high confidence: the Firebase reference prescribes the command that SKILL.md now says doesn't work
- **Where:** `local-server-isolation/reference/firebase-emulators.md:9`.
- **What's wrong:**
  - The reference still prefers `<pm> nx serve <app> --port-offset=auto` for an Nx-served app.
  - `SKILL.md` (Shift the whole stack) and HOUSE.md now say a second `nx serve` in the same tree attaches to the developer's `<app>:dev-stack`, or is refused by the preflight. It does not start an isolated stack.
  - The reference describes exactly the developer-is-running-a-suite case, so it sends Claude to the broken path.
- **Fix:** `tools/dev/dev serve <app> --port-offset=auto` in all cases, with the `dev-stack` reason.

### R7-3 · MED · high confidence: HOUSE.md contradicts itself on host-tab viewing of a worktree
- **Where:** rendered HOUSE.md *Serving an in-flight worktree* (tpl, base line 309): "A worktree serve is viewable ONLY through the shared browser — its shifted ports aren't forwarded".
- **What's wrong:** the rewritten *Two ways to view* §2 now says a worktree's app at `<slug>.localhost`, served through the forwarded `:80` proxy, works in a host tab and reaches its own shifted emulators. The old sentence was true only while emulators were dialled directly.
- **Fix:** rewrite it to "viewable in the shared browser, or a host tab at `<slug>.localhost` (subject to the multi-container caveat)".

### R7-4 · MED · high confidence: `firebase init firestore storage` pulls only Firestore
- **Where:** `plugins/house/tips.txt:20` and HOUSE.md.tpl *Deploying the backend* ("Rules not in the repo yet?").
- **What's wrong:**
  - Both say `npx firebase init firestore storage -P <alias>` pulls the live rules.
  - firebase-tools `commands/init.js` is `init [feature]`, a single positional. Commander drops the extra positional silently, so Storage is never pulled.
- **Fix:** two commands, `firebase init firestore -P <alias>` then `firebase init storage -P <alias>`. Each one downloads the live ruleset.

### R7-5 · MED · high confidence: the backend's connection can't be found the way `moving-accounts.md` says
- **Where:** `moving-accounts.md:21-24`.
- **What's wrong:**
  - It says the backend's connection is the one in its repository path, as shown by `backends:get` (the Repository column) or the console.
  - The table prints `codebase.repository.split("/").pop()`, which is only the git-repository-link id, never the connection name.
  - Step 2 ("keep the one the backend uses") depends on this, so a user can delete the live connection.
- **Fix:** `firebase apphosting:backends:get <id> --project <p> --json` → `codebase.repository` (`…/connections/<conn>/gitRepositoryLinks/<id>`).
- **Related, low confidence (medium):** the states `COMPLETE` / `PENDING_*` are `installationState.stage`. They may not appear in the default table, so suggest `--format='table(name,installationState.stage)'`.

### R7-6 · MED · high confidence: `setup-gcp.sh --dry-run` alone fails in the case CI is for
- **Where:** HOUSE.md.tpl *The one-time cloud setup* (`! bash tools/setup-gcp.sh --dry-run`) and `plugins/house/tips.txt` ("`! bash tools/setup-gcp.sh --dry-run` shows every IAM grant first").
- **What's wrong:** `setup-gcp.sh.tpl:65-67` dies with "binds several environments — choose one" whenever the model binds more than one environment, which is the staging + production case.
- **Fix:** document and tip `--dry-run --environment <environment>`, or make `--dry-run` without an environment iterate over all of them.

### R7-7 · LOW-MED · high confidence: HOUSE.rules.md grew with how-to

### R7-8 · LOW · medium confidence: `--skip=emulators` carries `?emulate=none` only when the declaration says so
- **Where:** rendered HOUSE.md *Per-service emulator toggling* (non-`nx-serve` variant).
- **What's wrong:**
  - The doc says `tools/dev/dev serve <app> --skip=emulators` "carries `?emulate=none` to the app".
  - It does so only if the declaration has the `url: [{param:"emulate",value:"none",when:"skipped"}]` entry (`lib/declaration.mjs.tpl:17`).
  - The same variant's recipe for hand-adding an `emulators` process omits that entry. Skipping then silently keeps the app emulated.
- **Fix:** add the `url` entry to the recipe.

### R7-11 · LOW · high confidence: the Firebase CLI is spelled two ways for the same steps

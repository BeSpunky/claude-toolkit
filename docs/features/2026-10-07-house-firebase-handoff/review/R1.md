# R1 — adversarial review: version truth and the Node source

Scope: `_utils/{versions,dependencies,firebase-compat,node-version}.ts`, `tools/firebase-compat/project.mjs`,
`adapters/angular/angularfire.ts`, the creation-time Angular pin, house.sh's Node, firebase-tools as a devDependency,
gcloud in the image, and the 0.50.0 rungs `pin-floating-dependencies`, `declare-node-version`,
`firebase-cli-from-package` and `gcloud-cli-from-image`. Reviewer: R1 (read-only). Throwaway fixtures are under
`…/scratchpad/r1`. Paths below are relative to `plugins/house/engine/nx-tools/src/` unless they say otherwise.

## Findings, most severe first

### R1-0 · BLOCKER · verified by running — `new --preset=angular --firebase` fails: the Angular 20 pin breaks the design-system library
`adapters/angular/angularfire.ts:290` (`pinAngularForFirebase`) together with `adapters/angular/libs.ts:62`.

**How I ran it.**
`PROJECTS_DIR=…/scratchpad/r1/new bash plugins/house/engine/house.sh new --local --preset=angular --firebase shop web`.

**What happened.** The pin worked: it logged "Angular 20 — the newest major @angular/fire supports". The app was
created on `@angular/core ~20.3.0`, with @angular/fire 20.1.0 and firebase ^11.8.0 (one SDK). Then the next layer step,
`nx g @bespunky/nx-tools:design-system`, asked @nx/angular for `unitTestRunner: 'vitest-angular'`, and @nx/angular
refused:

> The "vitest-angular" unit test runner requires Angular v21 or higher. Detected Angular v20.3.0.

The result was `UPGRADE_FAILED`, rc=1, with a half-built workspace left behind. This is the run W1 follow-up 1 says it
never did. The flagship creation path does not work at all, and no fixture can show it: the stand-in @nx/angular in
`versions.mjs` has no runner checks.

**Fix.** Make every Angular-version-dependent choice the adapter makes go through one place that knows the workspace's
Angular major. Here, a publishable library on Angular <21 uses `jest` or `vitest-analog`. Then add a real `new` run to
the release gate.

### R1-1 · major · verified by running — `declare-node-version` writes `.nvmrc = 1` for the stock VS Code TypeScript-Node devcontainer
`migrations/0.50.0/declare-node-version.ts:25` (`/typescript-node:(\d+)/`).

**What happens.** Microsoft's own "Add Dev Container Configuration Files → TypeScript & Node" template writes
`"image": "mcr.microsoft.com/devcontainers/typescript-node:1-22-bookworm"`. The `1` is the image's own version, not
the Node major. I ran the compiled rung against that devcontainer. It wrote `.nvmrc = 1` and logged "the Node this
project's devcontainer already runs (… typescript-node:1)". The generator then accepts `1` as a valid major:

- the CI workflow's `setup-node` (`node-version-file: .nvmrc`) asks for Node 1, so the deploy job fails;
- nvm and fnm users get Node 1;
- functions `engines.node` falls back to 24;
- `house.Dockerfile` becomes `FROM typescript-node:1`, which is the newest image. It is inert while the image is adopted.

The same rung also misses these:

- a feature `"version": "lts"` (the Node feature's own default) or `"22.11"`. No `.nvmrc` is written, so the generator
  seeds 24, and on an owned devcontainer the next upgrade moves Node. The rung exists to prevent exactly that.
- a project's own `build.dockerfile`. It is not read, so `.nvmrc` is seeded 24 regardless of what that image runs.

**Fix.** Parse the tag grammar (`[<imgver>-]<major>[-<distro>]`) and take the Node major, not the first digit run. Read
`major` from `X.Y` feature versions. Treat `lts` / `latest` and an unknown Dockerfile as "unknown → report, do not seed".
Add fixture cases for `1-22-bookworm`, `22-bookworm`, `lts` and `22.11`.

### R1-2 · major · verified by running — npm projects on Angular 17–19 can no longer install after `firebase-cli-from-package`
`migrations/0.50.0/firebase-cli-from-package.ts:57`, `generators/_utils/versions.ts:32`.

@angular/fire 17.1.0, 18.0.1 and 19.2.0 each declare an optional peer `firebase-tools@^13.0.0`. The rung adds
`firebase-tools 15.32.1` unconditionally. I ran
`npm install --package-lock-only` on `@angular/fire 19.2.0` + `firebase-tools 15.32.1`. It failed: **`ERESOLVE …
peerOptional firebase-tools@"^13.0.0" from @angular/fire@19.2.0`**.

The table already knows this (`firebaseToolsOk: false`). The generator only warns about it (`angularfire.ts:234`), and
the rung never consults it. So every npm-managed house app below Angular 20 upgrades into a broken `npm install`, and
nothing in the run says why.

**Fix.** In the rung and the generator, when the installed @angular/fire's peer rejects the house pin, either:
- declare the newest firebase-tools inside that peer range (derived in the table, like the rest), or
- refuse with the choices.

At minimum, the rung must say it before writing.

### R1-3 · major · verified by running — the gcloud apt pin expires in about 11 months and breaks every image build
`generators/_utils/versions.ts:40`, `layers/firebase.ts:106`, `generators/devcontainer/house.packages.sh.tpl:104-125`.

Google's apt index holds 48 `google-cloud-cli` versions today (543.0.0-0 … 588.0.0-0), which is a rolling window of
about a year. `588.0.0-0` is the newest, so its lifetime is as long as it gets.

After that, any **cache-miss** image build of a house Firebase project fails. That means a new teammate, a new machine,
CI, Codespaces, or "Rebuild Without Cache" (which HOUSE.md tells users to run for security updates). It fails after
3 retries with 10 s and 20 s sleeps, then exits 1, and the container never builds. The project cannot fix this itself:
`house.packages.sh` is generator-owned, and `nx-tools` is pinned exactly, so the only way out is a toolkit release plus
an upgrade.

The `GONE:` check in `project.mjs` only runs in **this** repo's CI. It protects the next release, not any project
already on disk. The persistence audit is correct (`~/.config/gcloud`), but pinning to an expiring artifact is the
wrong mechanism.

**Fix.** Pin to Google's versioned archive (`dl.google.com/dl/cloudsdk/channels/rapid/downloads/google-cloud-cli-<v>-linux-<arch>.tar.gz`,
which is kept), or fall back to the newest version in the repository with a loud warning. An image that fails to build
is worse than an unpinned gcloud.

Related problems:
- Once a pin moves, `apt-get install -y google-cloud-cli=<older>` needs `--allow-downgrades`. An adopted image whose
  gcloud was upgraded loops through the retry ladder on **every container create**.
- An adopted image that already declares Google's repository under a different file name or keyring gets
  `Conflicting values set for option Signed-By`. `apt-get update` then fails for **all** packages, including the JDK
  (suspected; not run).

### R1-4 · major · verified by running — a common `.nvmrc` stops every upgrade
`generators/_utils/node-version.ts:24-35`, called by `generators/devcontainer/generator.ts:125` and
`generators/firebase-emulators/generator.ts:456`.

These all throw: `lts/*`, `lts/iron`, `node`, `22.x`, and a `.nvmrc` with a `#` comment (nvm ≥0.40 accepts comments).
The `declare-node-version` rung only warns, "the next upgrade will refuse it". But the generators run later in the
**same** upgrade, so it aborts mid-run after the migrations have committed. The fix it asks for (a bare major) forces a
project to rewrite a file that nvm, setup-node and Volta users already read correctly.

Two more cases fail late:
- **Odd majors** (19, 21, 23, 25): the house builds `typescript-node:<major>`, and MCR publishes only 14, 16, 18, 20, 22,
  24 and 26. These are accepted silently and fail at image pull, which is exactly the "environment not observed" class.
- **18**: functions `engines.node` falls back to the *newest* runtime (24), not the nearest
  (`firebase-emulators/generator.ts:459`).

**Fix.**
- Accept the nvm grammar: strip comments, resolve `lts/<codename>` from a small projected table, and resolve
  `lts/*` / `node` the same way with a report.
- Validate the major against the image tags the `node` layer can actually use (project them like the other tables).
- Refuse in the probe, before anything is written, never mid-generate.

### R1-5 · minor · verified by reading — the staleness alarm masks the test suite, misses releases, and is half dead
`.github/workflows/migration-tests.yml:63-70`, `tools/firebase-compat/project.mjs:67`.

- The check runs **before** "Run generator fixture tests" in the same job. When an upstream release lands, every PR
  goes red for a reason unrelated to the PR, and the generator tests do not run at all.
- There is no `schedule:`, so the alarm sounds only when someone happens to push.
- `publish.sh` and `publish-nx-tools.yml` never run it, so a stale table can be published.
- `minAngular`: `semver.validRange('(^21.2.0) >=21.0.0')` returns **null**, because node-semver has no parentheses, so
  the major-clamp is dead code. Every row falls back to `minVersion(peer)`. Today that is harmless. For a peer that
  spans majors (`^20 || ^21`) it reports the earlier major's minimum.

**Fix.**
- Move the check to its own job with `continue-on-error` and a weekly schedule.
- Gate `publish.sh` on it.
- Clamp with `semver.intersects` plus a `minVersion` on `>=M.0.0 <M+1.0.0-0`.

### R1-6 · minor · verified by reading — the refusal states a frozen fact as live
`adapters/angular/angularfire.ts:133,208`.

The messages say "No stable @angular/fire supports Angular N **yet**" and "Every house upgrade checks again and names
the release when it ships". The table is frozen inside the project's exactly pinned nx-tools, so neither claim is true
until a toolkit release regenerates the table and the project upgrades.

**Fix.** Stamp the projection date into the table, and say "as of <date>".

### R1-7 · minor · verified by reading — the guard is not airtight
`tools/test-generators/cases/versions.mjs:78-81`, `generators/_utils/dependencies.ts`.

The class guard catches only the identifier `addDependenciesToPackageJson` and a quoted `'latest'` or `'next'`. These
bypass it:
- writes through `updateJsonInPlace(tree,'package.json',…)` (`angularfire.ts:307`, `publishable-lib/generator.ts:204`,
  `adopt-extracted`);
- template-rendered manifests (`*.tpl` are not scanned);
- any `'*'`, `'^22'` or `'>=x'`.

Separately, the rung's own report regex (`pin-floating-dependencies.ts:34`) disagrees with the seam's: `^1`, `>=1`
and `1.x` are refused by the seam but never reported by the rung.

**Fix.** Validate at the write: run every package.json write in generators through one helper that calls `isPinnedSpec`.
Have the rung report with `isPinnedSpec`.

### R1-8 · nit · verified by reading — the pairing assumes the @angular/fire major equals the Angular major
`angularfire.ts:110,195-196`.

`majorOf(fire)` is compared with Angular's major. If a stable release ever peers two majors (as AngularFire 7.x did),
row N+1's `stable` is a release with major N. The generator then warns "built for Angular N" on every upgrade, while
recommending that same release as the fix. `project.mjs` does not assert the premise.

**Fix.** Assert `semver.major(angularfire) === major` in the projection, or judge by the release's `angularCore` peer.

### R1-9 · nit · verified by reading — a no-op check
`angularfire.ts:110`: `isPinnedSpec(installedFire.version)` is always true, because an installed version is exact.

## Disputes of design choices

- **Migrations import live code.** `versions.ts:17-18` states that a migration "never imports these (it freezes its own
  copy)". `pin-floating-dependencies` imports `angularfire.ts`, and with it the live table and live versions. FX2
  argues this keeps one voice. The cost is that a 0.50.0 rung behaves differently under every later payload, so its
  fixture no longer pins its behaviour. Either drop the rule from the header or freeze the judge. Today the code
  contradicts its own stated rule.
- **The Angular major depends on a creation flag.** `new --preset=angular` (no `--firebase`) creates Angular 22. A
  later `add-layer firebase` then **refuses**, by throwing mid-generate in the per-app step, not in a probe. So the
  flagship stack is reachable only if you knew at creation time. Either `new --preset=angular` should pick the
  Firebase-capable major too, or the refusal must run before anything is written.
- **firebase-tools as a root devDependency** puts the CLI's very large dependency graph, and its peer constraints
  (R1-2), into the app's install graph and lockfile. A separate tools manifest or `npx -p firebase-tools@<pin>` would
  pin it as well, without coupling to the app's resolver. This was not weighed in W1.
- **`.nvmrc` as the one Node fact** ignores `.node-version`, `engines.node` and Volta (`package.json` → `volta.node`)
  that a project may already use. It seeds a second, contradicting source and calls it the only one. On an adopted
  devcontainer with its own image, `.nvmrc` drives nothing, yet HOUSE.md says it sets the container's Node.
- **Offline / registry error.** No runtime registry call was added (the tables are static), so `new` is no worse
  offline than before. That is fine.

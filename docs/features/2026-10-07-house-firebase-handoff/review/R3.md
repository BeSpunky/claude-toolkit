# R3: adversarial review of stack identity and the dev loop

Reviewer: R3 (read-only on code). Scope: run records and `dev ps`/`dev stop`, the per-stack TMPDIR, the port table, the
detached emulator keeper, the `dev-stack`/`serve`/`serve-preflight` split, the invoker postscript, and migrations
`stack-owned-dev-processes` and `split-serve-follower`. Base: `git merge-base HEAD origin/development`.
Throwaway fixtures: `scratchpad/r3/` (dev engine copied from the templates; `emulators.sh` rendered the same way
`emulators-stop.test.sh` renders it; a functions-only firebase-tools 15.32.1 project using fx4's `node_modules`).
Every process I started was stopped by its PID.

Findings are ranked most severe first.

---

## R3-1: concurrent serves in one tree lose stack handles, and `auto` is refused with "use auto". HIGH, verified by running

**Where:** `dev/files/dev.mjs.tpl:286-301`. `resolvePortOffset` consults only port probes, and the twin check comes
after it. Also `dev.mjs.tpl:366` and `lib/stacks.mjs.tpl:97-102`: `writeRecord` renames over any existing record, so
claiming a key is not exclusive. Also `stacks.mjs.tpl:109-120`: `removeRecord` matches on the PID, and a record that
was overwritten belongs to the overwriter.

**Scenario 1 (verified).** Run `tools/dev/dev serve web` twice, 1 s apart, while the first is still binding.
- Ports are not bound yet, so `auto` picks the same block.
- The twin check then refuses: `web@0 is already being served … or serve another stack beside it (--port-offset=auto)`.
- The caller *did* pass auto.

**Scenario 2 (verified).** Start five `dev serve web` at once.
- Afterwards, `dev ps` listed only `web@21000`.
- `web@0` (pid 160670, holding :41234) and `web@20000` (pid 160671, :61234) were live, but neither had a record.
- `tools/dev/dev stop web --offset=0` printed "nothing of yours to stop" and exited **0**.
- The losers overwrote each other's records, failed to bind, and then removed the record. By then it was theirs, so
  the PID check let them.

This is exactly the fan-out case the house guidance creates: several agents in one shared tree, each told to run
`dev serve <app> --port-offset=auto`. Leaked servers that no handle can reach are what the whole feature exists to
prevent.

**Fix:**
- Claim the key atomically before spawning anything: `open(record, 'wx')`, or `mkdir` the state dir as the lock.
- Make `auto` skip every offset that has a live, orphaned or finishing record. The records, not the ports, are the
  identity during startup.
- If an `auto` claim loses the race, try the next block instead of refusing.

## R3-2: the per-stack TMPDIR breaks Functions emulator workers in deep trees. HIGH, verified by running

**Where:** `firebase-emulators/emulators.sh.tpl:81-92` sets `TMPDIR=<tree>/.bespunky/run/<app>@<off>/tmp`.

**The mechanism.** firebase-tools `functionsEmulatorShared.getTemporarySocketPath()` is
`os.tmpdir()/fire_emu_<16 hex>.sock`, and every Functions worker listens on that Unix socket. libuv silently truncates
`sun_path` to 107 bytes.

**What I observed:**
- With a 99-character TMPDIR, the socket file on disk was literally `…/tmp/fire_emu`. The random part was gone.
- Two concurrent requests to functions `a` and `b` both returned **"B"**: a request was answered by the other
  function's worker.
- One worker then crashed with `listen EADDRINUSE`.
- With a 178-character TMPDIR, both requests failed.

**Real house paths:**
- `/workspaces/claude-toolkit/.claude/worktrees/house-firebase-handoff/.bespunky/run/web@24000/tmp` is 95 characters,
  which leaves 2 hex characters (256 names).
- From 97 characters on, every worker shares one socket. A longer slug, project name or app name gets there.

**Why nobody saw it:**
- It is a regression: `/tmp/fire_emu_*.sock` always fit.
- DF2b never invoked a function, and FX1 and FX4 tested Auth and Firestore only.
- The dogfood fixtures' own paths (129 characters) would have shown it on the first function call.

**Fix:**
- Give each stack a short, hashed TMPDIR, e.g. `${XDG_RUNTIME_DIR:-/tmp}/bsk-<hash(tree,key)>`.
- Record that path in the run record. Prune it and release it the same way the state dir is handled today.
- Add a test asserting a length budget, e.g. TMPDIR ≤ 60 characters.

## R3-3: a hung export wedges the stack forever, and nothing can stop it by handle. HIGH, verified by running

**Where:**
- `emulators.sh.tpl:524-533`: the keeper loops `while kill -0 $fb`, with no deadline and no escalation.
- `emulators.sh.tpl:301-319`: a restart waits for the old suite, then refuses.
- `dev.mjs.tpl:595-600`: for a finishing stack, `pids = []`, so it signals nothing.

**Scenario (verified).** I used a fake `firebase` whose TERM handler never finishes the export.
1. SIGKILL the script, which is what Nx does after 5 s.
2. The keeper (PPID 1, its own process group) sends TERM and then waits forever. Its entry stays `stopping`.
3. `dev ps` shows FINISHING indefinitely, and `dev stop` only waits.
4. Every restart prints "previous suite STILL saving … Not starting over it" and exits 1.

The only way out is a manual kill by PID, which the house rules steer people away from. That is the
"outside any process tree" design defeating teardown-by-handle exactly when it matters: nobody owns the keeper's
deadline. Normally the keeper does follow its proxy, so TaskStop and Ctrl+C still end it.

**Fix:**
- After the stop request, the keeper SIGKILLs its own process group once a deadline passes
  (`EMULATORS_STOP_TIMEOUT` plus a grace period).
- It then records `result: export ABANDONED after Ns` with a non-zero code.
- Add `dev stop --abandon` for a finishing stack. It signals the keeper's group, verified by PID and start time.

## R3-4: a stale exit record under a reused PID ends `nx serve` at once. MEDIUM, read in code

**Where:**
- `executors/serve-preflight/executor.ts:112` is the only place a stale `exits/<invocation>@<app>.json` is cleared.
- `follow-stack/executor.ts:278-279` ends on any record it finds.
- `serve/executor.ts:106` starts nothing if that record says `refused`.

**Why it reaches projects.** Migration `split-serve-follower.ts:72-83` copies the old composer as is. A project whose
per-app generator steps are skipped (`UPGRADE_PARTIAL`) therefore has `dev-stack` with no `serve-preflight`
dependency and no `serve-preflight` target, and nothing ever clears the record.

**Scenario.** After a container restart, PIDs repeat. The new `nx serve` gets the PID of an invocation that left a
record. The follower ends immediately with the old status (0, or an old FAILED block). Nx then reaps `dev-stack` as
"fulfilled".

`pruneExits` cannot catch this, because the reused PID is alive.

**Fix:**
- Stamp the invocation's kernel start time into the record, and ignore any record whose stamp differs, in every
  reader.
- Or have the migration add the preflight target and dependency.

## R3-5: "not continuous" depends on the key being absent, and Nx fills absent keys. MEDIUM, read in code

**Where:**
- The follower omits `continuous`: `_utils/dev-server.ts` `followerFor`, and `split-serve-follower.ts:45-53`.
- `stack-owned-dev-processes.ts:52,68,78` deletes the key rather than setting it to false.

**What Nx does.** Nx resolves an absent `continuous` from two sources:
- nx.json `targetDefaults`, keyed by target name. A `targetDefaults.serve` now applies to the *follower*.
- The executor schema (`target-normalization.js:52-58`).

**What re-imposes it.** The `@nx/angular` migration `update-21-0-0/set-continuous-option` sets `continuous: true` on
`@nx/angular:dev-server` and `@angular-devkit/build-angular:dev-server` whenever the key is undefined. That is
exactly the state this rung leaves. `split-serve-follower` scans targetDefaults' `dependsOn` lists, but not a
targetDefaults *key* named `serve`.

**Consequence.** If the follower becomes continuous, D3 is back: `nx serve` exits 0 on a dead stack. If the leaf
does, D2 is back: a second stack waits on the first.

**Fix:**
- Write `continuous: false` explicitly on the follower, the leaf and the emulator targets.
- Report `targetDefaults["serve"]`.

## R3-6: the preflight and follower identify "the running stack" by app alone, but Nx shares by configuration. MEDIUM, read in code

**Where:** `serve-preflight/executor.ts:122` and `follow-stack/executor.ts:285-293`.

**Scenario.** Run `nx serve web -c production` while `nx serve web` (development) runs.
- The task ids differ, so Nx starts a second `dev-stack`.
- The preflight still prints "This run ATTACHES to it", which is false.
- Until its own record appears (an install step can take minutes), the follower polls `dev ps` every 2 s.
- It can adopt the *other* invocation's stack as `followed` and register as its follower.
- If that stack stops first, this run ends with that stack's status. Nx then kills its own stack as "fulfilled".

**Fix:**
- Record the configuration in the run record, and match holders on app, configuration and nxRoot.
- Follow another invocation's stack only when the preflight's attach verdict was recorded for this invocation.

## R3-7: records from a previous container are "foreign" forever, or silently overwritten. LOW, verified by running

**Where:** `stacks.mjs.tpl:178`. The hostname is the container id, so it changes on every rebuild, and a rebuild while
serving is the common ungraceful end.

**What happens:**
- Such records are never pruned (`readStacks` prunes only `dead`). `dev ps` keeps listing them, and their state dirs
  stay.
- A new serve of the same key overwrote a foreign record without a word (verified).
- That contradicts the stated meaning of "foreign": another live container sharing the tree.

**Fix:**
- Identify the host by something that survives a restart but not a different machine, or record the container id
  explicitly.
- Expire foreign records after a TTL, or after `ps` confirms their ports are free.
- Treat a foreign record as a conflict at claim time (see R3-1).

## R3-8: the postscript waiters busy-poll for the invoker's whole life. LOW, read in code

**Where:**
- `emulators.sh.tpl:598-602` polls every 20 ms, forking `cat` and `sed` each time (about 100 forks/s).
- `invoker.ts:82-99` polls at 50 Hz.

**Problem:**
- The waiters live until the invoker exits. That is a whole `nx serve > log` session (the queued attach notice), or
  a CI `run-many` that keeps going for minutes after `dev-stack` stopped.
- The queue and lock files leak into `$TMPDIR` if a helper is killed.
- In a `> log; next-cmd > log` sequence, the late append can land in the next run's file.

**Fix:** poll at 1 s or more, and stamp the queue with the target inode.

## R3-9: "mine" is the whole Claude session. LOW, design

`ownerOf` falls back to `claude:<session>`, which is shared by the parent and every subagent. A child that forgets
`DEV_OWNER` and runs the prescribed `stop --all-mine` stops its siblings' and its parent's stacks in the middle of
their tests. Safety rests on prompt hygiene. Either make `--all-mine` require an explicit owner when the owner is
only the session, or record the spawning task id.

## Design disputes

**D1: a simpler design exists and was never weighed.**
- Make `serve` the same `@bespunky/nx-tools:serve` executor with `continuous: false`, and keep `dev-stack`
  continuous only for e2e `dependsOn`.
- Non-continuous tasks are never shared (V6), so a second `nx serve` simply starts its own isolated stack, which is
  what local-server-isolation demands anyway. The run's exit status is the engine's.
- This deletes `serve-preflight`, `follow-stack`, the exit records and their PID-reuse clearing (R3-4), the
  followers registry and the 10 s `attachedDone` waits, the 143 and `released` handling (the whole NB1/NB2 bug
  class), and R3-6.
- V6 and W3 weighed only leaf-level options. FX1 jumped straight to the follower.

**D2: the invoker postscript is a boundary violation, not a channel.** A task reopens another process's stderr
through `/proc/<pid>/fd/2`, and reads its fdinfo flags and its file offset behaviour, to beat Nx's renderer.
- It exists only because the account is routed through Nx.
- Under D1, the engine's own stderr is the run's output.
- For agents, the house skill already prefers `tools/dev/dev serve`, which no renderer hides.

**D3: the "detached keeper" is right for the export, but it must own a deadline (R3-3).** As it stands, only the
engine's 180 s wait and the restart's 120 s wait exist, and both only stop *waiting*.

**D4: three identity mechanisms with different keys.**
- The engine record is `<app>@<offset>`.
- A direct run's state dir is `firebase@<offset>`.
- The reaper's notion of an orphan is PPID==1.

A direct `nx run firebase:emulators` and a `dev serve web` at the same offset get different TMPDIRs and state dirs,
so neither's twin check sees the other; only the ports collide. One claim per port block would subsume all three.

**D5: migrations retarget well within project.json.** The gaps are targetDefaults keys (R3-5), and the
`UPGRADE_PARTIAL` composer that lacks the preflight its own comment says it has (R3-4,
`split-serve-follower.ts:7-8`).

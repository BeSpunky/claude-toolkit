# R4: adversarial review of emulator routing through the app's origin

Reviewer: R4 (read-only on code). Scope: `firebase.config.ts.tpl` (`emulatorEndpoint`), the four service configs,
`proxy.conf.mjs.tpl`, the SSR `PORT_OFFSET` path, the https refusal, `?emulate=none`, the forwardPorts kept for the
Emulator UI, and migration `0.50.0/route-emulators-through-origin` + `writeFirebaseClientGlue`.
Paths are under `plugins/house/engine/nx-tools/src/` unless stated otherwise.

## What I ran (scratch `r4/`, fixture copied from `fx4/coach`, which uses the current templates byte-for-byte)
- **Production build** (`@angular/build:application`) with all four services provided at root. Searched `main-*.js`
  for `emulate`, `PORT_OFFSET`, `is emulated`, `9099`, `8080`, `connectAuthEmulator` and `useEmulator`: none present.
  `emulator/auth` and `emulatorOrigin` are the SDK's own retained code. The emulate resolver, the overrides module and
  the https throw are all tree-shaken out. **A prod build cannot relay to an emulator.** No finding.
- **Real Angular dev server** (`nx run web:dev-server`, Angular's application builder, not the bare Vite server
  that W4 used), on a random port with `PORT_OFFSET=40000`, in front of stub listeners at base+40000.
  - The Functions route had never been run. It works: `/demo-coach/us-central1/hello` reached the :45001 stub.
  - All four Auth prefixes reach :49099, both Firestore prefixes reach :48080, and `/v0/b` reaches :49199.
  - The `x-goog-upload-url` rewrite works.
  - **Collisions confirmed** (see R4-2).
- SSR could not be run: the fixture has no `@angular/ssr` or `platform-server`, and the house scaffolds no SSR. The
  SSR findings are code-level only.

## Findings (ranked)

### R4-1: HIGH, confidence high. A project with its own `proxyConfig` loses every emulator after 0.50
`adapters/angular/index.ts:259-262` `useProxy` → `setLeafOption` is set-if-absent and returns **true** when the leaf
already points somewhere else. `firebase-client.ts:70` then reports nothing. The migration
(`route-emulators-through-origin.ts:92`) writes `proxy.conf.mjs` but never checks that the dev server uses it.

**Scenario:** the app's `dev-server.options.proxyConfig` is `proxy.conf.json`, the project's own relay for `/api`.
- Before 0.50, Firestore and Storage dialled their ports directly, and Auth did too because 0.24.3 left `proxied`
  off. Only callables needed the house proxy.
- After 0.50 every emulated service calls the page origin. The Angular dev server answers with a 404, or with the SPA
  `index.html` for a GET. Firestore hangs offline and Auth fails, silently.
- This is the "hangs, not errors" symptom from INBOUND-HANDOFF-2, now applied to every service.

The same happens for a non-Angular dev-server leaf. 0.35.0 warned about that case and did not wire it.

No fixture covers it: the 0.50.0 cases never set `proxyConfig`.

**Fix:**
- The migration and the generator detect a leaf whose `proxyConfig` is not the house file, and warn by name.
- Better: make the house relay composable. `proxy.conf.mjs` exports its routes, so a project proxy can spread them,
  or the house file imports a project-owned `proxy.local.mjs` seam.

### R4-2: MEDIUM, confidence high (reproduced). Proxy prefixes capture app routes
Vite (`url.startsWith(context)`, confirmed in the bundled Vite) and webpack's http-proxy-middleware both match by
plain prefix. In the real dev server these requests went to the emulators instead of the app:
- `/emulators` and `/emulator-settings` went to Auth.
- `/v0/blog` went to Storage, and its response even got `x-goog-upload-url` rewritten.
- `/demo-coach-landing` went to Functions.

A deep link or reload of such a route returns emulator JSON or 404. The header claim at `proxy.conf.mjs.tpl:251`
("none collides with an app route") is false.

**Fix:** anchor each key with a trailing slash as regex keys: `^/emulator/`, `^/v0/b/`, `^/<pid>/`, `^/v1/projects/<pid>/databases/`.
Angular passes keys that start with `^` through unchanged. Add a generator test that `/emulators` is not relayed.

### R4-3: MEDIUM (conditional on SSR), confidence high. The server ignores `?emulate=` / `?real=` / localStorage, including `--no-emulators`
`firebase.config.ts.tpl:104-111` with `emulator-overrides.ts.tpl` (`win` is `undefined` on the server) gives the
server the committed defaults, which are all emulated.

**Scenario:** `nx serve app --no-emulators` boots no suite and appends `?emulate=none`.
- The browser goes real, but SSR still connects to `localhost:8080+offset`, where nothing listens. Server renders
  then stall or error.
- In a worktree with `--no-emulators` the server dials an empty block. On the base stack it can hit the developer's
  running suite while the browser hits production data.
- With `?emulate=firestore`, the server and the client read different backends, which risks hydration mismatches.

The W4 note ("SSR: container address + PORT_OFFSET") solves the port but not the switch.

**Fix:** carry the per-session choice to the server.
- The dev engine exports an env var (for example `FIREBASE_EMULATE=none`) when the suite is skipped.
- The server-side resolver reads it.
- The per-request query override is documented as browser-only, or the resolver reads it from the `REQUEST` token.

### R4-4: LOW, confidence medium. The project id is scraped by regex from the env file's text
`proxy.conf.mjs.tpl:283-284` takes the first `projectId: '…'`, even one inside a comment such as a commented-out
staging block. A computed or imported `projectId` yields `''`. In that case the Functions and Firestore-REST prefixes
are **silently skipped**: Firestore transactions, batchGet and aggregations break while Listen/Write still work.

**Fix:** when no id is found, log once at dev-server start, and strip comments before matching.

### R4-5: LOW, confidence high. The Emulator UI is only correct on the base stack with identical forwards
The UI bundle (ui-v1.15.0) replaces a `0.0.0.0` listen address with `location.hostname` and the emulator's **container**
port. So:
- If the editor remaps a forward (8080→8081), that tab of the UI breaks.
- A worktree stack's UI (4000+offset) and its services are not in `forwardPorts` at all.

The comment admits this in part. Nothing reports it at runtime.

**Fix:** either accept it and say so in HOUSE.md's emulator section, or set `requireLocalPort` on the UI-dialled
ports so a remap is at least notified. V8 §3 shows this produces a dialog, not a refusal.

## Design disputes
- **A single global `proxyConfig` owned by the house is the wrong seam** (R4-1). The relay is infrastructure that a
  project's own proxy must be able to include. A generator-owned file that claims the whole option, with a silent
  set-if-absent, makes coexistence impossible without the project knowing the house's internals.
- **"Where the caller runs" is half the model.** `emulatorEndpoint` decides the address by runtime (window or not),
  but the on/off resolution is still browser-only state (URL plus localStorage). The SSR path therefore has an
  address and no decision (R4-3). The emulate choice needs one source both runtimes can read.
- **The https refusal throws inside a provider factory**, so a single emulated service bricks bootstrap. The
  neighbouring dev guard deliberately does *not* throw for the same class of misconfiguration ("bricking the whole dev
  app over one misconfigured service is worse"). The two guards contradict each other. Choose one policy.
  `initializeFirestore({host, ssl})` (V8 §4) would make Firestore work over https, so the refusal is broader than the
  SDK forces.
- **Not reviewed for lack of a runnable target:** the webpack dev-server path (`onProxyRes` under http-proxy-middleware
  v2/v3; v3 drops `onProxyRes` for `on.proxyRes`) and a real OAuth popup through `/emulator/auth/handler`. Both are
  still unproven.

# R2: adversarial review of "nothing run locally can reach production" (W2)

Reviewer scope: `emulators.sh.tpl` FUNCTIONS SECRETS, `functions.configDir`, `seed-apply.mjs.tpl`, migrations
`0.50.0/split-seed-applier` and `0.50.0/retell-secrets-example`, and the E1 warning. Checked against firebase-tools
15.32.1 (the pinned `FIREBASE_TOOLS_VERSION`) source, and by running the rendered `emulators.sh` with a fake
`firebase`, then feeding the file it wrote to firebase-tools' own `functions/env.js` `parseStrict`.
Harness: `scratchpad/r2/p`.

## Findings (most severe first)

### R2-1: a sandbox value identical to production goes live when it carries an inline comment or different quoting (major, verified by running)
`emulators.sh.tpl:400-447`. The clash check compares `unquote(m[2].trim())`, the raw text after `=`, and the
script writes the sandbox line through verbatim. firebase-tools' dotenv parser strips inline comments and quotes.
Example sandbox file:
```
STRIPE_KEY=sk_live_prod   # sandbox acct
BOT_TOKEN="prod-bot-token" #x
```
With `.secret.local` = `STRIPE_KEY=sk_live_prod`, `BOT_TOKEN=prod-bot-token`, the banner shows
`LIVE … BOT_TOKEN, STRIPE_KEY` with no `REFUSED` line. `parseStrict` of the placed file returns
`{"BOT_TOKEN":"prod-bot-token","STRIPE_KEY":"sk_live_prod"}`, so the production credentials are live in the
emulator. The refusal also does nothing in a worktree. The production `.secret.local` is gitignored and exists
only in the main tree, so in exactly the agent worktrees this protects, `prod` is empty and nothing is ever
refused. HOUSE.md (l.248) states the refusal with no caveat.
**Fix:** parse both files with the parser the emulator uses: `require('firebase-tools/lib/functions/env').parse`
from the project's installed firebase-tools, or a faithful port. Write the parsed value back out re-quoted, never
the raw text. In a worktree, compare against the main worktree's `.secret.local` values for this check only, the
one legitimate cross-tree read. Also refuse a value that equals *any* production value, not only the same key's.
Document that the check catches only exact copies.

### R2-2: one key firebase rejects silently discards every placeholder (major, verified by running)
`emulators.sh.tpl:400` (`LINE` accepts any identifier) and l.439 (`declared` = the union). firebase-tools
`resolveSecretEnvs` reads the file with `parseStrict`. That validates every key: no lowercase, no reserved
prefixes `FIREBASE_`, `X_GOOGLE_`, `EXT_`, `KIT_`, no reserved names. A `FirebaseError("Validation failed")` has
no `code`, so the catch neither logs it nor keeps anything: `secretEnvs = {}`. Example: a production
`.secret.local` holding `FIREBASE_SERVICE_ACCOUNT=…` (a plausible push-secrets entry), or `legacy_key=` in the
example. The emulator then loads no placeholder at all. Every declared secret falls through to
`accessSecretVersion`, and only the undocumented sink (R2-4) stands between it and production. The banner still
prints "no real credential is loaded". Layer 1 is one bad key name away from disappearing, silently, and that
breaks W2's claim "if firebase-tools renames it, layer 1 still holds".
**Fix:** write only keys that pass firebase's `validateKey` (same parser as R2-1). Report each rejected key by
name in the banner as something the emulator cannot be given. Validate the placed file with `parseStrict`
before launch, and exit 2 if it throws.

### R2-3: the guarantee covers Secret Manager only; production credentials and `.env` params stay live (major, read in code)
The brief promises "Nothing run locally can reach production", and HOUSE.md l.243 repeats it. The implementation
only stops the emulator from fetching secrets.
- **Credentials:** `functionsEmulator.start()` adds `getCredentialsEnvironment()` to every backend's env.
  `GOOGLE_APPLICATION_CREDENTIALS` becomes the developer's `firebase login` refresh token, or ADC is passed
  through with only a WARN. The runtime is spawned with `{...process.env, ...envs}`
  (`functionsEmulator.js:1127-1131`). Under the real project id that `emulators.sh` derives from
  `environment.ts` (the template tells users to put a real id there), any Admin SDK call to a service that is not
  emulated reaches production with real auth: `messaging().send()` pushes to real devices, as do Remote Config,
  Cloud Tasks, a non-emulated Storage bucket, and `@google-cloud/secret-manager` called directly. The last one
  ignores `CLOUD_SECRET_MANAGER_URL` and reads the real secret.
- **Params:** `.env` and `.env.<realProjectId>` hold production values and are loaded live by default (configDir
  adds `.env.<projectId>`). A Slack, Discord or Google-Chat webhook URL kept as a `defineString` param is a live
  capability. The only defence is a one-line hint in the banner.
- **Placeholder token plus live chat id:** nothing is delivered (Telegram returns 401). The request, with the
  chat id and message body, still leaves for the real API.

**Fix:** either narrow the claim everywhere to "no production *secret*", or enforce more. Options: under a
non-`demo-` project, unset or neutralise `GOOGLE_APPLICATION_CREDENTIALS` and point `CLOUDSDK_CONFIG` at an
empty dir for the emulator process unless sandbox mode is on. Refuse to start, or require an explicit
`EMULATOR_PARAMS=production`, when `.env` or `.env.<projectId>` keys are not overridden by `.env.local`.

### R2-4: the sink is an undocumented knob with no tripwire and no version guard (major, read in code)
`emulators.sh.tpl:377`. `CLOUD_SECRET_MANAGER_URL` → `utils.envOverride` (`lib/api.js:133`) is real in 15.32.1.
No test runs real firebase-tools against it: `emulator-secrets.test.sh` only checks that the fake `firebase`
saw the variable. `firebase-cli-from-package.ts:56` keeps any project's own `firebase-tools` pin, so the house
does not control which version reads it. CLAUDE.md treats the analogous `NX_IGNORE_UNSUPPORTED_TS_SETUP` as
needing a CI tripwire. This one guards production credentials and has none. Combined with R2-2 and with
string-form secrets (`secrets: ["KEY"]` in v2 options or `runWith`), which the bundle scan's
`defineSecret(...)` regex does not see, the sink is the only layer for real cases.
**Fix:** add a test that loads the pinned firebase-tools, sets the variable, and asserts that
`secretManagerOrigin()` returns the `.invalid` URL; run it on every firebase-tools bump. At launch, read the
project's installed firebase-tools version and warn when it is outside the verified range. Widen the scan to
string-literal `secrets: [...]` arrays.

### R2-5: the protection only exists when the emulators start through `tools/emulators.sh` (major, read in code)
The placeholder file is written at launch into `dist/` and is wiped by every `nx build functions`
(`deleteOutputPath: true`). That build is the normal edit-and-reload loop: the emulator watches `dist/` and
reloads. After it, every secret-using function crashes (`ENOTFOUND`) until a restart, and sandbox credentials
vanish too. HOUSE.md l.250 asks for a manual restart. A raw `firebase emulators:start` or `emulators:exec` gets
neither the placeholders nor the sink. That includes a CI test job, a developer following Firebase docs, or an
agent.
**Fix (design):** the inert file holds no secret. Emit it as a build output (an esbuild/Nx asset generated from
the declared keys), so every build and every entrypoint carries it. Have `emulators.sh` only overlay sandbox
values. Cache and deploy are unaffected: `functions.ignore` already excludes `*.local`.

### R2-6: `configDir` assumes a firebase-tools version the project may not have (minor, suspected)
`generator.ts:164` sets `configDir`, and the `.env` build asset is removed in the same change (l.579). A project
that keeps its own older pin (`firebase-cli-from-package.ts:56`), where firebase-tools predates `configDir`,
ignores the key and finds no `.env` in `dist`. The deploy then runs without its params: it prompts, fails in CI,
or ships the `default:` values. Not checked against older versions.
**Fix:** check the installed firebase-tools version when writing `configDir`. Keep the asset, or refuse with a
message, below the first version that supports it.

### R2-7: split-seed-applier mislabels a reformatted applier as customised and silently drops real customisations (minor, read in code)
`split-seed-applier.ts:147-160`. The match is exact text modulo trailing whitespace. A world.mjs that `nx format`
or prettier reformatted is called "customised": the warning says the customisation "no longer runs", and the
file keeps a dead `applyWorld`, `localhost:9099` fallbacks and its own `ref`/`at`. For a genuinely customised
applier (one that seeds Storage, for example), `build.mjs`, which is generator-owned, is rewritten to import from
`apply.mjs`. The project's logic stops running and `seed:build` produces a different seed. The only signal is a
`logger.warn` inside the `nx migrate` output.
**Fix:** compare a token- or AST-normalised form (strip whitespace and comments, normalise quotes and trailing
commas). For a truly customised applier, have `build.mjs` prefer `world.applyWorld` when world.mjs exports one,
so behaviour is preserved and the report becomes advice instead of a silent behaviour change.

### R2-8: the seed guard checks presence, not target (nit, read in code)
`seed-apply.mjs.tpl:22-35`. The guard checks only that both host variables are set. When the hosts are given but
`GCLOUD_PROJECT` is not, it writes to `demo-<ws>`, which is invisible to a stack running a real project id under
singleProjectMode. There is no production exposure: plain `http` and `Bearer owner` carry no credential.
`build-seeds.sh` (`emulators:exec --only auth,firestore` on a free offset) and CI are unaffected.
**Fix:** require `GCLOUD_PROJECT` whenever the hosts were supplied by hand rather than by `emulators:exec`.

### R2-9: the rule against arming the sandbox without the user is not always in context (nit)
"Never arm the sandbox without the user" lives only in HOUSE.md, which is read on demand. An unattended agent
never loads it. It belongs in HOUSE.rules.md, gated on the firebase layer.

## Design disputes
- **Inert placeholders at launch instead of at build** (see R2-5). The launch-time design creates the rebuild gap
  and leaves raw-CLI entrypoints unprotected. A build output removes both, and costs nothing because the file
  is not secret.
- **The sandbox "refusal" is security theatre as specified.** Exact-match, same key, same tree only (R2-1).
  Either make it real (parsed values, any key, the main tree's values) or drop the claim and rely on the opt-in
  plus the banner.
- **"Nothing run locally can reach production" overclaims** (R2-3). Under a real project id, credentials and
  `.env` params remain live by design. The headline should match what is enforced, or the enforcement should
  match the headline.
- **Two layers are not independent.** Layer 1 fails silently on a bad key (R2-2) or a string-form secret, and
  layer 2 is an unguarded, undocumented upstream variable (R2-4). "Defence in depth" holds only if each layer is
  tested against real firebase-tools.

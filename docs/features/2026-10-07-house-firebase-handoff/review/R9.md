**Nx ordering.** `executeMigrations` (nx 23.1.0 `dist/src/command-line/migrate/migrate.js:1802`) sorts with
`lt(a,b) ? -1 : 1`. That comparator is inconsistent for equal versions, but V8's TimSort then keeps input order. I
checked this for every floor (0.0.0, 0.23.0, 0.30.0, 0.47.0, 0.49.2) and for the whole file: the order within each
version is the order in migrations.json. So it holds, but it rests on an engine implementation detail and not on any
Nx contract.

## Findings

### R9-1 · HIGH · confidence high: split-serve-follower leaves `dev-stack` without `serve-preflight`
`migrations/0.50.0/split-serve-follower.ts:72-83`. The header at `:7-8` says the composer moves "unchanged … depends on
serve-preflight". The 0.49 composer had no `dependsOn`, and no 0.49 project has a `serve-preflight` target. Only the serve
generator adds them (`generators/serve/generator.ts:113-114`). The per-app generator refreshes only the ONE app the
upgrade resolves (`house.sh _resolve_upgrade_app`). Every other app in a multi-app workspace, and every app in an
UPGRADE_PARTIAL run, is therefore left with no preflight.

- **Failure:** a second `nx serve web --port-offset=N` gets no refusal. It silently attaches to the first stack, which is
  on the other ports. That is the W3 bug this release exists to fix. The ladder also produces two end states: in the
  serve check, `old` (recomposed through the generator) got a preflight and `web` did not.
- **The fixture hides it:** `tools/test-migrations/cases/0.50.0-split-serve-follower.mjs:14-23` builds a composer that
  never shipped, one that already has a preflight.
- **Fix:**
  - The rung adds a frozen `serve-preflight` target (only if it is absent).
  - The rung adds `{target:'serve-preflight', params:'forward'}` to `dev-stack`.
  - The fixture's input becomes the real 0.49 composer.
  - Correct the header.

### R9-2 · MEDIUM · confidence high: recompose runs after lint-house-apps, so a recomposed app is never linted
recompose (13) runs after lint-house-apps (8). An e76c12a app only becomes a house app (a composer) inside rung 13, so
rung 8 skipped it.

- **Failure:** in the serve check, `old` got no line at all in run 1 and was reported only on run 2. Real ladders run
  once, so it stays unlinted. No `platform:` tag means no report either. This also contradicts the "either order holds"
  comment at `lint-house-apps.ts:222`.
- **Fix:** move recompose before stack-owned-dev-processes in migrations.json (file order is preserved, see above), and
  add a cross-rung case.

### R9-3 · MEDIUM · confidence medium: read-functions-params-in-place relies on the generator for `configDir`
`read-functions-params-in-place.ts:60-65` removes the `.env` asset. The thing that replaces it, `firebase.json
functions[].configDir`, is written only by the firebase-emulators generator (`generator.ts:299`). The migration commits
on its own (`--create-commits`).

- **Failure:** the generator step fails or is not reached, or someone runs a bare `nx migrate --run-migrations`. The
  next `functions:deploy` then ships with no `.env` params, silently.
- This is the same class this release fixed for route-emulators (`writeFirebaseClientGlue`).
- **Fix:** the rung sets `configDir` on the matching functions block itself, in place. Alternatively, it removes the
  asset only when `configDir` is already present.

### R9-4 · MEDIUM (harness) · confidence high: the no-op honesty check almost never fires
`tools/test-migrations/run.mjs:58` `CLAIMS_A_CHANGE` is case-sensitive and matches capitalised verbs only. **0 of the 37
info lines** the 0.50 ladder logged would match: the rungs say "removed", "wrote", "moved", "refreshed", "corrected",
"is no longer continuous".

- **Failure:** a rung that is a no-op on re-run but still logs "removed X" passes the check.
- **Fix:** add the `/i` flag and the verbs the rungs actually use. Better: fail on any info line from a second run that
  changed nothing, with an explicit allowlist.

### R9-5 · LOW (harness) · confidence high: a `diverges` shape's `expect` sees other runs' log lines
`run.mjs:138` passes `log.lines` to a diverging shape's `expect`, but the log is never reset between the canonical run
and the historical runs.

- **Failure:** an assertion like "reported X" passes on the canonical run's line. No case uses `diverges` yet, so this
  is latent.
- **Fix:** call `log.reset()` inside `run()` and pass that run's lines.

### R9-6 · LOW · confidence high: the new CLAUDE.md `historicalShapes` rule is not applied to this release's rungs
Only 2 of the 18 rungs declare shapes. These skip on a single marker and have none:

- split-serve-follower: `serve.executor` is the composer
- stack-owned: `continuous`
- split-seed-applier: the banner

R9-1 is exactly the "fixture models a shape that never shipped" failure the rule exists to catch.
**Fix:** take the shapes from git with the sha named, starting with the 0.49 composer.

### R9-7 · LOW · confidence high: descriptions and report lines that are wrong
- **recompose description:** says "serve composer". It actually writes `dev-stack` + the `serve` follower +
  `serve-preflight`, and adds the dev.json `install` step.
- **lint-house-apps description:** omits the conversion of `functions:lint`.
- **declare-node-version `:36`, `:42`:** says "the next upgrade will refuse it / moves the container". It is THIS
  run's generators that do it. `declaredNodeMajor` throws (`_utils/node-version.ts:27`), so the current upgrade fails
  after the migrations have already been committed.
- **declare-node-version `:29`:** its regex `^v?(\d+)` accepts `.nvmrc` values that the generator's
  `^v?(\d+)(\.\d+){0,2}$` refuses, so the rung stays silent where the generator then throws.
- **Fix:** reuse the generator's regex, and say "this upgrade will stop at the generators".

### R9-8 · LOW · confidence medium: the firewall tags tooling projects `platform:shared`
In the combined run, close-the-platform-firewall tagged the emulator-suite project `firebase` `platform:shared`
("nothing in it is bound to a platform"). `lint-house-apps` (`:201-203`) calls such projects tooling. The tag claims
"isomorphic code" for scripts.

- **Fix:** classify only projects where `holdsCode` is true.

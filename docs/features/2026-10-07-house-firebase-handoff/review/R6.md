# R6 — adversarial review: CI deploy layer, setup-gcp.sh, structured `deploys`

Reviewer: R6 (read-only on code). Base: `git merge-base HEAD origin/development` (4f01d00). Scope: `ci` layer,
`LayerDescriptor.ciDeploy`, `generators/ci/*`, `setup-gcp.sh.tpl`, structured `deploys` in the branch-and-release
engine, `evidence --app-hosting`, `house-branches.sh`, payload `branch-model.ts`, migration `0.50.0/deploys-object-form`.

## How it was checked (observed, not read off the notes)

- Engine: `branches.mjs expand --preset gitflow --maintained`, then `ci` bindings added to `stages[0]`, `releases`,
  `hotfixes` → `validate` says **valid**; `write` projects all three (`main`, `release/*`, `hotfix/*/*`).
- Generator: compiled payload (`tools/test-support/payload.mjs`) run on that projection (scratch script
  `scratchpad/r6/gen.mjs`); the rendered `deploy.yml` and `setup-gcp.sh` are quoted below.
- `setup-gcp.sh --dry-run` and `--rollback --dry-run` against a fixture repo (functions + secrets + firestore + storage),
  with and without `node` on PATH. `bash -n` clean (no shellcheck/actionlint on this box).
- Nx 23.1.0: `run-many -t deploy --project=prod --non-interactive` forwards both flags to the target (works as W5 assumed).
- `node tools/test-branches/run.mjs`: 51/51 pass. The tests do not cover any finding below.

## Findings (ranked)

### R6-1 — HIGH (confidence high) — a `ci` binding on `hotfixes` deploys unreviewed, unprotected branches to production, and the WIF condition trusts them
`model.mjs:333` validates `hotfixes.deploys` like any other holder; `model.mjs:423` projects it as a `pattern`;
`generators/ci/generator.ts:156-191` wires it. Observed output:
```
push.branches: 'main', 'release/*', 'hotfix/*/*'
CEL: … || assertion.ref.matches('^refs/heads/hotfix/[^/]+/[^/]+$')
```
Hotfix branches are WORK branches (`projection.protectedPatterns` holds only the release glob). **Scenario:** anyone
with push access pushes `hotfix/main/x` → the workflow resolves `production` → the WIF condition accepts the ref →
arbitrary code is deployed to production with no review. The script's "optionally restrict the environment to its
branches" prints the same glob, so even that does not help.
**Fix:** the engine refuses `ci` on any holder whose lines are not protected (hotfixes today; check against
`protected` ∪ `protectedPatterns`), and the generator refuses any binding whose `line` is not protected in the
projection (defence in depth for a hand-edited projection).

### R6-2 — HIGH (confidence medium) — the SA binding is POOL-scoped, so any other provider in an adopted `github-actions` pool bypasses the environment + ref condition
`setup-gcp.sh.tpl:146` `PRINCIPAL=principalSet://…/workloadIdentityPools/$POOL/attribute.repository/$REPO`;
`:171-176` adopts an existing pool named `github-actions` ("= pool exists"); `:198` grants `workloadIdentityUser`.
A principalSet on a pool attribute matches tokens exchanged through **every** provider in the pool. **Scenario:** the
consumer this feature comes from already deploys with WIF (handoff B3); if their pool is the very common
`github-actions` with a provider whose condition is repo-only (or owner-only), a token from ANY branch/workflow of the
repo, through that provider, impersonates `github-deployer` and gets every role granted here. The house's
environment/ref condition is decoration. Same mechanism lets `gh-staging` mint the production SA when both
environments share a GCP project.
**Fix:** a pool the house owns per environment (`house-<env>`), or map a house-only attribute (e.g.
`attribute.house_env=assertion.environment` on this provider only) and bind
`principalSet://…/attribute.house_env/<env>`; refuse (or report) a pre-existing pool holding providers the house did
not create.

### R6-3 — HIGH (confidence high) — `--rollback` removes grants it cannot know it made, including a runtime-critical one
`setup-gcp.sh.tpl:154-164`. It keeps no record of what it added; it removes whatever the CURRENT `firebase.json`
implies. Observed dry run removes `roles/secretmanager.secretAccessor` from `<n>-compute@developer` project-wide
(`:158`) and deletes `github-deployer` (`:159`).
**Scenarios:** (a) the project granted the compute SA secret access before (common — `functions:secrets:set` users,
or a hand-made setup) → rollback strips it → every deployed function using a secret fails at run time in production.
(b) Two environments in one GCP project share the SA → rolling back one deletes the other's identity. (c) A
pre-existing SA named `github-deployer` (generic name) is adopted on setup and deleted on rollback.
(d) Roles granted for a `firebase.json` feature since removed are never revoked.
**Fix:** record what the run actually created or added (a labelled SA description, or a state file printed for the
human to commit) and roll back only that; never touch the runtime SA's bindings in rollback unless recorded; refuse
to delete an SA still referenced by another environment's provider.

### R6-4 — MEDIUM (confidence high) — one environment bound to several lines: per-branch `affected` bases desync the environment, and the runs race
`generator.ts:177-181` merges several lines into one environment (`existing.branches.push`); `workflow.ts:88-90` makes
concurrency per **ref**; `nx-set-shas` takes the base per **branch**. **Scenario:** `main` and `release/*` both bind
`production` (the projection above). A push to `release/1.2` deploys `functions` from 1.2; the next push to `main`
touches only rules → `functions` stays at 1.2 code, which matches no branch. Two pushes at once deploy into the same
Firebase project at the same time. With `maintained` releases, a fix on `release/1.0` rolls production back to 1.0.
**Fix:** refuse a second line on an environment (and `ci` on a maintained release pattern) unless every run is
`run-many`; at minimum set `concurrency.group: deploy-<environment>` (resolved in job 1, so put it on the `deploy` job).

### R6-5 — MEDIUM (confidence high) — every step of the deploy job can mint a production OIDC token, and third-party actions are tag-pinned
`workflow.ts:11-15`, `firebase-provider.ts:171` (`@v4`, `@v2` tags); `workflow.ts:121-125` gives `id-token: write` to
the whole job, which also runs `yarn install` (every dependency's install scripts) and `nrwl/nx-set-shas`. Any step
can call `ACTIONS_ID_TOKEN_REQUEST_URL` and exchange the token through WIF. **Scenario:** a hijacked `v4` tag of a
third-party action, or a compromised postinstall in the lockfile, deploys or exfiltrates with production's SA.
**Fix:** pin third-party actions to full SHAs (comment the tag); move install + nx-set-shas + build into a job without
`id-token`, hand base/head as outputs, and keep `id-token: write` on a job that runs only the auth + deploy steps.

### R6-6 — MEDIUM (confidence high) — removing a binding orphans a live cloud identity and deletes the tool that would clean it up
`generator.ts:82-85` writes `setup-gcp.sh` only while an environment is bound; `:98-103` then deletes it;
`:108-115` prints HUMAN_STEP only for environments still bound. **Scenario:** a human removes `staging`'s `ci`
binding → the upgrade deletes `tools/setup-gcp.sh`, says nothing about the cloud, and the WIF provider + SA with its
roles keep trusting `development` indefinitely. The rollback script that would undo it is gone.
**Fix:** diff `previous.cloud` against the current set; for each vanished environment print a HUMAN_STEP to run
`--rollback --environment <env>`, and keep rendering that environment's row (marked "retired") until the marker
records the rollback happened.

### R6-7 — MEDIUM (confidence medium) — secrets: the project-wide grant does not stop the Firebase CLI from calling `secrets.setIamPolicy`
`setup-gcp.sh.tpl:220-225` grants `secretAccessor` project-wide to the compute SA "so a deploy … never has to change
IAM". firebase-tools' `ensureSecretAccess` → `ensureServiceAgentRole` reads the **secret's** policy (where a
project-level grant does not appear) and calls `setIamPolicy` for each new secret/SA pair. The deployer has only
`secretmanager.viewer`. **Scenario:** the first CI deploy of a function with a new `defineSecret` fails with 403. The
grant itself also widens access: the compute default SA (every Cloud Run/GCE workload in the project) can now read
every secret. Not verified against a real project (W6 also says the role set is unverified).
**Fix:** grant `secretAccessor` per secret (or grant the deployer `roles/secretmanager.admin` scoped by an IAM
condition on the secret-name prefix), and verify on a throwaway project before release. Same unverified risk: new
HTTPS functions — firebase-tools' `checkHttpIam` tests `cloudfunctions.functions.setIamPolicy`, which neither
`cloudfunctions.developer` nor `run.admin` has.

### R6-8 — MEDIUM (confidence medium) — the WIF condition does not pin the workflow or the event
`setup-gcp.sh.tpl:147`: `repository && environment && ref`. A `pull_request_target` workflow on `main` (ref claim
= `refs/heads/main`) that declares `environment: production` passes. So does any other workflow file on a bound
branch. `assertion.repository` is a mutable name: if the repo is renamed or transferred, someone can recreate it.
**Fix:** add `assertion.workflow_ref.startsWith('<owner/repo>/.github/workflows/deploy.yml@')` (or `job_workflow_ref`),
`assertion.event_name in ['push','workflow_dispatch']`, and `assertion.repository_id == '<id>'` (from `gh api`).

### R6-9 — LOW-MEDIUM (confidence high) — setup-gcp silently degrades without `node`
`:78` and `:90-103` swallow `node` failures. Without node: `USES` is empty (no functions/rules roles are granted, and
it prints "nothing the CLI needs roles for"), and `PROJECT` falls back to the **alias** (`prod`). Observed with node
off PATH. The header invites "any terminal". **Scenario:** the human runs it on a laptop without node, it reports
success, and the first deploy fails with 403 (or it targets a project whose id happens to equal the alias).
**Fix:** `command -v node || die`; die when `.firebaserc` exists but the alias does not resolve.

### R6-10 — LOW (confidence high) — "converges the role set" is false
`:21-22` claims re-running converges roles; `:200-204` only adds. Roles granted for a feature since dropped from
`firebase.json` stay. **Fix:** fix the claim, or converge using a recorded set (see R6-3).

### R6-11 — LOW (confidence high) — the "lands" remedy is claimed for any working copy without a string `deploys`
`resolve.mjs:130`: `check(local).outdated.length === 0` is also true when the branch's copy predates the notes, has
no `deploys` at all, or carries other errors. **Scenario:** a branch cut before a note was added is told "it resolves
when this branch lands — nothing else to do". Landing does not touch the file, so the notice stays wrong.
**Fix:** `lands` only when the local copy equals `rewrite(inForce)` at every outdated path (same note text, object form).

### R6-12 — LOW — the two resolvers now disagree on more inputs
Node treats any `deploys` error (now validated on `integration` too, where nothing was checked before; e.g. a
malformed `ci`) as **unreadable**. `house-branches.sh` reads only the projection, so it says **declared**, and the
`ci` generator renders a workflow from a model the engine refuses. The divergence existed before, but this change
widens it. **Fix:** have the engine's `write` be the only way a binding reaches the projection (already true), and
have house.sh prefer `branches.mjs status --json` when the workflow plugin is reachable, or document the gap in
CONTRACT.md.

### R6-13 — LOW — `evidence --app-hosting` robustness
`evidence.mjs:353` puts the bearer token in curl's argv, where `ps` shows it (use `-H @file` or node `fetch`). Any
non-zero `firebase` exit (API disabled, permission denied) is reported as "not installed or not logged in". A
`pattern` binding (`release/*`) is compared with `!==` against a concrete `codebaseBranch`, so it always reports drift.

### R6-14 — LOW — glob semantics differ across the three matchers
GitHub's filter and the CEL (`[^/]+`) do not let `*` cross `/`; the bash `case` arm in the resolve job does. A
`workflow_dispatch` on `release/a/b` resolves to an environment and then fails at auth with a cryptic WIF error,
not the friendly "no binding" one. **Fix:** in bash, use `extglob` or reject a ref containing more `/` than the
pattern does.

## Design disputes

- **D1 — "stack-agnostic" is false in practice.** The provider's args (`--project=<alias> --non-interactive`) reach
  EVERY project's `deploy` target (`workflow.ts:146-148`). A user's own `deploy` (Vercel, a docs site, `gh-pages`)
  receives `--project=prod` and may interpret it (Vercel does). The ">1 provider → throw" guard admits that the
  abstraction cannot compose. Fix: scope args by project, for example a `deploy` target that reads
  `DEPLOY_<PROVIDER>_TARGET` from the env instead of argv. Then the ci layer really is agnostic and N providers compose.
- **D2 — over-engineered for one provider, under-engineered where it matters.** `CiDeployProvider.variables` is
  consumed by nothing (`descriptor.ts:203`). The variable names are hard-coded in 4 files (the provider, the
  setup-gcp template, firebase-deploy.mjs.tpl, HOUSE.md.tpl). There is a provider registry but no CI-host abstraction,
  although U4 proposed "detected from the origin remote". Meanwhile the parts with security weight (pool ownership,
  rollback state, protected-line check) are thin. Either delete `variables`, or make it the single source the four
  files render from.
- **D3 — a GitHub environment is the right unit for the provider condition, but GitHub enforces nothing here.** The
  house leaves the environment's deployment-branch policy "optional" and never sets required reviewers. Production
  should at least get `gh api … deployment_branch_policy` with the protected lines, printed as a non-optional step.
- **D4 — the format migration.** CLAUDE.md now carves out "a format-only migration the user explicitly approved".
  The rewrite is meaning-preserving and lands through the human merge, so it is defensible. But the exemption is
  "approved by this repo's owner, applied to every consumer's model". The engine already refuses
  `describe`/`verify` until the rewrite lands, so the migration is the only path that does not need a human. Keep
  the precedent explicitly singular, as CLAUDE.md does, and test that the migration never touches `projection`.

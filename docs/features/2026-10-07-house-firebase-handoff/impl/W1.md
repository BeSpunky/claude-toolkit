## What changed

- **One versions source.** `nx-tools/src/generators/_utils/versions.ts` holds every house pin: `PLAYWRIGHT_VERSION` (moved here from `_utils/playwright.ts`), `FIREBASE_TOOLS_VERSION` 15.32.1, `FIREBASE_ADMIN_VERSION` / `FIREBASE_FUNCTIONS_VERSION`, `TYPESCRIPT_UTILS_VERSION` 0.1.0-alpha.0 (the only one published), `HOUSE_NODE_MAJOR` 24 (a seed only).
- **Derived data, never typed by hand.** `_utils/firebase-compat.ts` is GENERATED by `tools/firebase-compat/project.mjs [--write]` from npm: per Angular major 17…22 the newest stable `@angular/fire` (exact) with its own `dependencies.firebase`, peer `@angular/core`, `minAngular`, and whether its optional `firebase-tools` peer admits the house pin; else the newest prerelease (named in the refusal). Plus Cloud Functions' GA Node runtimes read from the pinned firebase-tools tarball (20, 22, 24). Check mode re-asks npm and fails on drift — wired into `.github/workflows/migration-tests.yml` beside playwright-deps (it WILL go red when upstream ships, e.g. the first stable @angular/fire for Angular 21: that is the staleness alarm). Offline consistency (table projected from the pinned firebase-tools; seed Node is a GA runtime) is in `tools/test-layers`.
- **The seam.** `_utils/dependencies.ts` `declareDependencies(tree, by, deps, devDeps)` — adds only what the project lacks, and THROWS on a floating spec (only exact / `^x.y.z` / `~x.y.z` pass). Every generator now goes through it (playwright, navigation-core, adopt-extracted, firebase-emulators, the Angular firebase client).
- **Class guard.** `tools/test-generators/cases/versions.mjs`: a static scan fails on `addDependenciesToPackageJson` outside the seam or a quoted `'latest'`/`'next'` anywhere in the payload source (migrations excluded); plus runtime cases for the seam, the Angular pairing, the refusals, `.nvmrc`, functions runtime.
- **@angular/fire follows Angular, firebase follows @angular/fire** (`adapters/angular/angularfire.ts`): Angular read from `node_modules/@angular/core`, else the declared range. Majors with no stable release (21, 22), newer than the table, older than 17, or below the release's `minAngular` → **refuse** with what is true and the choices (the exact prerelease + its firebase range; the newest Angular with a stable release; or declare both by hand — the generator keeps what is declared). Both declared → nothing written, but a `firebase` that disagrees with the INSTALLED @angular/fire's own range is warned on every upgrade (the two-SDK state). The per-app step therefore no longer re-adds `latest`.
- **Floats fixed:** navigation-core (`@bespunky/typescript-utils`), adopt-extracted (default = `^<version extract-tool recorded>`, else it asks — schema default `latest` removed, docs/reusable-tool-extraction.md updated), firebase-emulators `@nx/esbuild` (declared pinned `nx`, else installed nx, else refuse).
- **Node is the project's `.nvmrc`** (`_utils/node-version.ts`): `projectNodeMajor` reads it (`22`, `v22`, `22.11.0`; an alias like `lts/*` is refused with the fix) or seeds `HOUSE_NODE_MAJOR` once, logging it. The devcontainer generator reads it; its `nodeMajor` option, `PlanContext.nodeMajor`, `cli.js plan --node-major` and house.sh's host-Node `MAJOR` are gone (the Docker-fallback `MAJOR` remains — it only picks the image the generators RUN in, now commented as such). Functions `engines.node` is rendered from `.nvmrc` (nearest GA runtime below it, with a warning, when Functions lacks it), firebase-admin/functions from versions.ts, `@types/node` fallback follows the runtime. Every run names a functions `engines.node` that disagrees with `.nvmrc` — never rewrites it.
- **firebase-tools is a pinned devDependency**; the `firebase-cli` devcontainer feature is gone from `layers/firebase.ts`. `firebase` resolves via `node_modules/.bin`: on the container PATH (node layer) and in every Nx run-commands target (verified in nx 23.1.0 `running-tasks.js` `processEnv` → npm-run-path from cwd = workspaceRoot) — so `firebase:emulators`, `functions:deploy`, `push-secrets`, `seed:build`, and the dev engine (which runs `nx run firebase:emulators`) all get the pinned CLI.

## Follow-ups (orchestrator decisions, 2026-10-07)

### 1. `new` + Angular + Firebase creates at the newest Angular @angular/fire supports

- New optional port `FirebaseClientPort.chooseFrameworkVersion(tree)` (`adapters/stack-adapter.ts`); the house `app` generator calls it BEFORE `stack.apps.create` when the app will wear firebase (`--layers` / detected / `--firebase`). It is a creation-time choice: the Angular port (`angularfire.ts` `pinAngularForFirebase`) is a no-op when `@angular/core` is already declared — existing projects keep their Angular and still get the refusal with its choices (add-layer firebase / upgrade).
- Mechanism (read from @nx/angular 23.3.0's source, not guessed): `nx add @nx/angular`'s init adds only `@angular-devkit/core`; @nx/angular's generators then take EVERY Angular package version from the DECLARED `@angular/core` major (`versions(tree)` → `getPkgVersionsForAngularMajorVersion` → `backwardCompatibleVersions[major]`; `supportedVersions` = [22, 21, 20]). So the port declares `@angular/core` at @nx/angular's own range for the newest major that has a stable @angular/fire AND that @nx/angular supports (today `~20.3.0`), realigns the `@angular-devkit/core` init added at 22, and logs: `Angular 20 — the newest major @angular/fire supports; upgrade when AngularFire ships 21+`. The table is not on @nx/angular's exports map (hidden since Nx 23), so it is read from `dist/src/utils/` (fallback `src/utils/`) by path; if Nx moves it, the error names the paths and the cause and says to declare `@angular/core` by hand.
- No house.sh change: the existing `new` sequence (`nx add @nx/angular` → `nx g @bespunky/nx-tools:app --layers=$ENSURED`) already hands the app generator the ensure set.
- Tests: `versions.mjs` — a fresh workspace (real dir, stand-in @nx/angular in the 23.3 layout) gets `~20.3.0` + realigned devkit + the line; an existing `~21.2.0` stays. Checked against the REAL @nx/angular 23.3.0 files: `supportedVersions` [22,21,20], `backwardCompatibleVersions[20].angularVersion` `~20.3.0`, latest `~22.1.0`.
- NOT run: a real `house.sh new --preset=angular --firebase` end to end (network, minutes). One risk to watch there: node_modules holds @angular-devkit/core 22 (installed by `nx add`) while the app generator writes Angular 20 deps; the generator's install task realigns it.

### 2. gcloud pinned, in the image

- `GCLOUD_CLI_VERSION = '588.0.0-0'` (versions.ts; Google's apt version string, present for amd64 + arm64). The firebase layer contributes `google-cloud-cli=588.0.0-0` as an `osPackages` group with a new `repository` field (`AptRepository`: id, key URL, deb source). The jajera feature is gone.
- Installer infrastructure (`house.packages.sh.tpl`): `HOUSE_REPOSITORIES` (validated by the composer), added the modern way — key → `gpg --dearmor` → `/usr/share/keyrings/<id>.gpg`, `deb [signed-by=…]` in `/etc/apt/sources.list.d/<id>.list` (no apt-key), bootstrapping curl/gnupg/ca-certificates from Debian if missing; `name=version` pins accepted (name + version validated) and "present" means installed AT that version, so a moved pin reinstalls. Still one cached image layer; post-create runs the same installer (adopted images).
- Migration `0.50.0/gcloud-cli-from-image` (fixture case): removes the feature + comment + lock pin where `houseWrote()`, reports a project-added one. The feature-retiring logic is now shared: `retireHouseFeature()` in `_utils/devcontainer-feature.ts` (firebase-cli-from-package uses it too).

- Verified HERE (Debian 13 devcontainer, non-root + sudo = the post-create path): the rendered installer added the repository, installed `google-cloud-cli 588.0.0-0` (`/usr/bin/gcloud`, `Google Cloud SDK 588.0.0`), a second run said "all present"; `gcloud info` → global config dir `/home/node/.config/gcloud` (also read in googlecloudsdk/core/config.py) — the persisted ~/.config.

## B1 — route-emulators-through-origin relies on a regeneration that an UPGRADE_PARTIAL run skips

- **Shape.** Any 0.49 Firebase app with `proxied: true` (the template default since 8312546 for auth, eddc392 for
  functions) whose per-app steps an upgrade cannot resolve (`house.sh` sets `_UPGRADE_PARTIAL=1`). The 0.49 owned
  client (a556912~1 `firebase-auth.config.ts.tpl:52`): `const proxied = (e as { proxied?: boolean }).proxied;` — it
  compiles against the new interface (the cast), so nothing breaks loudly.
- **Impact.** The rung removes `proxied` (`:144`), the stale client reads `undefined`, and auth + callables dial
  :9099/:5001 directly until some later full upgrade — the forwarded-port hang `proxied` was introduced to fix. The
  repo's own rule ("carrying data means clearing the original … UPGRADE_PARTIAL is exactly the run where the stale
  copy survives") names this case.
- **Fix.** Make the rung self-sufficient like `split-seed-applier` (`writeSeedTooling`) and `0.33.0/split-firebase-service-providers`:
  for every app it edits, write the owned set itself — `writeFirebaseConfigs(tree, root)` plus the app's
  `proxy.conf.mjs` (the writer at `adapters/angular/firebase-client.ts:63-66`, extracted to a shared function). Add a
  fixture: stock 0.49 bundle + 0.49 `firebase-auth.config.ts`, run the rung alone, assert the client no longer reads
  `proxied`.

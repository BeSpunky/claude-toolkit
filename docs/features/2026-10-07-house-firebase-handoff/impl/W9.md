# W9 — `deploys` is object-only; a 0.50.0 migration moves the string form

Branch `feat/house-firebase-handoff--w9`. The user's decision (verbatim): *"object-only, no compat. Migration should
take care of shifting to the new format"* — answering W6's open question about keeping the string note.

## What was built

- **Engine (workflow plugin).** `model.mjs` gains `check(m) → { errors, outdated }`; `validate` = both. A bare-string
  `deploys` (any holder: integration, stages, releases, hotfixes, tags) is an **outdated** problem, not an error, with
  a self-fixing message: the field, the exact replacement `"deploys": { "note": "<their text>" }`, and that the house
  upgrade migrates it automatically. `deploysText` lost its string branch.
- **Per command, on a declaration still carrying a string:**
  - `status` — reads on (`declared`, exit 0); the fix is in `notes` (stderr / `--json`), so every skill start sees it.
  - `plan` — reads on, the note printed: it reads names and moves only, which the format leaves intact.
  - `describe`, `verify` — refuse (exit 1), printing the rewrite and "propose it to the human, or run the house upgrade".
  - `validate`, `write`, `verify --proposed` — refuse (exit 1) with the same message.
  - **Why `status` keeps working**: the resolver (`resolve.mjs`) used to run full validation on the copy in force, so
    the string would have made the model `unreadable` (refuse to act) in every consumer until they upgrade. A note
    binds nothing, so the projection is identical before and after the rewrite (`deployBindings` ignores note-only) —
    the resolver now treats outdated-only problems as declared + notes. The bash resolver (`house-branches.sh`) only
    ever read the projection, so the two resolvers agree.
- **Skill text.** SKILL.md: `deploys` is always an object; on the outdated note, Claude proposes the rewrite to the
  human (or the upgrade) and lands it through the normal flow. `choosing-a-branch-model.md` and the house-doc
  template now speak of a `note` field, never a string.
- **Migration `0.50.0/deploys-object-form`** (layer `nx`). jsonc-parser edits at the known `deploys` paths only;
  result byte-identical to what `branches.mjs write` writes (indent and EOL detected). Projection untouched — provably
  unchanged, asserted in the fixture against the engine's own `project()` and `check()`. Not-JSON → left + reported.
  Header states it is a user-approved format shift, not a model change; CLAUDE.md and `branch-model.ts` narrowed.
- **Which copy.** The migration edits the tree it runs in (the upgrade's branch); the copy in force is the integration
  line's, reached when that branch lands. A tree without the file (branch predating the declaration) has nothing to
  rewrite — a Tree has no git — and `status` keeps naming the fix until an upgrade runs from a tree carrying it.

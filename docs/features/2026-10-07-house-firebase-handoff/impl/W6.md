# W6 — CI deploy layer, setup-gcp.sh, structured `deploys` (B3, B4, C3)

Branch `feat/house-firebase-handoff--w6`. Payload version set to 0.50.0 (shared with the other units).

## What was built

- **Structured `deploys` (workflow plugin, C3).** `deploys` on any line kind (integration now too, for trunk) is either a
  **note** (string — documentation, as before) or a **binding** `{ note?, ci?: { environment, providers: { <id>: <target> } },
  appHosting?: [{ project, backend }] }`. Validated in `model.mjs`; projected flat as `projection.deploys`
  (`[{ kind: line|pattern|tag, line, ci?, appHosting? }]`) **only when something is bound**, so every existing declaration
  projects exactly as before (no invariant-5 drift) and the projection schema stays major 1 (an additive optional key).
  `describe` renders both forms. `write` stays the only writer.
- **`evidence --app-hosting` (opt-in).** Per `.firebaserc` project: `firebase apphosting:backends:list --json` (project-local
  CLI first) → region, linked repository (none = local-source deploys), root directory, environment. The live branch is the
  backend's traffic `rolloutPolicy.codebaseBranch`, which no firebase command prints — read from the API with a `gcloud`
  token when available, else its own `unobservable` fact. On a declared model it emits `drift` facts (declared backend
  missing / unlinked / on another branch; linked backend declared nowhere). No CLI or no login → `unobservable`, never an error.
- **`ci` layer (house, B3).** Opt-in (no preset), requires `nx`, registered last, detected by `.bespunky/ci.json`.
  Generator `ci` renders an OWNED `.github/workflows/deploy.yml` from `projection.deploys` `ci` bindings (resolve job maps
  `GITHUB_REF_NAME` → environment + provider args; deploy job in that GitHub environment, `nx-set-shas` base = last
  successful run, `affected -t deploy` / dispatch `scope=all` → `run-many`, concurrency per ref never cancelled, Node from
  `.nvmrc`, frozen install per package manager, `./nx` on the wrapper host). Args passed as W5's contract:
  `--project=<alias> --non-interactive` (no `--`). Tag bindings are reported, not wired. Undeclared / unbound → no workflow,
  `pending` in the marker says why. Never overwrites a file the house did not write; writes no workflow when another
  workflow already deploys (`firebase deploy`, `-t deploy`, `nx run x:deploy`) — names it and the switch. Removes owned
  files a model change no longer calls for.
- **Deploy providers are a layer contribution** (`LayerDescriptor.ciDeploy`: deployArgs, authSteps, variables, files,
  humanStep). Firebase contributes keyless WIF (`google-github-actions/auth@v2`, vars `GCP_WORKLOAD_IDENTITY_PROVIDER` /
  `GCP_DEPLOY_SERVICE_ACCOUNT` per GitHub environment, a friendly failure step when unset) and `tools/setup-gcp.sh`.
  Two args-contributing providers → the generator throws (their args would reach each other's targets); a per-provider
  run is the redesign when a second provider arrives. App Hosting is never deployed by CI.
- **`tools/setup-gcp.sh` (B4).** Owned, rendered per environment (target + branches + CEL ref condition from the model);
  repo from `origin`, project from `.firebaserc`. Idempotent: describe-before-create, undelete of soft-deleted pool/provider,
  `update-oidc` converges the condition. Provider condition = repository AND environment AND the bound refs. Roles derived
  from `firebase.json` at run time, each justified inline. `--dry-run` (reads still run when gcloud is authed, so it shows
  only what would change), `--rollback` (keeps the shared pool, says so). Ends with the `gh` commands to create the
  environment and set both variables. Header, HOUSE.md, HOUSE.rules.md (ci+firebase), the `new` skill and upgrade.md all say
  the HUMAN runs it with `!`. The generator records what it rendered (`cloud` in the marker) and prints
  `HUMAN_STEP: ! bash tools/setup-gcp.sh --environment <env> …` only when that changed.
- **Docs.** HOUSE.md: the *Deploy bindings* paragraph now renders the structured bindings as a table and states both App
  Hosting modes (GitHub-linked = an `appHosting` binding; local-source = bound to no line), pointing at
  `evidence --app-hosting` and W7's `bespunky-house:firebase-app-hosting` skill; new *Continuous deployment (CI)* section.
  branch-and-release SKILL + references (proposal table from evidence; drift; App Hosting re-check). README layer row; tips.

## Decisions taken here (challengeable)

- Kept the string form of `deploys` as a **note**, not a deprecated alias: it carries information no binding expresses
  (a manual ritual, a Vercel preview), and making it invalid would turn every existing declaration with prose into
  `unreadable` — which nothing may repair without a human. **Open question for the user** (house rule: compat is asked).
- `ci.environment` is explicit (a GitHub environment) rather than derived from the Firebase alias — environments carry the
  per-environment cloud identity and protection rules, and a second provider needs the same name.
- Persistence audit: the `ci` layer adds nothing to the container (gcloud/firebase are the firebase layer's; their logins
  live under `~/.config`, already persisted). Nothing to keep.
- Migration: none owed — a new, explicitly ensured layer; HOUSE docs are owned and regenerated.

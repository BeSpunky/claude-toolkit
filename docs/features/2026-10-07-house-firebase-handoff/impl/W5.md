# W5 — declared deploys (B1, B2, B6) + house targets as shared ground

Branch `feat/house-firebase-handoff--w5`. Payload `0.50.0`.

## What shipped

- **House targets merge three-way** (`_utils/house-targets.ts`, called by `ensureHouseProject`). Base = `.bespunky/house-targets.json`, a committed record of what the house last wrote per house project. Project additions and edits inside a house target survive upgrades; a key both sides changed takes the house's value and is **reported** (`logger.warn`, with the replaced value); a key the house drops and nobody touched is removed; `inputs`/`outputs`/`dependsOn` merge as sets. No record (every project's first 0.50 upgrade) → house-declared keys win and differences are reported as "cannot tell an edit from an older house value"; undeclared keys are kept. Affects every house project (functions, firebase, shared-browser, worktree-domains).
- **`functions:deploy`**: `dependsOn: [build, lint?]`, `inputs: [default, ^default, {workspaceRoot}/firebase.json, {workspaceRoot}/.firebaserc]`, `cache: false`, `parallelism: false`; command unchanged. firebase.json `functions[0].predeploy` removed (the block is re-asserted whole every run, so existing projects lose it on upgrade — no migration).
- **`firebase:deploy`** (new): `node tools/firebase-deploy-rules.mjs` (owned) — derives `--only` from firebase.json at run time (firestore rules → `firestore:rules`, indexes → `firestore:indexes`, storage rules → `storage`; objects or arrays), refuses a declared-but-missing file, skips a file carrying the `bespunky:house-seed` marker, and when nothing is declared exits 0 with the adoption recipe (`npx firebase init firestore storage -P <alias>` — verified in firebase-tools 15.32.1 source: `init firestore`/`init storage` download the live rules and indexes). Inputs: default + root Firebase files + declared rules files outside `firebase/` + the conventional root locations.
- **`--seedRules`** (layer passes it only when firebase is ENSURED): deny-all marked `firebase/firestore.rules`, `firebase/storage.rules`, empty `firebase/firestore.indexes.json`, declared in firebase.json — per service, never over a declaration, never over a loose root file (reported).
- Docs: HOUSE.md.tpl *Deploying the backend* (firebase section, after Cloud Functions) + a *House targets are yours to extend* bullet under *Working with Nx*; new-skill text; three tips.

## Verified (real Nx 23.1, scratch workspace)

- `nx affected|run-many -t deploy --project=<alias> --non-interactive` forwards both args to every deploy command; `dependsOn` tasks do NOT receive them.
- `nx run p:deploy --project=x` → Nx itself consumes `--project` ("Cannot find project"); `-P <alias>`, `-- --project=…` and `--args=…` pass through. Docs say `-P` for `nx run`.
- `parallelism: false` (schema + tasks-schedule.js): the two deploys ran serially.
- A `{workspaceRoot}/firestore.rules` input marks only its project affected.

## Migrations

None owed by W5 — considered: the predeploy removal rides the owned `functions` block; target changes ride the owned targets; the record is written by the generator. **Hazard for other units:** at the 0.50 upgrade there is no record yet, so a key another unit DROPS from an owned target survives (kept as "undeclared"); such a drop needs a migration this release.

## E4 — the platform firewall fails closed

Facts checked (`@nx/eslint-plugin@23.3.0`, packed): `depConstraints` carry NO custom message — the lint text is
Nx's fixed `A project tagged with "{{sourceTag}}" can only depend on libs tagged with {{tags}}`. So "the error
says what to do" has to be carried by (a) the tag names themselves, (b) a comment block written beside the
constraints in eslint.config.mjs (what a developer or Claude opens next), (c) HOUSE.md, (d) a one-line command
that fixes it: a new `platform` generator.

Decisions:
- **Platform is a concept, not a Firebase detail** → `src/platform/` (tags, the lattice web/server/shared with
  shared as bottom, the classifier, the firewall writer). firebase-emulators only CALLS it.
- Constraints: web → only web|shared, bans server-only packages; server → only server|shared, bans web-only;
  shared → only shared, bans both. Every project in a web app's graph is then itself web or shared and checks
  its own imports, so `checkNestedExternalImports` (a rule-wide, whole-graph cost) is redundant — not set.
- **Every new project is classified at birth**: `StackAdapter.platform` (angular → web, js → shared);
  `LibOptions.platform` is REQUIRED (a library cannot be created through a port without one — compile-time);
  the `app` generator stamps the stack's platform; `publishable-lib --platform` (default: the stack's).
- **Classification without an enforcer is a label nobody checks**, so existing UNTAGGED projects are classified
  when the firewall arrives (firebase-emulators' first insertion) and, for workspaces that already have the old
  firewall, by migration 0.50.0 — never in a workspace without one.
- Classifier evidence: the project's own imports (server-only / web-only packages), the stack that builds it,
  and the platforms of the workspace projects it imports (fixed point). web+server → not classified, reported
  with the command. Also reported: every existing dependency the tightened firewall will now fail on.

## E3 — the Analog tsconfig warning

Reproduced by reading (not by running Nx's graph): `@nx/angular` 23.1 writes `libs/<lib>/vite.config.mts` with
`plugins: [angular(), …]` for a `vitest-analog` library (seen in a fixture run of navigation-core); Analog 2.8 resolves
the tsconfig in its `config` hook, defaulting to `tsconfig.app.json` outside `VITEST`/`NODE_ENV=test`.
Fix: `adapters/angular/analog-tsconfig` rewrites the bare call to `angular({ tsconfig: './tsconfig.spec.json' })` —
what Analog already uses under a test run, so tests see no change. Applied at creation by the Angular `libs` port,
and to existing libraries by migration `0.50.0/state-analog-spec-tsconfig` (every library, not only the house's — the
warning and the fix are identical; skipped: apps, configs naming a tsconfig, configs that also build → reported).
Upstream: @nx/vitest should pass the tsconfig itself; our rewrite then becomes a no-op (only a bare call matches).

Harness fix on the way: `unparseable` asserted on `.d.ts` files (transpileModule has no output for them) — the
vendored kernel's `strong-router.d.ts` was the first written by a generator case; it is now parsed instead.

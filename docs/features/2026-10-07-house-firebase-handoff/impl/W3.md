# W3 — each running dev stack (tree + port offset) has an identity

Unit of the implementation fan-out (`handoffs/20261007T020000Z-implement.md`). Scope: D1, D2 (design), D3, the
free-port probe. Worktree `hfh-w3`, branch `feat/house-firebase-handoff--w3`. Written as it happens.

## D2 — design rationale (written BEFORE implementing)

**The facts (Nx 23.1.0, read in `node_modules/nx/dist/src`; reproduced in V6):**

- `task-orchestrator.js` `startContinuousTask()` shares a continuous task whose id is already in
  `RunningTasksService` (the LOCAL workspace-data DB, per worktree). Only continuous tasks are shared. The id is
  `project:target[:configuration]`; overrides (`--port`, `--port-offset`) are not part of it.
- No opt-out: the only gate is `IS_WASM`. `continuous` comes only from the target configuration
  (`create-task-graph.js:209`), never from the CLI.
- A non-existent configuration is silently ignored by `combineOptionsForExecutor` (`utils/params.js:447`) — so a
  "per-offset configuration" would drop the leaf's `defaultConfiguration: development` options. Unsound.
- `NX_WORKSPACE_DATA_DIRECTORY` moves the running-tasks DB **and** the graph cache **and** the shared DB that
  indexes the computation cache (`db-connection.js`: an absolute value bypasses the main-worktree redirect). Cold
  graph + cache misses — ruled out by V6 and the user.

**Two levels collide, and they want opposite things:**

| Level | Target | Who depends on it | Is sharing right? |
| --- | --- | --- | --- |
| outer | `<app>:serve` (the composer) | e2e targets (`dependsOn: serve`), the developer | **Yes** — two `nx e2e` (or e2e beside the developer's `nx serve`) SHOULD reuse the one running stack. That is Nx's model, and it is right at this level. |
| inner | `<app>:dev-server`, `firebase:emulators*` (what the dev engine runs per process) | **nobody** — the engine spawns them by name; nothing in the house `dependsOn` them | **No** — each stack runs its OWN instance on its OWN shifted ports. A second stack's engine waiting on the first's dev-server (listening on the *other* stack's port) is the D2 bug. |

**Options weighed:**

1. Per-stack `NX_WORKSPACE_DATA_DIRECTORY` — cold graph, cache misses, and does not touch the outer level. Rejected.
2. Per-offset configuration so the task key differs — the offset is resolved by the engine AFTER Nx has already
   started the outer task, and a non-existent configuration silently drops the real one's options. Rejected.
3. The engine runs the leaf's executor itself (`@nx/devkit` `runExecutor`), no task runner — loses `dependsOn`
   (the emulators need the functions build), Nx's `.env` loading and sync; a second, divergent way to run a
   target. Rejected.
4. Agents call `tools/dev/dev serve` directly — removes the OUTER collision only; the inner one still bites
   (the engine itself runs `nx run <app>:dev-server`). Necessary, not sufficient.
5. **Identity at ONE level.** The stack is the instance. Nx models the stack as the `serve` composer — keep it
   `continuous` (e2e sharing stays exactly as it is). The processes the engine composes are the stack's parts,
   not separately-shared Nx instances: the targets the engine drives (`dev-server` leaf, `firebase:emulators*`)
   are **not** `continuous`. Nothing depends on them, so `continuous` bought only the sharing that breaks a
   second stack. A direct `nx run <app>:dev-server` still works (a long-running task); a second one at the base
   port now fails loudly on the bind instead of silently "sharing".

**Chosen: 5 + 4, plus a preflight at the outer level** — because the outer collision can still happen (a
developer typing `nx serve <app> --port-offset=3000` while `nx serve <app>` runs in the same tree), and Nx's own
"Waiting for <app>:serve in another nx process" then ends in a false "Successfully ran target serve":

- The composer `dependsOn` a non-continuous `serve-preflight` target (`params: 'forward'`), an executor that runs
  in the colliding nx process BEFORE Nx decides to share. It reads the stacks' run records (D3): when this tree's
  Nx already runs `<app>:serve`, it names the holder (offset, pid, URL, since, owner) and:
  - the request names a DIFFERENT stack (an explicit `--port-offset` or `--worktree` that the live stack is not)
    → **refuses** (exit 1) with the exact command that starts it (`tools/dev/dev serve <app> …`) and the one that
    stops the holder (`tools/dev/dev stop …`);
  - otherwise (plain `nx serve <app>`, or an e2e target depending on `serve`) → says that this run attaches to the
    running stack and will end when it stops, and how to get a second stack instead. Sharing proceeds.
- Migration `0.50.0/stack-owned-dev-processes`: removes `continuous` from the house-written `dev-server` leaf and
  the `firebase:emulators*` targets (the generators stop writing it; the migration is what reaches a project
  whose per-app steps are skipped, `UPGRADE_PARTIAL`, and does not depend on how owned targets are re-asserted).
  A project-brought leaf (another executor) is reported, not touched.

Why not detect the inner collision too: after 5 there is none for house-written targets; a project-brought
continuous leaf is reported by the migration with the fix.

**Verified on Nx 23.1.0 (scratch workspace, `nx:run-commands` stand-ins):** a second `nx serve app --port-offset=3000`
ran the preflight (flags forwarded: `[--port-offset=3000]`) BEFORE the share and its exit 1 stopped the run
("… failed"); a plain second `nx serve app` ran the preflight, then printed "Waiting for app:serve in another nx
process" — the attach path. Non-continuous targets run concurrently (V6).

## What was built

- **D3 — the handle.** `tools/dev/lib/stacks.mjs`: run record `<tree>/.bespunky/run/<app>@<offset>.json` (pid +
  kernel start time, host, owner, ports, child pids + their start times, url, nxRoot) and the stack's state dir
  (`DEV_STACK_DIR`, `${STACK_DIR}`); `.bespunky/run/` ignores itself (no root .gitignore line, no migration).
  States: live / orphaned (serve SIGKILLed, children alive — record KEPT as their only handle) / foreign (other
  host) / dead (pruned). `dev ps [app] [--json]`; `dev stop [app] [--worktree] [--offset=N | --all-mine]
  [--owner] [--any-owner]`: SIGTERM to the serve's verified PID (not the group — stack.mjs's signal rule: a group
  SIGTERM is the double signal that makes the emulator suite skip its export), wait, confirm ports free; an
  orphan's verified children get one SIGTERM each. Owner = `--owner`/`DEV_OWNER`, else `claude:<session>`, else
  `user:<name>`; another owner's stack is refused without `--any-owner`. A serve of a stack already running is
  refused naming it. Not exposed as Nx targets: a process-table query gains nothing from the task graph, and the
  engine is stack-free (works in a Python repo).
- **Free-port probe** covers every port of every non-skipped process (`boundPorts`).
- **D1.** `emulators.sh` exports `TMPDIR=$DEV_STACK_DIR/tmp` (fallback `.bespunky/run/firebase@<offset>`) for every
  stack incl. offset 0. ONE port table: `firebase-emulators/suite-ports.json` → read by `emulator-ports.ts`,
  projected into the owned `tools/emulator-ports.mjs` (`ports` / `shift` / `free-offset`), used by emulators.sh,
  reap-emulators.sh (no 4400/4500 literals, no `isolated` mode) and build-seeds.sh. Shift now moves declared
  nested ports (`firestore.websocketPort`) and pins undeclared defaults shifted.
- **Seed builds** (asked by W2 via the orchestrator): `build-seeds.sh` runs its own suite on a free SHIFTED block
  with its own TMPDIR and reaps only that block — it no longer reaps/binds the base ports.
- **D2** as designed above; migration `0.50.0/stack-owned-dev-processes` + fixture case.
- Docs: HOUSE.rules.md.tpl Local servers (teardown by handle, prove ports free, children stop what they started);
  HOUSE.md.tpl *Running stacks* (+ "main tree prefers 0" correction); local-server-isolation (description fires at
  stop time; Teardown section); delegate-and-parallelize (processes clause, litterbug, process roster, ledger).

# S1 — the flaky `emulators-stop.test.sh`: a PRODUCT race in the keeper's identity

Branch `feat/house-firebase-handoff--s1`, worktree `hfh-s1`.

## Verdict

**A product race, not a test race.** The detached keeper recorded the wrong kernel start time for itself.
About 1 time in 11 every reader of its entry then took the live keeper, still exporting, for dead. The test's
assertions were right. They caught a real data-loss path whenever the bad tick happened.

## The failures

The orchestrator and other agents reported failures in these cases: "restart waited" and "state dir is released".
A 30-run loop here (3 streams at once) failed once:

- `restart: the killed run's stack is FINISHING (its keeper still saving)`
- `restart: the new start's claim waited for the previous suite's save`

In the kept fixture, the second start had claimed `firebase@0` without the "is still finishing" wait. Over 10+ s of
polling, `dev ps` never once showed the first run's stack as FINISHING, even though its export takes 1.5 s.

## Root cause

`emulators.sh.tpl`, `keep()`:

```bash
KEEPER_PID=$BASHPID
KEEPER_START="$(proc_start "$BASHPID")"
```

A command substitution is a fork, and `$BASHPID` expands inside it. So this recorded the start time of a throwaway
subshell. That matches the keeper's own start time only when the fork lands in the same 10 ms clock tick. Measured
here, it differed in 26 of 300 tries (about 9%).

Every consumer checks the entry with `isSameProcess(pid, procStart)`. With the wrong start time, the live keeper reads
as **not alive**, which caused all of the following:

- **The script stops waiting at once.** `while is_proc "$KEEPER_PID" "$KEEPER_START"` falls through. The script exits
  without waiting for the export (the "stop was announced" case). Its supervisor is told the suite ended while it is
  still running.
- **`dev ps` reports ORPHANED.** In `recordState`, a dead-looking keeper makes the group members of its process group
  (the keeper itself, firebase-tools, the JVM) into `survivors`. So the stack reads ORPHANED, not FINISHING.
  `dev stop` on an ORPHANED stack **SIGKILLs those processes**, which kills a running export. **That is data loss.**
- **A restart's claim does not wait.** `ownPrevious` needs `finishing`. On ORPHANED, an explicit offset is
  refused. Once the keeper exits, the record is `dead`, gets pruned, and the new start claims with no wait at all
  (the failure above).
- **The keeper cannot release its own stack.** At its own release, its group still contains itself, so the stack
  stays ORPHANED and the record and state dir stay behind ("state dir is released"; "serve gone … removes").

To prove the cause deterministically, I forced the old line across a tick boundary
(`sleep 0.03; KEEPER_START="$(proc_start "$BASHPID")"`). Every run then fails exactly the reported family:

- nx release
- stop announced
- restart FINISHING
- restart waited
- serve-gone prune
- both abandon cases

Ctrl+C passes only by luck: the script's 2 s log drain catches the INT.

## Fix

Take the start time of the PID that was already captured, inside the keeper itself:

```bash
KEEPER_PID=$BASHPID
KEEPER_START="$(proc_start "$KEEPER_PID")"
```

No sleep or timeout was changed. There are no other `$BASHPID`-in-substitution sites: a sweep found that
`group_members`' `$BASHPID` runs in the keeper itself, and `PROXY_START` uses `$$`. The template is an owned
artifact that every upgrade regenerates, so **nothing to migrate**.

The test now also asserts directly that the keeper's recorded `procStart` equals `/proc/<pid>/stat`'s start time.
A recurrence then shows up under its own name, not as a downstream flake.

# V2 — adversarial verification (Node major, firebase-cli feature, functions engines, firebase-tools)

Paths relative to `plugins/house/engine/` unless stated.

## 1. Devcontainer Node major follows the upgrading machine — CONFIRMED (with a refinement)
- `house.sh:1008` (native path, local Node >= 22.18): `MAJOR="$(node -p 'process.versions.node.split(".")[0]')"`.
- `house.sh:1021` (Docker fallback): `MAJOR="$(base_image_node_major)"` -> `container-engine.sh:72-77` curls MCR's
  typescript-node tag list and takes the HIGHEST `<n>-bookworm` major (fallback `24`). So the two runtimes disagree
  by construction: native = host Node, Docker = newest published image. Neither consults the project.
- Flow: `house.sh:2068` passes `--node-major=$MAJOR` to `layers/cli.js plan` -> `cli.ts:54 nodeMajor` ->
  `layers/agent.ts:34` `--nodeMajor=${ctx.nodeMajor}` to the devcontainer generator -> `generator.ts:124`
  (`options.nodeMajor ?? process.versions.node...`) -> `compose(contributors, { nodeMajor })` -> `compose.ts:114`
  substitutes `{{nodeMajor}}` into:
  - `layers/node.ts:33` image `mcr.microsoft.com/devcontainers/typescript-node:{{nodeMajor}}` (-> `house.Dockerfile` FROM), and
  - `layers/agent.ts:54` feature `ghcr.io/devcontainers/features/node:1` `{ version: '{{nodeMajor}}' }` (agent-only hosts).
- Existing value preserved? No: `generator.ts` never reads the current Dockerfile/devcontainer for a major; the
  owned files are regenerated each upgrade (class A artifact).
- This repo: `.devcontainer/house.Dockerfile` `FROM mcr.microsoft.com/devcontainers/typescript-node:22`; local
  `node -v` = v22.23.2 — consistent with "set from the runner's Node". A teammate on Node 24 (or the Docker path)
  would flip it to 24.
- Scope refinement: "every house project" holds for every project whose devcontainer the generator composes
  (agent layer active). Adopted devcontainers keeping their own image source don't take the image tag.

## 4. firebase-tools not a devDependency — CONFIRMED
`firebase-emulators/generator.ts:296-299` adds only `firebase-admin`, `firebase-functions` (deps) and
`@nx/esbuild` + functions toolchain (devDeps). `git grep firebase-tools` in nx-tools src: comments only.
"Nx targets would find a local one": every invocation is an Nx target — `firebase:emulators` (dev-fragment.ts:34
runs `nx run firebase:emulators` -> tools/emulators.sh `exec firebase ...`), `deploy` (`firebase deploy --only
functions`, nx:run-commands), `push-secrets`. nx:run-commands prepends `node_modules/.bin` (Nx's appendLocalEnv) —
UNVERIFIED here (no nx package installed in this checkout to read), from Nx knowledge.

## 5. Remove feature in favour of devDependency is safer — LARGELY CONFIRMED, with conditions
- Bare `firebase` callers: `emulators.sh.tpl:243`, `seed-build-seeds.sh.tpl:31`, `push-secrets.sh.tpl:59`, the
  `deploy` target; docs/banners tell humans to run `firebase login`, `firebase use --add`,
  `firebase apphosting:backends:create` (environment.prod.ts.tpl, apphosting.yaml.tpl, firebase.config.ts.tpl).
  `firebase-banner.sh.tpl` only installs a profile.d hook, calls no `firebase`.
- `node_modules/.bin` on PATH in the container: yes — `layers/node.ts:43` contributes it to the composed
  `remoteEnv.PATH` (`compose.ts:172-179`), so interactive `firebase login` resolves to the local bin after install.
- Wrapper host: impossible to have a devDependency — but `layers/firebase.ts:28` `requires: ['nx', 'node']`, and
  `generator.ts:279-285` bails without a package.json. So firebase never lands on a wrapper host; non-issue.
- Conditions: the local bin exists only after `yarn install` (post-create runs it); outside the devcontainer the
  user needs no global either. Also gcloud-cli has no npm equivalent — it stays a feature and still needs pinning.
- Also owed: a migration (class B, package.json) to add firebase-tools to existing firebase projects, and an
  adopted-devcontainer cleanup of the feature via houseWrote().

# V8 — adversarial verification: emulator routing, port forwards, offsets

Verified 2026-10-07 by reading every cited line in this worktree, the published SDK sources
(`@firebase/firestore` 4.17.2, `@firebase/storage` 0.14.5; their original TypeScript recovered from the shipped
sourcemaps), `firebase-tools` 15.32.1 (npm pack), the containers.dev spec, and VS Code `main`
`tunnelModel.ts`. Paths below are under `plugins/house/engine/nx-tools/src/`.

## 1. Auth + Functions go through the origin when `proxied`; Firestore/Storage always dial ports — CONFIRMED

- `generators/firebase-emulators/environment.ts.tpl:53` `auth: {…, proxied: true}`; `:60` `functions: {…, proxied: true}`;
  `:54-55` firestore/storage have no `proxied`.
- `firebase-auth.config.ts.tpl:52-56`: `proxied && typeof window !== 'undefined' ? window.location.origin : offsetUrl(e.url, portOffset)`.
- `firebase-functions.config.ts.tpl:46-52`: proxied → `connectFunctionsEmulator(functions, location.hostname, port)`.
- `firebase-firestore.config.ts.tpl:46` `connectFirestoreEmulator(db, e.host, e.port + portOffset)` — unconditional.
- `firebase-storage.config.ts.tpl:34` `connectStorageEmulator(storage, e.host, e.port + portOffset)` — unconditional.
- `proxy.conf.mjs.tpl` relays only `/<projectId>` and the four Auth prefixes, with `changeOrigin: true`; its header
  states Firestore is deliberately not relayed.

## 2. migrations/0.24.3 deliberately leaves `proxied` off — CONFIRMED

`migrations/0.24.3/upgrade-emulator-environment-shape.ts:36-40`: "It does not add `proxied: true` … turning it on here
would change RUNTIME ROUTING on a project mid-upgrade … Direct dialling is what these projects already do". `:470`

## 3. App/emulator forwards lack `requireLocalPort` — CONFIRMED; but `requireLocalPort` does NOT fail, it STILL SHIFTS

- `layers/angular.ts:52` `ports: [{ port: …basePort, label: 'Angular Dev Server', onAutoForward: 'openPreview' }]` — no flag.
- `layers/firebase.ts` `clientDevServerPorts` (~`:112-130`) and `emulatorForwards` (`:131-139`) — no flag. The only
  user is `layers/web.ts:139` (noVNC band); `compose.ts:419` passes it through when set.
- Spec (containers.dev json_reference): "If set to `false` … silently map to a different one if it is unavailable. If
  set to `true`, you will be notified if it is not possible to use the same port."
- VS Code `src/vs/workbench/services/remote/common/tunnelModel.ts` `showPortMismatchModalIfNeeded`: when
  `requireLocalPort` and `tunnelLocalPort !== expectedLocal`, it shows an **info dialog** — "Local port {0} could not
  be used … Port number {2} has been used instead." The tunnel is already established on the other port; nothing is
  refused. A `MISMATCH_LOCAL_PORT_COOLDOWN` also suppresses repeat dialogs, so several mismatching ports at once
  (an emulator suite) can produce **one** dialog. Exact-key-only honouring is confirmed (`:232` exact key vs `:239`
  ranges never set it), matching `novnc-band.ts`'s comment.
- Consequence: adding the flag turns a silent shift into a **notified** shift. It does not make the Firebase SDK's
  hard-coded `localhost:<port>` work, and it cannot see a squatter that does not block the local bind.

## 4. Can Firestore and Storage be relayed through the dev-server origin? — FEASIBLE, with three caveats the claim must carry

### Firestore (`@firebase/firestore` 4.17.2)
- `lite-api/database.ts:321-358` `connectFirestoreEmulator(host, port)`: `host: \`${host}:${port}\``, `ssl: isCloudWorkstation(host)`.
  `isCloudWorkstation` = `host.endsWith('.cloudworkstations.dev')` (`@firebase/util`). So it accepts the page's
  hostname + port, but **forces `http`** on any other host. **An https dev server breaks it** (mixed content /
  TLS-on-plain mismatch).
- Workaround that keeps https: `initializeFirestore(app, { host: location.host, ssl: location.protocol === 'https:' })`
  — `lite-api/settings.ts:143-156` accepts any `host`+`ssl`. The only thing `connectFirestoreEmulator` adds is
  `emulatorOptions` → `isUsingEmulator`, which in 4.17.2 is only stored in `DatabaseInfo` (`core/database_info.ts:52`,
  `lite-api/components.ts:125`), never read for behaviour; `mockUserToken` would be lost. Note the template uses
  `getFirestore()`, so this would mean switching to `initializeFirestore`.
- Paths (all origin-relative, so a path proxy can forward them):
  - streams (Listen/Write over WebChannel, long-polling or fetch streams alike):
    `${baseUrl}/google.firestore.v1.Firestore/<Listen|Write>/channel` (`platform/browser/webchannel_connection.ts:53,222-229`);
  - unary REST (commit, batchGet, runQuery, runAggregationQuery…): `${baseUrl}/v1/projects/<pid>/databases/<db>/documents…:<rpc>`
    (`remote/rest_connection.ts:76-80,202-213`). **The relay must cover `/v1/projects/<projectId>/databases` too**,
    not only `/google.firestore.v1.Firestore`. Headers sent are ordinary (`google-cloud-resource-prefix`,
    `x-goog-request-params`, `x-goog-api-key`); WebChannel encodes init headers into the POST body
    (`encodeInitMessageHeaders = true`, `:281`). The proxy must not buffer responses (http-proxy streams by default).
  - So the "gRPC-Web transport needs its own design" note in `proxy.conf.mjs.tpl` / `HOUSE.md.tpl:272` overstates it:
    the browser SDK speaks WebChannel/HTTP, not gRPC, on two path prefixes.

### Storage (`@firebase/storage` 0.14.5)
- `service.ts:140-155` `connectStorageEmulator`: `host = \`${host}:${port}\``, `_protocol = isCloudWorkstation(host) ? 'https' : 'http'`
  — same forced-http limitation; `storage.host`/`_protocol` are not public settings, so there is no clean https
  workaround.
- URLs: `implementation/url.ts makeUrl` → `${protocol}://${host}/v0${urlPart}` → everything under **`/v0/b/`**.
- **Resumable uploads trap**: the URL for subsequent chunks comes from the emulator's `X-Goog-Upload-URL` header
  (`implementation/requests.ts:441`), which `firebase-tools` builds from the **request's `Host` header and protocol**
  (`lib/emulator/storage/apis/firebase.js:225-230` → `registry.js:95-103`). The existing `relay()` uses
  `changeOrigin: true`, which rewrites `Host` to `localhost:<emulator port>` — so uploads > the multipart threshold
  would bounce the browser straight back to the emulator port. A Storage relay needs `changeOrigin: false` (or a
  header rewrite), and even then `req.protocol` is `http`, so an https dev server would get an http upload URL.

## 5. SSR uses offset 0, so a worktree's SSR dials the main stack — CONFIRMED (conditional on SSR existing)

- `firebase.config.ts.tpl:128` `export const portOffset = ngDevMode ? resolvePortOffset() : 0;`
- `emulator-overrides.ts.tpl:92-96` `win = typeof window === 'undefined' ? undefined : window; if (!win) return 0;`
- No browser-side template reads `process.env.PORT_OFFSET` (grep: only `proxy.conf.mjs.tpl` and shell scripts do).
  Auth's proxied branch also falls back to `offsetUrl(e.url, 0)` server-side. So any server render in a shifted
  worktree hits base-port emulators. The house does not scaffold SSR itself (no `ssr`/`server.ts` in `adapters/`
  or the app generator), so this bites only apps that add SSR.

## 6. `resolvePortOffset` probes only the app's own ports — CONFIRMED (for the dev loop's resolver)

`generators/dev/files/dev.mjs.tpl:195-200` passes `probed: Object.values(primaryOf(app).ports)`; `lib/ports.mjs.tpl:77`
documents `probed` as "the PRIMARY process's ports — the app's own"; `:98,:111` `allFree(probed, …)`. The emulator
ports only size the block (`block = portBlock(declaredPorts(app))`), never decide freedom. (The browser-side
`resolvePortOffset` in `emulator-overrides.ts.tpl` is a different function that just reads `?portOffset=`.)

## Verdict on "route everything through the origin"

Feasible for an **http** dev server: Firestore needs two relay prefixes (`/google.firestore.v1.Firestore`,
`/v1/projects/<pid>/databases`) and Storage one (`/v0/b`) plus `changeOrigin: false`. Not achievable with the stock
`connect*Emulator` APIs under an **https** dev server (both force http off Cloud Workstations); Firestore can dodge
that via `initializeFirestore({host, ssl})`, Storage cannot cleanly. SSR still needs `PORT_OFFSET` from the server
environment — origin-relaying is a browser-only answer.

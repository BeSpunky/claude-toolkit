# V5 — two emulator suites, one project id: does export-on-exit swap data?

Verdict: **CONFIRMED** (observed, firebase-tools 15.32.1 = npm latest at test time). Plus a second, worse failure mode the claim did not name. The offset-map claim is literally true but its impact is overstated.

## Source (firebase-tools 15.32.1, `lib/emulator/`)

- **Locator key** — `hub.js` `EmulatorHub.getLocatorFilePath(projectId)`: `path.join(os.tmpdir(), \`hub-${projectId}.json\`)`. Keyed by project id ONLY (and `TMPDIR`); not by config, cwd or hub port. Contents: `{version, origins:[hub URL], pid}`.
- **Second suite does NOT register** — `hub.js` `writeLocatorFile()`: if an existing locator's pid is live (`isProcessLive` = `kill(pid,0)`), it logs *"It seems that you are running multiple instances of the emulator suite for project X. This may result in unexpected behavior."* and **returns** — no locator written, no cleanup handler installed. The warning is only a log line; the second suite's own hub still listens on its port, but nothing can find it.
- **Export routes via the locator** — `controller.js` `onExit → exportOnExit → exportEmulatorData(path)` builds `new EmulatorHubClient(projectId)` (`hubClient.js` constructor reads `readLocatorFile(projectId)`), `postExport` POSTs `/_admin/export` to the FIRST suite's hub. That hub (`hub.js` createExpressApp, `PATH_EXPORT` handler) runs `new HubExport(...).exportAll()` against **its own process's** `EmulatorRegistry` (`hubExport.js`) — i.e. the other suite's emulators — writing into the path the caller supplied.
- **Cleanup** — the first suite's exit handler deletes the locator (pid matches). After that, `exportEmulatorData` throws "Did not find any running emulators for project"; `exportOnExit` catches, logs "Automatic export ... failed, going to exit now...".

## Reproduction (auth emulator only — no Java on this host, so no firestore; same hub/export path)

Script: `/tmp/claude-1000/-workspaces-claude-toolkit/e1012b18-1895-4ed1-a84a-b6122db345e0/scratchpad/v5/scripts/repro.sh` (two dirs, random 127.0.0.1 ports for auth/hub/logging, project `demo-v5repro<rand>`, ui off). A started plain; B started with `--export-on-exit B/export`. One user signed up in each suite. Full output: `/tmp/claude-1000/-workspaces-claude-toolkit/e1012b18-1895-4ed1-a84a-b6122db345e0/scratchpad/v5/run1.txt`, `/tmp/claude-1000/-workspaces-claude-toolkit/e1012b18-1895-4ed1-a84a-b6122db345e0/scratchpad/v5/run2.txt`.

Run 1 (B exits first):
- locator after A: `{"origins":["http://127.0.0.1:38387"],"pid":433216}` (A). After B started: **unchanged** (still A's hub/pid). B.log: the "multiple instances" warning.
- On B's SIGINT, B.log: "Found running emulator hub for project ... at http://127.0.0.1:38387" (A's hub). A.log: "Received export request. Exporting data to .../B/export".
- `B/export/auth_export/accounts.json` users: **`['in-suite-a@example.com']`** — A's data, B's own user lost.

Run 2 (A exits first, then B):
- A's exit deleted `/tmp/hub-<proj>.json`. B's exit: "Automatic export to .../B/export failed, going to exit now..." — **no export at all**; B's session data lost.

So for the house: a worktree stack (PORT_OFFSET≠0, same derived project id, same container `/tmp`) started while main's suite runs exports **main's** world into `.emulator-data-<offset>` on exit (data swap), or exports nothing if main stopped first. Symmetrically, main restarted while a worktree suite owns the locator would export the worktree's world into `.emulator-data`. Shifted hub ports do not help: the locator, not the port, routes the export.

## Offset map (emulators.sh.tpl:54-70)

The node one-liner shifts `port` of every **top-level** `emulators.<k>` entry that has a numeric port, and pins hub/logging shifted. Consequences:
- `eventarc`, `tasks`: shifted **only if firebase.json declares them** (the house block — `HOUSE_EMULATORS` = auth, firestore, storage, functions, ui — does not). Unset, firebase-tools does NOT bind 9299/9499 fixed: `constants.js` `FIND_AVAILBLE_PORT_BY_DEFAULT` has `eventarc: true, tasks: true`, so `getListenConfig` marks them portFixed=false and `resolveHostAndAssignPorts` picks a free one. Not shifted → but no collision.
- `firestore.websocketPort` is nested, so it is **never** shifted, even when declared. Unset: `controller.js` sets port 9150 with `portFixed: !!wsPortConfig` = false → floats to a free port (no collision, but the forwarded 9150 then belongs to main). Declared: fixed and unshifted → the offset suite would collide on it.
- So "doesn't shift eventarc, tasks or websocketPort" is CONFIRMED as a reading; as a collision risk it is real only for a declared `websocketPort` (or the floating ports being unpredictable for host forwarding).

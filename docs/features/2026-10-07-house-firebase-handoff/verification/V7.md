## 1. Targets are re-asserted every upgrade — CONFIRMED (shallow, per-target replace)

`generators/_utils/project-files.ts:180` — `config.targets = { ...(config.targets ?? {}), ...owned.targets };`
(tags at :179 are unioned). A one-level spread: each house-owned target KEY is replaced wholesale; nothing inside it
is merged. The header comment (:104-106) says so deliberately ("WHAT IS OURS? The house's targets and tags —
re-asserted on every run").

| `functions:deploy.options.args`, `.configurations` | **gone** |

The generator runs on upgrade: `layers/firebase.ts:31` `ensurable: { upgrade: true }`, `workspace:` steps (:63-65)
include `firebase-emulators`. So (a) a newly declared house target reaches existing projects with no migration,

`emulators`/`functions` keys, generator.ts:193-200) as class A-ish "owned", contradicting CLAUDE.md's listing of
`project.json` targets and `firebase.json` as class B. The code is what runs; CLAUDE.md is inaccurate (or the code
violates it) for house-owned targets/keys. Project-added targets/keys are left alone, consistent with B for those.

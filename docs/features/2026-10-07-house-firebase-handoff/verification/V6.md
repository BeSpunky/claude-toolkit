# V6 — Nx shared continuous tasks vs. two dev-servers of one project

Verifier: adversarial, Nx **23.1.0** (`/workspaces/claude-toolkit/node_modules/nx`). Reproduced in a scratch
workspace (`app/project.json`, `dev-server` = `continuous: true`, `nx:run-commands` `sleep 30`), `NX_DAEMON=false`.

## Mechanism (source)

- `nx/dist/src/tasks-runner/task-orchestrator.js`
  - ctor L61: `this.runningTasksService = !IS_WASM ? new RunningTasksService(getLocalDbConnection()) : null`
  - `startContinuousTask()` L897-919: if `runningTasksService.getRunningTasks([task.id]).length` → wraps in
    `SharedRunningTask`, sets TUI status `Shared`, never spawns. Else spawns and `addRunningTask(task.id)` (L936).
    This check exists ONLY in `startContinuousTask` — non-continuous tasks are never shared.
- `running-tasks/shared-running-task.js`: prints `Waiting for ${taskId} in another nx process`, polls every 100 ms
  until the id leaves the table, then fires exit callbacks with **code 0**.
- Key = `task.id` = `createTaskId(project, target, configuration)` (`tasks-runner/utils.js` L445) →
  `app:dev-server[:config]`. Overrides such as `--port` are NOT part of it.
- Store = native `RunningTasksService` on `getLocalDbConnection()` (`utils/db-connection.js`): the DB in
  `workspaceDataDirectoryForWorkspace(workspaceRoot)` = `NX_WORKSPACE_DATA_DIRECTORY ?? NX_PROJECT_GRAPH_CACHE_DIRECTORY ?? .nx/workspace-data`,
  deliberately per-worktree (not the main-repo shared DB). `workspaceRoot` honours `NX_WORKSPACE_ROOT_PATH`.
- No supported opt-out: the only gate is `IS_WASM`. No env var / flag.

## Observed

| Run | Result |
|---|---|
| A `nx run app:dev-server --port=41001`, then B `--port=41002` same tree | B: `Waiting for app:dev-server in another nx process`, nothing spawned |
| A ends normally (30 s) | B exits **"Successfully ran target dev-server"** without ever having run — not "forever", but for A's whole life, then a false success |
| C with `NX_WORKSPACE_DATA_DIRECTORY=<other dir>` while A runs | C spawns normally — isolation works |
| A killed with SIGKILL, then B | B runs — entries are liveness-checked, no stale lock |
| `app:dev-server:x` (other configuration) while default runs | runs — configuration is part of the key |
| non-continuous target run twice concurrently | both run |

## House path

- `fragments/nx.ts`: the dev engine spawns `<nx> run <project>:dev-server --port=${PORT:app}` with
  `NX_DAEMON=false`, `NX_WORKSPACE_ROOT_PATH=${TREE}`. The leaf is `continuous: true`
  (`adapters/angular/index.ts` L232). So two `tools/dev/dev serve <app>` stacks of the SAME tree (any offsets)
  collide. Different worktrees do not (per-tree local DB).
- Not house-specific: any second `nx run app:dev-server` (e.g. an agent's) in the same tree collides, either way round.
- The `serve` composer is ALSO `continuous: true` (`generators/_utils/dev-server.ts` `composerFor`), so a second
  `nx serve app --port-offset=N` in the same tree blocks at `app:serve` in the user's own nx process — before the
  dev engine (and any env it sets for its children) is reached.

## Proposed fix: per-stack NX_WORKSPACE_DATA_DIRECTORY

Works for the inner `nx run …:dev-server` (observed). Costs/limits:
- Outer `nx serve` collision is untouched (env set by the engine can't reach the parent nx process).
- Same dir also holds project-graph.json/file-map/lockfile-parse caches → a fresh dir = cold graph compute on
  first run (keep it stable per stack, e.g. keyed by offset, not random).
- `getDbConnection()` (shared DB, which indexes the local task cache via `NxCache`, plus task history) also
  resolves through the variable (an absolute value bypasses the main-worktree redirect) → cache hits recorded in
  the default DB are invisible to the stack; `dependsOn` builds may re-run.
- Daemon dir (`daemon/tmp-dir.js`) moves too — moot with `NX_DAEMON=false`.
- Inherited by the dev-server and everything it spawns.
Alternatives to weigh: drop `continuous` on the leaf the engine drives (sharing is continuous-only; but loses
`dependsOn` semantics for e2e consumers), or have the engine invoke a non-continuous target/configuration.

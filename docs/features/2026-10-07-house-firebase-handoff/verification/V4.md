# V4 — "root apphosting*.yaml are never read; every staging backend ships prod config"

**Verdict: REFUTED (as stated).** The mechanism is wrong: App Hosting's build walks UP from the backend root
directory to find `apphosting.yaml`, so root-level files ARE read for a backend rooted at `/apps/<app>`.
There are real staging defects, but they are different ones (below).

## 1. What the toolkit writes / tells the user

- `plugins/house/engine/nx-tools/src/generators/firebase-emulators/generator.ts:205-209` — writes
  `apphosting.yaml` and (with `--staging`) `apphosting.staging.yaml` at the **workspace root**, only when a client
  app exists. `apphosting.staging.yaml` = `scripts.buildCommand: npx nx build <app> --configuration=staging`.
- `firebase.json`: the generator asserts only `emulators` and `functions` (generator.ts:197-200). It **never
  writes an `apphosting` key / `rootDir`**. (The consumer's `apphosting.rootDir` was user-added; that key is for
  `firebase deploy` source deploys, firebase-tools `deploy/apphosting/index.js`.)
- **No toolkit text names a Root Directory at all.** `git grep -i "root dir"` over `plugins/` finds nothing
  relevant. HOUSE.md.tpl:249, SKILL.md:477, apphosting.yaml.tpl:10, firebase-welcome.sh.tpl:59 all say just
  `firebase apphosting:backends:create --project <projectId>` ("interactive — picks region and links a GitHub
  repo"). HOUSE.md.tpl:253 / SKILL.md:472,483: "Tweak build/runtime behavior in `apphosting.yaml` at the
  workspace root."
- firebase-tools 15.32.1 `apphosting/backend.js:90-93`: the interactive prompt is
  `message: "Specify your app's root directory relative to your repository", default: "/"`. So following the
  toolkit, a user who presses Enter gets root `/`.
- Staging binding: HOUSE.md.tpl:262 and apphosting.staging.yaml.tpl:7 say
  `firebase apphosting:backends:create … --environment staging`. **That flag does not exist** —
  `commands/apphosting-backends-create.js` options are only `--app, --backend, --service-account,
  --primary-region, --root-dir` (+ `--runtime` behind the abiu experiment). The tpl's alternative ("or set the
  backend's environment to `staging` in the Firebase console") is the only working path.

## 2. Official semantics

Docs (firebase.google.com/docs/app-hosting/multiple-environments): "create an apphosting.yaml file in your
app's root directory." / "…`apphosting.ENVIRONMENT_NAME.yaml` … must be located in your app's root directory
alongside apphosting.yaml." / "Each App Hosting backend has an Environment name setting. This field is used to
map your backend to an environment-specific configuration file … For backends without an associated
environment name, you can continue to use apphosting.yaml." Set via console: Settings tab → Environment →
Environment name.

**Actual implementation** (GoogleCloudPlatform/buildpacks @ 2f69b08, the App Hosting builder):
- `cmd/firebase/preparer/main.go:113` — `filesystem.DetectAppHostingYAMLPath(*workspacePath, *backendRootDirectory)`.
- `pkg/firebase/util/filesystem/filesystem.go` `detectAppHostingYAMLRoot`: "If no apphosting.yaml file is found
  in the root directory or any parent directories…" — loops `current = path.Dir(current)` up to `/`, stopping at
  the first dir containing any file matching `^apphosting(\.[a-z0-9_]+)?\.yaml$`.
- `pkg/firebase/apphostingschema/apphostingschema.go:366-372` — env override path is
  `filepath.Join(filepath.Dir(appHostingYAMLPath), "apphosting.<env>.yaml")`, and `if environmentName == "" { return nil }`.
  ⇒ With rootDir `/apps/<app>` and no apphosting files in `apps/<app>`, the **repo-root** `apphosting.yaml` and
  `apphosting.staging.yaml` are found and merged. The docs' "app's root directory" is the recommended placement,
  not an exclusive lookup.

Nx (docs/app-hosting/monorepos): "If you don't specify the "root directory" field for Nx, then the build will
fail and display a message that App Hosting can't find a project to target inside the Nx monorepo." Example:
"The app's root directory relative to your repository is apps/target-app." / "For Nx + Angular applications,
you must use the Angular application build system … specified in project.json." So rootDir = the app IS
required for the framework-adapter Nx build; the docs offer no repo-root + app-target alternative.

## 3. Correct statement of the problem

- Root files are read (walk-up) under the correct rootDir `/apps/<app>` — claim's mechanism false.
- Real defect A: toolkit guidance never tells the user to set Root Directory to `<appsDir>/<app>`; the CLI
  default `/` is what they get, and per the Nx doc the default-build (prod) backend then fails. (A staging backend
  at `/` runs the explicit `npx nx build` buildCommand and may build, but that is incidental.)
- Real defect B: the staging override applies only if the backend's **Environment name** = `staging`; the toolkit's
  stated way to set it (`--environment staging`) is a non-existent CLI flag. If the user follows that line and it
  errors/they skip it, environmentName is "" and `MergeWithEnvironmentSpecificYAML` returns early ⇒ staging builds
  with prod config. So "staging ships prod" is true **only when the Environment name was not set** — not because
  of file location.
- Fragility (not a current bug): if anyone later adds any `apphosting*.yaml` inside `apps/<app>`, the walk-up stops
  there and the root files are silently ignored.
